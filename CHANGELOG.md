### Added
- The sample model shows the whole metamodel: a domain model (Payments, Accounts, Customers and Fraud & Risk with eight entities, realised by the services), the Payment and Fraud case lifecycles as state machines with their events and who emits them, and eight concern packs from the Hub (authentication, authorization, encryption, personal data, data consistency, messaging, availability, backup and recovery) answered for a bank and bound to its systems; its 36 views sit in the folders Conceptual, Logical, Governance and Concerns, new views of the Domain map, Domain model, State machines, Entity lifecycles, Event catalogue, Domain realisation, Requirement coverage, Requirement gaps and Fitness functions viewpoints among them, and every Structure view is laid out by Smart Layout
- Use cases page on radical.tools (`usecases.html`, *Use cases* in the site navigation): six ways to use one model, from a modelling tool instead of a drawing tool, through requirements that stay attached to the architecture, one language across the organisation and a model from a brief or from the code you have, to the architecture the code follows and a harness for vibe coding, each with when, how (which parts of the family) and what it gives
- Concern Hub — the Hub holds concern packs, each settling one concern (authentication, personal data, secrets, deployment, …) in nine groups by where the decision is made: Architecture (style, monolith or services, communication style, module boundaries), Identity & access, Security, Data, Integration, Reliability, Operations, Maintainability and Technology (backend stack, frontend stack, infrastructure, data store). A pack asks three to five questions; the answers pick the requirements (EARS, each with its scenario), the decision (an ADR naming technologies and criteria), the fitness functions (each with its tool and a rule or test to copy) and the need, all linked. Every pack rests on named sources (OWASP ASVS, NIST, the GDPR, Google SRE, …) kept in the pack; the catalogue refuses a pack below that standard. Packs are written as specs (`packages/hub-catalogue/packs/`) and built with `npm run build:packs`
- The concern wizard in Studio (*Import from Hub* → *Add to Model*, or *Answer the questions…* in the Inspector): where the decision applies (the fewest elements that cover what the concern applies to, checked, and any other element), one question a step, the details and a review; it binds the pack to any number of elements, or none, as one undo step. A Hub link with several packs opens their wizards one after another. Every imported pack (in Studio, over MCP and in Forge) gets a canvas view of its own in the folder *Concerns*, with what it brought and what it is bound to
- The Hub as a critic: `radical check` and the Inspector report `concern-unaddressed` for a concern a pack's trigger finds in the model and no accepted decision covers (with the pack's questions), and `concern-unbound` for a decision that constrains no element; the MCP server's `get_issues` lists the open concerns with where to bind them, and `forge_import_hub_concept` imports a pack with the answers, bound to the elements given or unbound
- Radical Forge settles concerns early: in the Requirements stage the model picks the concern packs the description calls for and their questions join the stage's, those the description already settles answered from it, with its words, for the user to accept or change (in Studio and over MCP); the packs come in whole before the stage, later stages are told what is decided, and after the C4 stage what is still unbound is bound where each pack's trigger points (in Studio and over MCP)

Claude Code skills `crucible-explore` and `crucible-fix` run a round and a fix round on this repository; `docs/EXPLORATORY-TESTING.md` asks for the report's JSON block

- Dragging is calm: a drag moves only the dragged element — with the other selected elements and the members of its rows and columns, which follow it across the line (an ordered line pushes the next member ahead) — and the live physics no longer runs while you drag. On the drop, the elements it now covers are pushed clear, each whole and in one direction, and a container that grew pushes its neighbours the same way; nothing else moves. On this repository's own architecture model (499 elements), dragging an element used to move 44 of the 45 elements shown, the farthest by 27 000 px, and they kept moving for 4 s after the drop; now 5 move, by at most 80 px (the frames of the containers around it growing), and nothing moves after the drop. Hold ⌘/Ctrl when starting a drag for the old behaviour, the physics making room around it. Dragging a selection of several elements now moves them all (the physics used to put the others back)
- Expanding a large container under the live physics stays smooth (on a 150-node, 300-edge canvas: main-thread long tasks 3.6 s → 0.15 s over five seconds, frames over 50 ms 40 → 2): edges skip routing around obstacles while the layout moves and route once it comes to rest, the Relations list subscribes once instead of once per row, the closed Radical Forge dialog no longer follows every move, and the canvas no longer re-renders on every camera frame of Smart fit, a pan or a zoom

Under the live physics the canvas no longer draws, for a few frames, an arrangement the physics then discards (siblings pushed aside, snapping back)

- Opening a view, or loading a document, sets the camera at once instead of flying from the previous view's camera (each view has its own coordinates, so the diagram vanished and slid in from an edge): with Smart fit on, the view is fitted in the first frame that draws it and followed while it settles; with Smart fit off, the view's saved camera is used
- Smart fit keeps the diagram on screen: when no element is in view any more (the live layout carried the diagram off after an expand or collapse), it fits the diagram again; it waits 2 s after you pan or zoom by hand
- The expand / collapse button in a container's header is larger (28 px, bolder + / −) and reacts to clicks a little around it, so it is easy to hit on a zoomed-out canvas; a click on it also works when an edge between the container's children is drawn over it (it used to select the edge)

### Fixed
- Deleting an element takes it out of the references that named it: a transition's trigger event and the events it raises, a requirement's precondition state. They pointed at nothing, and Validation said the edit broke the metamodel
- `radical harden --gate` judges an e2e test: a runner's `build` in `crucible.json` is made before the run without the fix and before the run with it (Playwright served the build made with the fix both times, so every e2e test passed without its fix), and its `repeat` makes the runs at once one Playwright run (five processes fought for the same fixed ports); `--test "<file> › <describe> › <name>"` finds the test (it matched none); the gate's Playwright runs no longer overwrite `reports/e2e.json`
- `radical explore record` keeps the screenshot a finding names: it is copied beside the finding's script and named in the finding (it was dropped); it warns about a copied script that names the repository's or the round's absolute paths, which run only where the round ran, and the round's brief asks scripts to find the repository by walking up instead
- `radical explore verify` serves every server `crucible.json`'s `explore.serve` lists, each on its port of the run (Studio and the Hub in this repository); it served Studio alone, so scripts that tested the Hub failed
- `radical harden --gate` interrupted with Ctrl+C or `kill` stops the test and puts the fix back (the changed files and the new ones) before it ends, with exit status 2; it used to end with the working tree set back to the base and the new files deleted, their only copies in a temporary folder nothing named
- Presenter: *Capture* on a slide while a milestone is shown links the slide to that milestone, as *Add slide* does; it used to keep a hidden copy of the milestone, and the slide went on showing it after the milestone was deleted
