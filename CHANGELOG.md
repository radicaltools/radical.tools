# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Architecture Hub — browse and import 120+ curated architecture concepts
- AI assistant integration (OpenAI, Anthropic, Gemini, Ollama)
- Smart Layout pipeline with SA-based auto-layout
- Metamodel editor — customise node types, relation types, and constraints
- Milestone-based time travel (named undo/redo snapshots)
- Multiple view types: Canvas, Matrix, Sequence, Treemap, Table, Wiki
- Presentation mode with fullscreen slides
- C4 model elements: Person, Software System, Container, Component, Database, Web App, Queue
- Domain & Governance elements: Domain, ADR, Fitness Function, Requirement, Blueprint
- Multiple layout engines: ELK (hierarchical/layered/force), webcola, Smart Layout
- PNG/SVG export, JSON save/load
- Electron desktop app + browser mode
- Mockup element (UX) with screen / route, design link and a low-fi SVG wireframe — generated by AI from the linked requirements and scenarios, sanitised and rendered as an image; shown on the canvas, in the properties panel and on Wiki pages
- Mockup relations: Illustrates (→ requirement / scenario), Presented by (→ web app / container), Navigates to (→ mockup) for screen flows
- Need element (governance, ISO/IEC/IEEE 29148 "stakeholder need") for raw free-text input — a brief, user story, meeting notes, a quoted regulation or raw requirements — kept verbatim as its description (the Markdown body of its file in a folder model), with kind and source (no status — being in the model means it is accepted); EARS requirements derive from it (`derives`: requirement → need), needs nest under broader needs the same way (need → need, asked as "Part of" in its wizard), and its Wiki page and the table's Need tab show what derives from it as a tree
- Radical Forge stores its input description as a Need when a run starts (or starts from an existing one picked on the Description step), and links the extracted requirements to it
- Sample model shows where its requirements come from: three Needs — the PSD2 & AMLD6 obligations, a retail payments brief and a corporate treasurer's feedback — each with the EARS requirements derived from it, in the Requirements Traceability view, the Requirements Register and the Product Wiki
- Radical Forge: Mockups stage before C4 with batch wireframe generation, "Finish here" at every stage with a summary step, and a single footer action bar
- Hub blueprints: per-actor screen flows (79 mockups in 19 flows) and named views — canvas: System context, Containers, Governance map, Mockups, technical flow, one per screen flow; wiki: Governance, Requirements; a per-mode view selector and `/cv/<viewId>` deep links in the Hub; views are imported with the concept
- Sample model showcases the product layer: 10 EARS requirements (with a `derives` decomposition), 5 Gherkin scenarios and 13 UI mockups with wireframes in three per-actor screen flows (customer, corporate, operator), a Back Office Console web app and an accessibility fitness function; new views — Screen Map, one flow view per journey, Requirements Traceability, Requirements Register (table) and a multi-page Product Wiki — a v4 "Product & UX" milestone and matching presentation slides
- Welcome screen: on a first visit the sample model gets its own card (preview, what it contains, "Explore the sample") in place of the placeholder diagram, and opens on the System Context view instead of the all-elements canvas
- Desktop installers for macOS (dmg, Apple Silicon + Intel), Windows (NSIS) and Linux (AppImage), built by electron-builder and drafted as a GitHub Release when a `v*` tag is pushed
- App icon for the desktop builds
- Node wizards: creating an ADR, fitness function, requirement, scenario or mockup — on the canvas, in a table or from a wiki page — opens a step-by-step form with guidance per field and a final step for its relations (constrains, supersedes, satisfies…); the element is created when the wizard finishes, as one undo step. Reopen it for an existing element from the properties panel; turn the automatic wizard off with *Wizard on create* in the app menu. Wizards are metamodel data (`NodeTypeDef.wizard`), so custom node types can have them too
- Markdown-folder models follow edits made outside Studio (another editor, `git pull`): the active document's folder is polled (desktop every second, browser every two) and reloaded from disk, keeping the open view and selection; a save never overwrites a file changed on disk since Studio read it
- Alignments: select two or more elements and choose *Align… → Keep in a row / Keep in a column* to keep their centres on one line on this canvas (All elements or a view, each its own). Drags, the live physics and Smart Layout keep it: drag one member and the rest follow; Smart Layout ranks its candidates with the alignment applied. Works across parents and for expanded containers. *Keep their order* (on by default, remembered) also keeps the elements in the order you selected them — left to right, top to bottom: dragging one past its neighbour pushes the neighbour ahead, and Smart Layout never swaps them. The canvas now remembers the order elements were selected in. *Keep in a grid* (three or more elements) keeps them in a grid filled row by row in selection order — every row stays an ordered row and every column an ordered column — and lays them out in even cells; the column count (about square by default) is set in the menu and changed later with − / + on the canvas guide or in the view's properties. With a single container selected the menu reads *Align children…* and does the same for its children in the view, taking them in the order they stand (left to right, top to bottom, or row by row for a grid); for a collapsed container the rule is saved at once and its children line up when it is expanded. Dashed guides show the alignments on the canvas (arrowheads when ordered), with buttons to switch order-keeping and to remove the alignment when a member is selected; a view's alignments are listed in its properties. Saved in the document (`views.json`, `_layout.json` for All elements). The AI tools and the MCP server get `align_nodes` (with `keepOrder`), `grid_nodes` and `remove_alignment`
- Wiki glossary: a *Glossary* page at the end of the list of pages says what each kind of element and relation the view uses is, with the fields of a type, how a relation reads from either end and what it joins; under the heading that first names a type on a page a line says what the type is, and the type under a title and the verb of a sentence about relations say it on hover
- Metamodel: element types and relation types have a *Description* (what the type is, in a sentence or two), and relation types say how they read in a sentence — *Reads as* from the source when the label is a name rather than a verb ("Uses" for Interacts) and *Reads back as* from the target ("Constrained by" for Constrains). All built-in types have them; they are edited in the metamodel editor and through the MCP tools `upsert_node_type` / `upsert_relation_type` (`description`, `forwardLabel`, `inverseLabel`). The canvas shows none of them
- Wiki: one menu for an element — *[edit]* beside its title or chapter heading, and a right click on the element in a page or in the list of pages — with *Add child* (types grouped as in the palette), *Add relationship*, *Edit facts* and *Delete*; a relationship is added in two steps that read as the sentence the page then writes (how it reads from this element, for instance "Used by…", then the element it names), so incoming relations and the relation type can be chosen; a link in a sentence about relations has *Edit relationship*, *Remove relationship* and *Open*
- Wiki: the search above the list of pages also looks through what the pages say (description, the sentence of a requirement, text fields), shows the words around a match under the page's name, marks a match in a name, and opens the first page found on Enter

### Changed
- Wiki pages read as encyclopedia articles instead of forms: a serif title with the element's type and place under it, the short facts in a box beside the lead, a *Contents* box, long fields as sections, and relations as sentences read from the page's element ("Uses Event Bus (publishes payment.completed, Kafka) and Transactions DB. Used by API Gateway."); a sentence that would name more than six elements says how many there are and shows them on request
- Wiki: the elements under a page are grouped by type under a heading with their count ("Requirements (46)") at every level, in both page modes; a few are a paragraph each (name and the start of the description), more are a run of links. A group is shown by its name and description, never as "Group"
- Wiki: *Multi page* writes the children as chapters of one article — a heading, the type and short facts in one line, the text, long fields as paragraphs that open with their name — instead of embedding each child's whole page with its own buttons
- Wiki: the list of pages is a tree laid out as the articles are (groups first, then a row for each type with its count, at every level), closed until a branch is opened or the page being read is inside it; *Overview* is fixed at its top and *Glossary* at its bottom. The fixed sections "C4 / Governance / Other" are gone
- A requirement whose action is a whole clause with its own subject ("The wiki view shall show…") reads by that subject: the element that satisfies it is no longer put in front of it, which said "shall" twice, and the sentence ends with one full stop
- Dragging is calm: a drag moves only the dragged element — with the other selected elements and the members of its rows and columns, which follow it across the line (an ordered line pushes the next member ahead) — and the live physics no longer runs while you drag. On the drop, the elements it now covers are pushed clear, each whole and in one direction, and a container that grew pushes its neighbours the same way; nothing else moves. On this repository's own architecture model (499 elements), dragging an element used to move 44 of the 45 elements shown, the farthest by 27 000 px, and they kept moving for 4 s after the drop; now 5 move, by at most 80 px (the frames of the containers around it growing), and nothing moves after the drop. Dropped elements are pinned (a `pin` layout constraint per canvas, saved with the alignments): the live physics leaves them where they are; select one to unpin it from the pin at its corner, or unpin a view's pins in its properties. Smart Layout (and the tree layout) rearranges the whole canvas and unpins it, in the same undo step; the MCP server's `smart_layout` does the same. Hold ⌘/Ctrl when starting a drag for the old behaviour, the physics making room around it. Dragging a selection of several elements now moves them all (the physics used to put the others back)
- Expanding a large container under the live physics stays smooth (on a 150-node, 300-edge canvas: main-thread long tasks 3.6 s → 0.15 s over five seconds, frames over 50 ms 40 → 2): edges skip routing around obstacles while the layout moves and route once it comes to rest, the Relations list subscribes once instead of once per row, the closed Radical Forge dialog no longer follows every move, and the canvas no longer re-renders on every camera frame of Smart fit, a pan or a zoom
- Expand and collapse keep the container's centre: an expanded container grows around its collapsed box and a collapsed one shrinks to the centre of its box (it used to grow right and down from the top-left corner and push the diagram below it away). Under the live physics the canvas no longer draws, for a few frames, an arrangement the physics then discards (siblings pushed aside, snapping back)
- Smart fit frames an expand or collapse in the first frame that shows it and follows the live layout every frame while it moves the diagram, instead of easing towards a target refreshed every 300 ms (it trailed one to three seconds behind, and the diagram slid in from an edge)
- Opening a view, or loading a document, sets the camera at once instead of flying from the previous view's camera (each view has its own coordinates, so the diagram vanished and slid in from an edge): with Smart fit on, the view is fitted in the first frame that draws it and followed while it settles; with Smart fit off, the view's saved camera is used
- Smart fit keeps the diagram on screen: when no element is in view any more (the live layout carried the diagram off after an expand or collapse), it fits the diagram again; it waits 2 s after you pan or zoom by hand
- The expand / collapse button in a container's header is larger (28 px, bolder + / −) and reacts to clicks a little around it, so it is easy to hit on a zoomed-out canvas; a click on it also works when an edge between the container's children is drawn over it (it used to select the edge)
- The Studio app is named radical.studio (installers, window and page title); radical.tools names the family of apps
- Radical Hub uses its own emerald palette (accent, background, borders) in both themes so it reads apart from radical.tools; Studio keeps its blue
- Dark theme is a dimmed graphite instead of near-black (canvas, panels, borders, muted text), so the dark C4 palette stays visible; type icons in the node tree and filter chips are lightened in the dark theme
- Sequence view participants are drawn as their C4 shapes (person, database cylinder, queue, web app, boxes) in the canvas node colours, instead of one dark box style for every type

### Fixed
- The layout Smart Layout reports is the one that stays. On diagrams under 150 elements the live physics used to relax the whole diagram right after every layout, on opening a model and on switching views: every element moved (by up to 1 700 px on the sample model), mostly to an arrangement Smart Layout itself scores worse (the sample's All elements: 16 937 before the physics, 20 713 after), and that was what got saved. The physics now leaves a laid-out diagram alone and moves only what is added or expanded, with its surroundings, as it already did on larger diagrams. Smart Layout scores what the physics would make of its winner as one more candidate and keeps it only when it wins, in Studio and in the MCP server's `smart_layout` alike
- An element related only to open containers (an actor that uses an expanded web app, an entity next to its expanded state machine) no longer ends up far from the diagram: nothing held it, so it stayed behind while the rest of the diagram settled, and was saved there. When the physics runs, it now comes back by the container it is related to, without pushing anything else
- A reload, a view switch or a redo no longer moves a container's children down after an element was added into the container or the container was expanded: the canvas drew them about 50 px lower than the file had them
- Smart Layout run in Viewer or Presenter is no longer saved into the model: the canvas went back to the Designer layout on return, but the file kept the other one and a reload showed it
- Smart Layout no longer lands on another view when a view is opened while it is computing: it wrote the positions computed for the first canvas onto the second and saved them there. The layout is dropped with a notice instead
- Reloading the page while a view is shown no longer replaces the layout of All elements with that view's: a container could shrink to the size it has in the view and leave its children outside it
- Smart Layout gives the same layout whatever order the document keeps its elements in. A model kept in a folder was rearranged by Smart Layout after a reload although it had just reported the layout as the best, and the MCP server picked another arrangement than Studio for the same folder. Layouts of models kept in the browser or in a `.radical` file may come out differently once
- `update_relation` (MCP server and AI assistant) refuses a relation type that does not connect the two elements, as `add_relation` does; the validation lists a relation whose type does not fit its ends; an element cannot be retyped when a relation it has would not be allowed for its new type
- Dragging an element no longer changes the frames of open containers it does not touch
- A drag can be undone: Undo puts back what the drag moved or pushed and takes off the pins it set. It used to do nothing after a drag, or take back the drag together with the edit made before it
- A small diagram whose elements overlap when it is opened gets the hint to run Smart Layout, as large ones did; the physics no longer rearranges it on its own
- A link opened right after another one (a deep link to a wiki page followed by one to another page, or to another perspective) is no longer lost now and then: the address the link asked for is applied even when Studio had just written its own state back to the address bar
- Viewer and Presenter fit a view when it opens: a view with a saved camera stayed under the previous view's camera, off centre or partly off screen (the saved camera reached the canvas as a value it could no longer read, so the fit never started)
- Wiki: an element's description keeps its paragraphs and line breaks instead of running them together
- Wiki: children linked by a relation rather than contained (requirements deriving from a need or a parent requirement) are listed on the page of what they derive from, under their type, instead of being left out
- Table view: a requirement deriving from a need stays in the Requirements tree instead of dropping out of it with its sub-requirements
- Production desktop build showed a blank window: the CSP header handler dropped every other response header (including `Content-Type`), so the renderer's module scripts were refused
- Hub concept files' `views` were ignored by the viewer and on import
- Importing from the Hub no longer stacks one "Imported …" notification per concept over the template-parameter form
- Markdown-folder models: renaming or moving an element whose description was never opened lost that description on the next save
- Markdown-folder models: saving deleted files Studio did not write — any top-level `.json` (e.g. `package.json`) and any file under `nodes/`, such as a hand-written `README.md`; "Save as folder…" into a folder that holds other files but no model now asks first
- Markdown-folder models: two saves overlapping (a slow disk, a large model) could delete an element's file altogether
- Switching documents while a slow one was still loading could load it into — and autosave it over — the document switched to; an edit made just before a switch now lands in the document being left
- Markdown-folder saves write only the files that changed, and only the model's own files are read (a folder inside a repository no longer walks `node_modules`)
- Live physics: a dragged element was simulated 40 px right of and below where it is drawn, so neighbours made room around the wrong spot
- Live physics: expanding a container in a grid of containers that sits in another alignment (a column of groups holding a grid of groups) could leave the canvas shaking for good, the groups flipping thousands of pixels between two places: a line inside a container now moves with it, and on a large diagram the elements aligned with a container that grows are no longer held in place. A run with an alignment of containers stops after 4 s if it has not come to rest by then
- Presentation slides without a captured canvas (the sample model's walkthrough, imported slides) lay nodes out with their view's saved positions instead of whatever layout was on screen, so they no longer need a Smart Layout to look right; a slide after a milestone slide shows the live model again instead of the milestone's subset
