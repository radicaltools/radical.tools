Element types

The C4 metamodel has the first eight. The Radical metamodel has all of them, lets a Software System sit inside a Domain, and adds the rest. Types of the Radical layers sit at the root, in a system, in a domain or in a group unless the table says otherwise. Every type has a name, a description and a parent.

Summary templates

Summary in tables on a node type is a template of tokens. A part in [ ] is left out when a token in it is empty; the template's own text may use Markdown. Left empty, the built-in template applies, else the description's first sentence.

TokenWhat it gives
{key}A property; also {label}, {description}, {technology}, {type}
{ears}A requirement's whole EARS sentence
{obligation} · {condition}Who shall do what; the when / while / if / where it holds under
{transitions}Where a state machine goes from a state or on an event
{out:type} · {in:type}The elements linked by relations of a type, out or in
{key.sentence} · {key.phrase}The first sentence; the first phrase
{key.cap} · {key.bold}Capitalised; bold
{a|b}The first of them that has a value

Built-in templates: [{obligation.bold}][ — {condition}] for a requirement, [{then.phrase.cap.bold}][ — when {when}] for a scenario, [{status.cap.bold}: ]{decision.sentence} for an ADR.

Rules & checks

The metamodel is enforced in three rings: what Studio refuses at once, what the Validation list and get_issues list as issues, and what only radical check and the Inspector report.

Refused at once

  • Placing or moving an element where its type may not sit, or at the root when it needs a parent.
  • One more element of a type that has reached its maximum.
  • A relation type that does not join its two ends, or a pair no relation type allows.
  • Changing an element's type when one of its relations would then not be allowed.
  • Moving a group where something it holds would have no place; moving an element into itself.
  • A transition out of a final state, or into an initial pseudostate.

The same refusals reach the AI assistant, Radical Forge and the MCP server as messages they can act on.

Listed as issues

AreaIssues
Any metamodelAn unknown type, a misplaced element, a relation to an element that is gone or between types no relation joins, a reference that points at nothing or the wrong type, an empty required field, too few or too many elements of a type; in custom metamodels, two properties of a type with one key.
Domain modelAn aggregate root that is part of something; a part of something that is not a root; an entity that belongs to no aggregate or to two.
State machinesA machine with no entity, or an entity with two machines; no initial pseudostate, or more than one; an initial pseudostate without exactly one outgoing transition; a parallel state with fewer than two regions; a final state with children or outgoing transitions; a transition that leaves its machine; two unguarded transitions from one state on one event; a state the initial state cannot reach.

Checked by radical check

Warnings unless check.json says otherwise; radical check --list-rules lists them with their ids.

radical check

Checks a Markdown folder: the folder's files, the metamodel rules and the completeness rules above. It never changes the model. Run the published package, or build it from a clone (see Install & build).

npx -y @radicaltools/cli check path/to/my-model --report reports
OptionWhat it does
[folder]The model folder. Default: the working directory.
--config <file>Rule settings. Default: check.json in the model folder.
--format text|json|githubPlain text (default), JSON, or GitHub Actions annotations.
--report <path>A test report (Vitest or Jest JSON, Playwright JSON, JUnit XML) or a directory of them; repeat for more. The test cases read are kept in .radical/test-results.json for the Inspector. A report with no test case stops the check with status 2.
--from-ciReads the test reports of CI instead of --report: those of the latest completed GitHub Actions runs of the nearest commit in HEAD's history that CI tested (a commit merged from a pull request stands for the pull request's head), downloaded with the GitHub CLI (gh, signed in). The artifacts read are check.json's "ci": { "artifacts": […] }, or every artifact of the run. They are kept in .radical/test-results.json with the commit and runs they come from, unless the results there were read with --report at that commit or a later one.
--quietPrints nothing.
--detachStarts the same check in the background and returns at once; the git hooks run --from-ci --quiet --detach.
--metrics <path>A radical-metrics/1 file (radical sense --out) or a directory of them; repeat for more. Added to .radical/measurements.json, which the check reads without the option too. The reviews in the model folder's reviews.json are read as measurements as well.
--baseline <path>Earlier radical-metrics/1 files, or a directory of them, that a condition against a baseline compares with (the median of the latest seven of its metric). Read only; never kept beside the model.
--trigger <event>The event the check runs on (pull-request in the gate): a metric condition of a fitness function that runs on another event, or continually, is not reported when nothing measured it.
--evidence <file>With --report or measurements: writes what they say about each scenario, fitness function, requirement and ADR as JSON.

--list-rulesLists the rules, their default severity, and the metrics goals can set.
radical --versionPrints the version, with the commit when the build is not a release (0.3.0+1a2b3c4).

Exit status: 0 no errors (warnings allowed), 1 errors, 2 the check could not run.

check.json

rules sets a rule by its id, or one kind of metamodel issue by metamodel/<code>, to error, warning or off. With max, up to that many findings pass as warnings and one more fails the check, so an existing model can adopt a rule before every gap is closed. goals sets the least share of a metric, in percent; a metric below its goal is goal-unmet, an error unless set otherwise.

{
  "rules": {
    "adr-incomplete": "off",
    "requirement-without-scenario": { "severity": "error", "max": 104 }
  },
  "goals": {
    "requirements-with-scenario": { "min": 85 },
    "requirements-verified": { "min": 80 }
  }
}

The Inspector's Settings tab edits the same file.

Metrics and sensors

A scenario or fitness function says what checks it in Metrics, one condition per line; blank lines and lines starting with # are left out. Sensors (radical sense) only measure; radical check and the Inspector compare each value with its condition.

FieldWhat it holds
Metricstest(<file> › <title>) passed: a test that has to pass, named as Vitest and Playwright print it (a file or directory alone names every test in it). <metric>{<label>=<value>, …} <op> <number> [unit]: a measured value, with < <= > >= == !=; it is judged by the latest measurement of the metric whose labels include the condition's. <metric>{…} <op> baseline [+|- <number> %|unit]: the same against earlier measurements given with radical check --baseline, the median of the latest seven of the metric and labels, with the margin (<= baseline + 20%, <= baseline + 500 ms); not evaluated, a warning, while there are none. review(<name>) passed: the latest review of that name radical sense review recorded passed.
Combineall (default): every condition passes. any: one does. at least N.
Max ageHow old a measurement may be (7d, 12h, 30min, 2w). An older one makes the condition stale, which never passes.

Units of one kind convert: ns us ms s min h d, and B KB MB GB TB KiB MiB GiB TiB; other units must match. A condition or a measurement without a unit compares the numbers as they are.

radical sense

A fitness function is classified as Building Evolutionary Architectures classifies it. Its result is read from its metrics: static for fixed limits, dynamic for one against a baseline.

PropertyValues
CharacteristicWhat it protects, a quality of ISO/IEC 25010:2023: functional-suitability performance-efficiency compatibility interaction-capability reliability security maintainability flexibility safety other.
Scopeatomic: one part in one context (a unit test, a linter rule). holistic: several parts together (latency under load, an end-to-end run).
Cadencetriggered: on an event, set in Runs on: pull-request nightly weekly release deploy. continual: measured all the time (monitoring in production). temporal: falls due after a time, set in Every (90d).
Invocationautomated: a sensor measures it. manual: a person reviews it and records the result with radical sense review.
MeasureAutomated only: what to run, one measurement a line, a sensor and its arguments as on the command line (playwright tests/load.spec.ts --cwd apps/e2e --label env=staging). Empty for tests the gate already runs.

Models saved with a category are read classified: holistic gives scope holistic, structural the characteristic maintainability, and one checked by tests alone is triggered on pull-request and automated. The rest stays empty for fitness-fn-unclassified to ask for.

Changes on branch

radical diff <folder> prints the elements and relations added, removed and changed since the branch left main, with old and new values. Views and layout are left out. --since <ref> compares with another commit, tag or branch.

The base is the model at git merge-base HEAD origin/main, saved to .radical/base.json. Studio reads the file every few seconds and compares the model with it as you edit. Only the command line and the MCP server save it:

Saves the baseThrough
A checkout or switch of branchthe post-checkout hook
A commit, amended toothe post-commit hook
A pull that merges or fast-forwards, a mergethe post-merge hook
A rebase, git pull --rebase, an amendthe post-rewrite hook
An agent's get_changes without sincethe MCP server
By handradical diff <folder> --save-base
  • radical hooks install <folder> adds the four hooks. A fetch, a reset or a stash runs no hook.
  • After saving the base, each hook starts radical check <folder> --from-ci --quiet in the background, so the Inspector has the test results of CI for the commit checked out. Without the GitHub CLI it does nothing.
  • Committing keeps the base, so the list holds the whole branch's work. After the pull request is merged, switch to main and pull: the list empties.
  • To see only what is not committed yet: radical diff <folder> --save-base --since HEAD.
  • A folder outside git has no base from git. A Radical Forge run on such a folder saves the model before it as the base; the next run replaces it.
  • A base older than a day is marked in the Inspector's This branch tab with the commands that save it again.

radical setup

radical setup [folder] connects coding agents to a model folder in five steps: Node, the folder (a missing or empty one becomes a new model; one with other files and no radical.md is refused), the agents, the git hooks (radical hooks install) and the checks of --status. In a terminal it asks each question with its default; without one, or with --yes, it takes the options and the defaults.

npx @radicaltools/cli setup
npx @radicaltools/cli setup architecture --client claude-code --client codex --yes

Outside a git repository, setup asks in a terminal whether to start one in the working directory before it adds the hooks.

The launcher

radical.sh (macOS, Linux) and radical.cmd (Windows), at https://radical.tools/radical.sh and /radical.cmd, run the CLI where Node.js is missing: sh radical.sh setup, radical.cmd setup, or any other command. They take Node.js 20.11 or later with npx beside it from the PATH, else from ~/.radical/node; with neither they ask, or take --yes, and download the latest Node.js 24 for the platform from nodejs.org, checked against its SHA-256 sum. radical.sh mcp --folder … runs the MCP server and never asks.

Setup run through a launcher pins its version line (default_version, DEFAULT_VERSION in radical.cmd) to the CLI's version, makes radical.sh executable, and writes each agent's entry as sh radical.sh mcp --folder … (radical.cmd mcp on Windows), with the launcher's path from the top of the repository in a project file and its absolute path in a user file. The git hooks run sh radical.sh diff. Commit the launcher with the model, and the project keeps one version for the CLI and every agent.

MCP server

Runs locally over stdio, bound to one Markdown folder. Node.js 20.11 or newer.

npx -y @radicaltools/mcp --folder /absolute/path/to/my-model   # waits for MCP messages on stdin
radical-mcp --version

radical setup writes the entry for you. By hand, for Claude Desktop: add it under mcpServers in ~/Library/Application Support/Claude/claude_desktop_config.json (Windows: %APPDATA%\Claude\claude_desktop_config.json) and restart the app. Give the full path to npx and put node's directory on the server's PATH, because the app does not see your shell's.

{
  "mcpServers": {
    "radical": {
      "command": "/opt/homebrew/bin/npx",
      "args": ["-y", "@radicaltools/mcp@0.2.0", "--folder", "/path/to/my-model"],
      "env": { "PATH": "/opt/homebrew/bin:/usr/local/bin:/usr/bin:/bin" }
    }
  }
}
  • --metamodel radical|c4 picks the metamodel of a new folder (default radical). A folder with other files and no radical.md is refused.
  • Studio warns once when the server's version differs from its own; update the older one.
  • Not supported: single .radical files, driving Studio's canvas, loading a milestone over the model, clearing the model, remote HTTP connections.

Radical Forgeforge_start · forge_clarify → forge_generate (with forge_propose_refinement → forge_answer_refinement when a stage finds what an earlier one lacks) → forge_complete_stage → forge_arrange, per stage · forge_wireframe · forge_import_hub_concept · forge_finish
  • Writes go through the same schemas and metamodel rules as Studio. An invalid parent, type or pair is refused with a message; warnings come back with the result. A tool reports success only after the files are written.
  • A reference such as a transition's event takes an element's id, or a tempId from the same session.
  • Changing a built-in metamodel saves a -custom copy and re-announces the tools with the new types.
  • The server keeps a Forge run in .radical/forge-run.json, and refuses direct writes to earlier stages while a proposal waits. In Claude Code, /mcp__radical-folder__forge starts a run.

Editing beside an agent

Studio and an agent can work on one folder at the same time; neither overwrites the other.

  • Turns. After each write the server marks the folder as being written (.radical/agent-activity.json) for 15 seconds. Studio holds its saves meanwhile, keeps your edits on top of the agent's, and saves them when the agent pauses. A reload keeps them in the browser until the folder has them.
  • Merges. Changes are merged element by element and field by field. Where both sides changed one value, what is in the folder is kept and a notice names it. What one side deleted stays deleted, with what the other side built on it, and the notice names that too. Two agents on one folder take turns through .radical/write.lock.
  • What stays. An agent's change leaves your view, selection, camera and milestone as they were. While you drag, the change waits for the drop; while a presentation plays, until it stops.
  • Undo. Your Undo and Redo take back your own steps only. Where a step meets a value or an element the agent changed since, the agent's version stays and a notice names it.
  • Files. A file that does not read as a model (conflict markers, a trailing comma) is never merged over: Studio says which file and saves nothing until it reads again.

File formats

.radical (JSON)

One file: nodes, relations, sequences, views (positions, camera and layout constraints per view), defaultEdgeStyle, snapshots (milestones), presentations, the metamodel and Hub template records. Older .c4.json files open unchanged.

Markdown folder

my-model/
├─ radical.md                 # manifest
├─ nodes/
│  ├─ retail-customer.md       # one element = one file
│  └─ core-banking-platform/   # an element with children becomes a directory
│     ├─ _index.md             # the element itself
│     └─ payments-service/
│        ├─ _index.md
│        └─ fx-engine.md
├─ relations.json
├─ views.json · sequences.json · snapshots.json · presentations.json
├─ metamodel.json · hubTemplates.json
├─ _layout.json               # positions, camera, line style — the only noisy file
├─ check.json                 # optional: rule settings for radical check and the Inspector
├─ reviews.json               # optional: reviews of manual fitness functions, from radical sense review
└─ .radical/                  # editor state, kept out of git by its own .gitignore
   ├─ selection.json          # what is selected in Studio, for the MCP server
   ├─ base.json               # the model where the branch left main
   ├─ forge-run.json          # where an agent's Forge run stands
   ├─ agent-activity.json     # an agent is writing
   ├─ test-results.json       # test cases from the last radical check --report or --from-ci
   ├─ measurements.json       # the latest value of each metric, from radical sense and --metrics
   └─ cache/                  # the folder in a few files, for opening it fast; safe to delete
  • Each .md has YAML front-matter (id, type, label, then the properties, sorted) and the description as body. Hierarchy is the directory tree.
  • Output is deterministic: sorted keys, stable file names. A file is named after its element and keeps its name until the element is renamed or moved; two of one name are orders-db.md and orders-db-2.md.
  • Edit the files by hand or through the MCP server; Studio picks them up and merges what you have not saved yet. A file with a byte-order mark reads as any other.
  • The files are the model; .radical/cache/ only repeats them: model.json each file with its modification time and size, changes.json the files saved or read since, views.json the elements each view shows for the model's structure. Studio opens a folder from it at once and lists the files right after, loading afresh what changed while it was closed; the MCP server takes from it each file that has not changed and reads only the others, and the CLI reads it when it is there. Deleting it is always safe.

Install & build

VS Code extension

The Radical.Tools extension opens .radical files in a Radical.Tools editor inside VS Code, keeps the file and the editor in sync both ways, and follows the editor's theme. Commands: Radical.Tools: Open current file, Open app, Stop and Show output log. Markdown folders open in Studio, not in VS Code.

Desktop app and a clone

# Node.js 20.11 or newer
git clone https://github.com/radicaltools/radical.tools.git
cd radical.tools
npm install
npm run dev                          # Electron, hot reload
npm run build && npm start           # desktop app
npm run dist                         # packaged desktop app
npm run dev:web                      # browser build of Studio
npm run dev:hub                      # Concern Hub
npm run build -w @radicaltools/mcp   # MCP server:  node apps/mcp/dist/index.js --folder …
npm run build -w @radicaltools/cli   # radical:     node apps/cli/dist/index.js check …
npm test                             # unit tests of every workspace
npm run e2e                          # browser tests
npm run check:architecture           # radical check on this repository's own model

The desktop app adds native file dialogs, Markdown folders without browser permissions and --file watching (or the RADICAL_FILE variable). Everything else is identical to the browser build. Studio, the desktop app, the VS Code extension, the MCP server and the command line share one version; a build that is not a release shows the commit after it.
