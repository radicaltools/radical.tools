Radical.Tools, explained

One model of your architecture; every diagram, table and wiki page derived from it. This guide walks through modelling, the six view kinds, milestones, presentations, the Inspector and radical check, files, the metamodel editor, the Concept Hub, the AI assistant, Radical Forge and the MCP server that lets coding agents edit the model.

Open Studio Start with the basics ↓

Screenshots follow the theme you pick in the top bar — toggle it to see the other look.

Getting started

Radical.Tools runs in the browser at studio.radical.tools — no account, nothing uploaded — or as a desktop app (see local install). On first launch you land on the Welcome screen. It asks one thing first — a new model or an existing one — and the details come in the next step:

  • New model — pick the metamodel (Radical is preselected, plain C4 is the other choice, and the metamodel editor changes it later) and where to keep the model: in this browser, in a file (one .radical file, every change saved to it) or in a folder (Markdown files, see Models & files). The choice of storage is remembered. Once an AI provider is set up, Create with Radical Forge starts the model from a description instead.
  • Open — a recent model, the ones kept in this browser, a file, a folder, a Structurizr DSL workspace or the sample.
  • Try the sample model — the Fintech Banking Platform used throughout this guide: 78 elements — architecture, ADRs and fitness functions, the needs behind it (a regulation, a product brief and a client's feedback), the EARS requirements derived from them, Gherkin scenarios, 13 UI mockups with wireframes in three screen flows and the process Send a payment — 17 views of every kind (the Requirements Register with a filter, Processes as a Warnier view), four sequences, four milestones and a ready-made presentation. A first visit offers it right under the two choices.
  • Recent — your last three models, one click away; Open lists more.
Tip: a deep link such as studio.radical.tools/#/m/designer/v/canvas skips the Welcome screen and opens the last active model directly. See Deep links.

The workspace

Toolbar

  • Radical menu (logo, top-left) — Manage models…, Import from Hub…, Metamodel editor…, light/dark mode, Smart fit, Lines in this model (curved or orthogonal), the Connect key, Wizard on create, AI providers…, Radical Forge… and export (Export as PNG…, Export as SVG…, Copy to clipboard) of the view shown, whatever its kind. Last, About Radical Studio shows which build you run: the version, the commit and day it was built from, whether it runs in the browser, the desktop app or VS Code, and the version of the model folder format it reads and writes. Copy puts all of it on the clipboard for a bug report, and What's new opens the changelog. radical.tools has one version for Studio, the desktop app, the VS Code extension, the MCP server and the command line; a build that is not a release shows the commit after its version (0.3.0+1a2b3c4), as Studio on the web does between releases.
  • Undo / Redo — they work in Designer; the Inspector has none.
  • Quick Search (⌘/Ctrl+P), in the middle of the top bar on every view — find any element, relation or view (a pick selects it where you are when the view shows it, else in a view that does); ✨ turns it into the AI prompt, and the Forge button beside it opens Radical Forge.
  • Perspective switch — Designer edits, Viewer explores read-only, Presenter builds and plays slide decks, and Inspector shows what radical check says about the model (see Inspector); its button counts the errors and warnings, and stays greyed out until a check report is there. Studio opens a model in Viewer, so nothing changes until you choose Designer; a link opens the perspective it names, and a model you have just created (empty, from Radical Forge, the sample or a Structurizr import) opens in Designer, as does a Forge run started from Viewer.

Left panel

Three sections, Views, Milestones and Sequences, each with its icon, colour and count. Views starts with All elements, the whole model as a table, then one card per view with how many elements it shows and its kind, each kind in its own colour, in folders if you made any; + New view is at the bottom. A view's properties (the button on its card), a folder's and a milestone's slide into the panel; ◀ Back returns. Click a section's header to open it, which folds the others, or to fold it when it is open. The open section takes the panel's free height; a folded one says in a line what it holds (the open view, the latest milestone, the sequences). Drag the panel's inner edge to widen it; double-click it for the default width.

Canvas

In Designer the Elements palette stands down the left side of the canvas, always there: one element type to a row, its icon and its name, grouped under C4, Domain, Governance, Requirements, States, UX and Other, with types you add in the metamodel editor last under Custom — drag a type onto the canvas; its tooltip describes it. It lies over the canvas, which keeps its size, and Fit All and a click on an element frame what they show beside it. A canvas lower than the palette scrolls it. The other view kinds, the table among them, and Viewer and Presenter have none.

At the bottom of the canvas, in the middle, are Fit All, zoom out / in and Smart Layout (or Tree Layout when the view asks for it); after a Smart Layout run, ⓘ beside it shows why that layout won. The controls are there in Viewer and Presenter too. The chip in the top-left corner names the active view (Structure: System Context) or, when time-travelling, the active milestone. Nodes can be dragged, nested, collapsed and connected here; the other view kinds replace the canvas, its palette and its controls with their own surface. Zoomed out below about 0.3, where a card's text would be too small to read, each element is drawn as a block of its type's colour with its name in large type, and a container with elements in it as a dashed frame. Containers still open and fold from the button in the corner. Zooming in brings the full cards back, and an exported picture always shows them. A large model opens faster this way, and relation labels hide at the same zoom. A card keeps its name and technology whole and shows as many whole lines of its description as fit, the last cut with an ellipsis. A relation's label shows its name on at most two lines and its technology on one, smaller than the elements' names, cut with an ellipsis; hover or select the relation, or an element at one of its ends, to read the whole of it.

What a view shows, and in what order, is its filter, set in the view's properties (see Views).

Properties card

Selecting one element, a relation or a sequence slides its properties card over the right side of the view; the view keeps its size, so nothing under it moves. The card goes when nothing is selected, and while several elements are selected (the selection bar acts on them). ✕ hides it until you select something else, or nothing: the element picked again after that has its card back. Its head has the type, the name, which you edit in place, and where the element sits (the elements it is in, or a relation's two ends), each a link that selects it; Wizard for a type that has one, and ⋯ to delete it. Under it each attribute is a row, its name on the left and its value on the right: the value reads as text, outlines under the pointer and is edited where it is. An empty one shows —, and a required one with no value has a red dot. Long fields (the description, an ADR's context…) are sections under the rows, shown as Markdown; a click edits one, and Esc or a click elsewhere shows it again. Drag the card's left edge to widen it; double-click the edge for the default width. A click on an element frames it in the part of the canvas the card leaves free. Viewer shows the same card read-only; Presenter has the slide dock instead.

Models & files

A model is a document, kept in one of three places:

  • This browser — browser storage. Nothing to pick; export a file to share it.
  • A file — a single .radical JSON file on disk. In the desktop app and in Chromium browsers (File System Access API) every change is saved back to the file; other browsers can only import and download one.
  • A folder — a Markdown folder: one .md per element with YAML front-matter, nested directories for containment, JSON sidecars for layout, views and relations. Diff-friendly and readable without the app. Works in the desktop app and in Chromium browsers.

Radical menu → Manage models… lists every model on one list, the last used first, with a search box and a filter by place (All, Browser, Files, Folders). Click a row to switch to it. Its ⋯ menu renames it, moves the open model to a file or a folder, and deletes it (a file or folder is only removed from the list; it stays on disk). + New model and Open… are the same steps as on the Welcome screen; Open… → Structurizr DSL… converts a .dsl workspace into a new model.

Every change is autosaved (a few hundred milliseconds after you stop editing) to wherever the document lives. In the browser, a file or folder needs access granted again after a reload: click it on the Welcome screen, or Reconnect… on its row.

Desktop: launch with radical --file path/to/model.radical (or the RADICAL_FILE environment variable) and the app reloads whenever that file changes on disk — handy next to a text editor or a Git checkout.

Elements

  1. Drag from the palette onto the canvas. Drop it on top of a container-type node (a system, domain, group…) to make it a child; a container that cannot hold it refuses the drop with a message.
  2. Double-click an empty spot on the canvas to create a Software System right there.
  3. Add it from a table with a + row (see Table views), or write it on a wiki page (see Wiki views).
  4. Import from the Hub — see Concept Hub; or let the AI assistant, Radical Forge or an agent over MCP add it.

The metamodel decides what is allowed. Dropping a Component directly on the canvas, a Person inside a System, or a fourth element of a type limited to three is refused with a message rather than silently drawn — so the model stays valid.

Containment

Change a parent any time with the Parent field in properties, or with Move to… in the selection bar; dragging an element moves it, not into another container. Collapse a container with the − button in its header (+ opens it again); children fold away and relations re-attach to the parent. In a named view, collapsing is per view — the same system can be open in one view and folded in another. A Group has no meaning of its own: it can sit at the root, in another group or inside a system, where it gathers some of the system's parts (shared libraries, say) the way groups do in Structurizr. It holds only what its place allows: a group at the root takes what could be at the root (people, systems, needs, requirements, decisions), a group inside a system takes the parts of a system. A component does not go into a group at the root.

Visibility per view

Elements exist once in the model and appear in as many views as you like. An element you create while a view is open is added to that view. Hide from view in the selection bar takes elements out of it. The view's filter decides what it shows, and Show every element there makes it show the whole model again. A view that lists no elements and shows what its filter gives, as a view per element does, has no Hide from view: what it leaves out is set in its filter, so whatever is added to the model later still shows there. Ancestors of a shown element are included automatically.

Relations

  1. Hold the connect key — Alt by default; change it under Radical menu → Connect key.
  2. Press on the source node, drag to the target, release. A preview line follows the pointer; Esc cancels.

The relation type is inferred from the metamodel (e.g. Interacts between C4 elements, Constrains from an ADR). Pairs the metamodel does not allow are refused; while you drag, a banner says which element you are connecting from. Select an edge to edit its label, its type (offered when more than one fits) and its type's fields — technology for Interacts, the trigger of a Navigates to — in the properties card. The edge action bar at the bottom of the canvas offers Change source…, Change destination…, Hide from view and Delete.

Properties & governance

Every element has a label, description and parent; containers, components, databases, web apps and queues add technology, and every C4 element but a group has an external flag. Everything else is defined by the metamodel: text, long text, number, boolean and enum fields — the description and every long text field are Markdown, rendered in the wiki and the table's summary and shown without their marks on the canvas — and references to other elements, optionally shown only when another field has a given value. A reference points at one element of a given type, or several (a transition's Event, the events it Raises): you pick them from a list, the model keeps their ids, and renaming the element never breaks the link. A reference to an element that was deleted is marked ⚠ and listed under Validation in the Metamodel editor.

Needs

A Need (palette group Requirements) keeps raw input exactly as it arrived: a brief, a user story, meeting notes, a quoted regulation or a list of raw requirements. The text is free-form and is the element's description, so in a Markdown folder it is simply the body of its file. Kind says what it is and Source who or where it came from. There is no status: a need in the model is an accepted one.

Needs are where EARS requirements come from. A requirement links to the need it was written from with Derives from (the same relation that links a sub-requirement to its parent), so every requirement traces back to the words someone actually wrote. Needs nest the same way: a need that is part of a broader one (one stakeholder's notes within a discovery, one chapter of a regulation) links to it with Derives from, which its wizard asks as Part of. A need's Wiki page lists its sub-needs and the requirements derived from it as its children, and Add child in its menu creates either, already linked. A Table whose filter starts with needs and goes on along Refined into shows them as a tree. Nothing satisfies or verifies a need directly; that is what its requirements are for.

Requirements (EARS)

A Requirement is edited as a sentence. Pick the EARS pattern — ubiquitous, event-driven (When …), state-driven (While …), unwanted behaviour (If …, then …), optional (Where …) or complex — and click the highlighted slots to fill trigger, condition and action. Or just type the whole thing into the quick-entry box:

When the user clicks save, the system shall persist the document

…and it is parsed into type, trigger and action. The subject (“the system”) is the element that satisfies the requirement, when there is one. A Rationale field says why it is needed.

ADRs and fitness functions

ADRs carry status (proposed → accepted → deprecated / superseded), date, context, decision, consequences and alternatives. Fitness functions carry a category (structural, operational, process or holistic), a threshold or success criteria, and their Tests, one file › title per line, which radical check looks up in the test reports. An ADR constrains the elements it governs and supersedes the decision it replaces; a fitness function implements (checks) the ADRs it verifies and constrains the elements it guards; a requirement traces to the ADRs and fitness functions that follow from it. They show up in the Table, Matrix and Wiki views like anything else.

Wizards

Creating an ADR, fitness function, need, requirement, scenario or mockup — dropped on the canvas, added with a table's + row, or added from a wiki page — opens a wizard that walks through its fields one step at a time, with a prompt for each, and ends with the relations that give it meaning (which elements an ADR constrains, which earlier ADR it supersedes…). The element is only created when you press Create (⌘/Ctrl+Enter from any step); Esc discards it. Wizard in the head of the properties card reopens it for an existing element, and Wizard on create in the Radical menu turns the automatic wizard off. Wizards are part of the metamodel (wizard on a node type), so custom metamodels can define their own.

Mockups & screen flows

A Mockup (palette group UX) is one screen of the product. Beside label and description it has a Screen / route and an optional Design link to an external design (Figma, Penpot, …). Link it to the rest of the model with three relations:

  • Illustrates — mockup → the requirements and scenarios the screen shows.
  • Presented by — mockup → the web app, container, component or system that renders it.
  • Navigates to — mockup → mockup, labelled with the triggering action (Pay, Add to cart). Chains of these are screen flows.

Wireframes

The Wireframe section of a mockup's properties (and of its Wiki page) shows a low-fi wireframe. With AI enabled, Generate wireframe drafts one from the model around the screen: its description and route, the EARS requirements and Gherkin scenarios it illustrates, the container that presents it and the screens it navigates to. Regenerate and Remove do what they say; Open design follows the design link. Wireframes appear as thumbnails on the canvas and on Wiki overview cards.

A wireframe is plain SVG stored on the element. Scripts, event handlers and external references are stripped, and it is only ever displayed as an image, so it can never run code or load anything.

Screen flows

Group the mockups of one actor's journey in a Group (“Shopper journey”) and link the steps with Navigates to, including branches and returns (Payment → Payment declined → try again). Record the steps as a sequence to replay the flow screen by screen in a Flow view or in Presenter.

Domain model

The Radical metamodel can hold the domain model the requirements talk about, in their own words (palette group Domain):

  • Domain — a bounded context or subdomain, a part of the business with its own language and rules. Kind says whether it is core (what sets the system apart), supporting or generic, and Vision what it is for. Domains nest for subdomains.
  • Entity — a thing with an identity inside a domain: a reservation, a customer, a product. An aggregate root is changed as a whole and keeps its own rules (solid border); an entity is a part that only lives inside one (dashed border). Plain values such as an address or an amount are not entities; describe them on the entity that holds them.

Relate them with:

  • Part of — entity → its aggregate root (an order line → the order). The Table and Wiki views list an aggregate's parts under its root.
  • References — entity → entity in another aggregate (a reservation is for a customer), with a Cardinality of one or many. Aggregates refer to each other only this way, never as parts.
  • Depends on and Partnership (with its pattern: customer-supplier, anti-corruption layer, …) — domain → domain: the context map.
  • Realises — the system or container that serves a domain, or the element that owns an entity's data → it. An entity Satisfies the requirements that are about it, and a state machine is the Lifecycle of an entity.

The Validation list in the Metamodel editor warns about an entity that is neither a root nor part of an aggregate, a part of two aggregates, a part of something that is not a root, and an aggregate root inside another.

State machines

A State machine (palette group States, in the Radical metamodel) models the lifecycle of one Entity — a domain object such as a reservation, an order or a payment (palette group Domain; its Kind says whether it is an aggregate root) — as an event-driven, hierarchical statechart with the semantics of SCXML and XState. It is a frame on the canvas, named after its entity; drop its parts into it.

  • State — a rounded box with optional entry, exit and do actions, drawn under its name (entry / start payment timer). Drop states into a state to make it compound: being in a child state means being in its parent too, and a transition that leaves the parent leaves any child (one Cancel for all of them). Set Kind to parallel to make its child states regions that are active at the same time, drawn with dashed borders (packing and invoicing an order), or to final to end the machine or its parent, drawn as a bullseye. A final state holds nothing: nothing can be added or moved into it, and a state that holds states is not made final.
  • Pseudostate — the dot that marks the initial state: the machine and every compound state that is not parallel have one, with a single transition to the state they start in. Shallow and deep history (H, H*) re-enter the state a compound state was last in; choice (a diamond) branches on guards.
  • Event — something that happens to the thing: a user action, a message from another system or a timer (Source), with an optional Payload. Events live in the machine or in a system, domain or group, so several machines can share them.

Connect the parts with relations:

  • Transition — state → state (or pseudostate). Pick its Event (the trigger; none for a transition that fires when its state completes), and fill in a Guard, Actions and the events it Raises. The arrow is labelled the usual way: PaymentReceived [amount ≥ total] / reserve stock ^OrderPaid, with the events' current names.
  • Emits — a state (on entry, exit or do), a machine, or a C4 element → the event it publishes.
  • Lifecycle of — machine → the entity it models; one machine per entity (two lifecycles of one thing are regions of a parallel state).
  • Implements — the system, container, component or web app that runs the machine → machine. Realises — the element that owns the entity's data → entity.
  • A scenario Verifies a machine, a machine Satisfies requirements, and a mockup Illustrates the state it shows. A state-driven requirement (While …) can point at the state it holds in with While in state: its sentence then reads While the Reservation is Confirmed, …, and follows a rename.

Beyond what may sit where, the Validation list in the Metamodel editor checks that a statechart can run: each machine the lifecycle of one entity and no entity with two machines, one initial state per machine and compound state, at least two regions in a parallel state, nothing leaving a final state, no transition leaving its machine, no two unguarded transitions from one state on the same event, and no state the initial state cannot reach. These are warnings: a machine is often incomplete while you build it. Radical Forge can derive machines from your scenarios, and the MCP server tells an agent about the warnings its changes bring in.

Processes

A Process (palette group Process, in the Radical metamodel) is process logic: a procedure, a workflow, an algorithm — Checkout, Month-end close. It holds Steps, and a step can hold steps of its own, to any depth. A process reads best as a Warnier–Orr diagram: the viewpoint Process (Warnier) under + New view draws every process with its steps.

  • Order — where a step stands among its siblings (1, 2, 3, …). Steps run in this order; the model keeps no other order among them.
  • Repeat — how often the step runs: 1 (once, the default), 0..1 (optional), 1..n or 0..n (repeated), drawn (0,1), (1,n), (0,n) under its name, with its Condition: for each order line, while stock is short, if the customer is new.
  • Children run (on a process or a step) — sequence, one after the other (the default); choice, exactly one of them (by card ⊕ by invoice); concurrent, at the same time (+).

On a canvas a process is a frame that holds its steps, and a step a card that holds the steps inside it, with its repetition and condition under its name; the header of either has ⊕ when its steps are a choice and + when they run at once, and each alternative of a choice is (0,1), as in a Warnier–Orr diagram. Dashed arrows lead from each step to the next in their order; there are none between alternatives or parts that run at once. They are drawn from the order, not kept in the model, and nothing moves for them: arrange the process in its Warnier view. A step is Performed by the person, system, container, component or web app that does it; a process Satisfies the requirements it meets, and scenarios Verify it. Agents write processes over the MCP server the same way.

Working with selections

Click selects one element; Shift-click adds more (⌘-click when Shift is your connect key), and Shift-drag on the empty canvas draws a box around several. A selection brings its relations forward: the selected elements, their relations (and those of anything inside a selected container) and the elements at the other ends stay as they are, the relations turn the accent colour, and the rest of the canvas is dimmed. A selected relation does the same for itself and its two ends. The camera frames what stays, and a click on the empty canvas clears the selection and brings back the camera from before, unless you moved it in the meantime. Leaving a view clears the selection: another view opens with nothing selected, and so does a view you come back to.

With one or more nodes selected (in Designer, on a structure view), the selection bar appears at the bottom of the canvas, above the zoom controls, with how many are selected. Wrap into… and Move to… show when the selection shares one parent; Unwrap when a single container is selected:

  • Wrap into… — create a new container of an allowed type around the selection.
  • Move to… — re-parent the selection into another container, or to the canvas root.
  • Unwrap — remove a container but keep its children and their relations.
  • Align… — keep the elements in a row, a column or a grid on this canvas, optionally in the order you selected them (see Alignments). With a single container selected it reads Align children….
  • Hide from view — in a named view, take the elements out of it without touching the model.
  • Delete — remove from the model (with children). The Delete key asks first: Remove from model, Hide from current view or Cancel; it works in Designer only (not in Viewer, Presenter or while a presentation plays), and on a Mac it is fn+⌫. Deleting several selected elements, or applying a Hub template's values again, is one undo step. Everything is undoable with ⌘/Ctrl+Z, views and sequences included. Undo belongs to Designer: Viewer and Presenter have none, in a text field the keys take back typing, and in an open dialog or wizard they do nothing to the model behind it. A view whose elements were all deleted stays empty; it does not turn into a view of the whole model. The arrow keys do not move elements: drag them.

Views

A view is a named, saved reading of the model: which elements it shows, how they are laid out, where the camera was, and how it renders them. Nothing in a view changes the model; deleting a view deletes no elements.

  • Create with + New view in the left panel. When the metamodel has viewpoints, it offers them under Blank view, each with what it shows. A blank view is named View 1, View 2…, is a table of the whole model, and opens its properties; pick another View type there (Structure for a canvas) and narrow it with its Filter or by hiding elements. A structure view that lists no elements is a canvas of the whole model. A view of a viewpoint is named after it and has its view type and filter. A structure view shown for the first time starts from where All elements has its elements; one of a viewpoint is also arranged by Smart Layout the first time it opens in the Designer (not while a milestone is shown).
  • Open properties with the gear on a view's card (shown under the pointer and on the active card). There you rename the view, move it to a folder, pick its Viewpoint (when the metamodel has any) and change its View type: Structure, Flow, Hierarchy, Table, Matrix or Wiki. A structure view also has Lines and Auto-layout (Auto (Smart Layout) or Hierarchical nested tree), and Layout rules: its pins, alignments and grids in one list. A wiki view has Depth, a Flow view its Sequence, and every view but a Flow view its Filter. Delete view is at the bottom. A group of a view per element has only its name, folder and the list of its views; one of its views has its Lines and Auto-layout, a read-only filter, and a folder that moves the whole group.
  • Folders keep a long list of views in order. In the view's properties, click the folder icon by Folder (Move to folder…) and pick a folder in use or type a new path such as C4/Components; a slash nests one folder in another. A folder opens and closes with a click, and the one holding the active view opens by itself. No folder takes a view out of its folder; it stands at the top level of the list, in its place among the others. Studio moves folders, not single views; agents reorder views with order_views. The gear on a folder's row opens its properties: rename it (its views and subfolders move along) and Move up or Move down to set its place among the folders beside it. A folder stands in the list where its first view does. Agents set the same path with update_view's folder.
  • Lines — a structure view draws its relations curved or orthogonal (horizontal and vertical segments with rounded corners); set it under Lines in the view's properties, or leave it to the model's setting, Lines in this model in the Radical menu (curved unless changed). A relation that has to go around an element keeps the style: a curved one bends around it, an orthogonal one turns at right angles. Smart Layout scores the lines as the view draws them.
  • Panel width — drag the left panel's inner edge to make it wider or narrower; double-click the edge for the default width. The width is kept in this browser.
  • Positions, camera and collapse state are per view. Arrange a container map one way and a context diagram another — switching back restores each exactly.
  • Hidden relations — a relation can be hidden in one view (edge action bar) while staying in the model and in every other view. Undo brings it back; agents can with update_view.

Viewpoints

A metamodel can name viewpoints of its own: a viewpoint is one of the view types above with a filter, under a name, for a question asked of the model again and again. Each belongs to a group, the concern it serves. Some are a view per element — one state machine, one process, one system's containers at a time — and a view of them is a group holding a view of each such element; + New view marks them View per element. The Radical metamodel comes with twenty-five:

  • C4 — System context, Containers and Components (structure views of the people and systems, of the containers inside the systems, of the components inside the containers, each with every relation between them), Containers of a system (one software system, the containers inside it and the people, systems and containers they are related to: C4's container diagram), Components of a container (one container or web app, its components and what they are related to) and Container dependencies (a matrix of the containers, web apps, databases and queues). The C4 metamodel comes with these six.
  • Domain — Domain map (domains and how they depend on and partner with each other), Domain model (entities, what they are part of and reference), Entities of a domain (one domain, its entities and the entities of other domains they reference or are part of) and Domain realisation (a table of domains, their entities and what realises each).
  • Requirements — Traceability (needs, the requirements refined from each, the scenarios that verify those), Requirement coverage (requirements, what satisfies and verifies each), Requirement gaps (the requirements no scenario verifies or nothing satisfies), Responsibilities (the systems, containers and components that satisfy requirements, with theirs) and Specification (a wiki of the needs, their requirements and the scenarios and screens for each).
  • Decisions — Decisions (ADRs, the fitness functions that check each and what it constrains), Decision log (a wiki of the ADRs, the newest first, each with the ones it supersedes) and Fitness functions (by category, with what each checks and constrains).
  • UX — Screen flow (the screens and how users move between them) and Screens (a table of the screens with what they illustrate and what presents them).
  • States — Entity lifecycles (the entities with a state machine, what implements and verifies it), State machine (one state machine with its states, events and transitions, and the entity it is the lifecycle of) and Event catalogue (the events and what emits each).
  • Process — Process (Warnier) (the processes and their steps as Warnier–Orr diagrams) and Process (one process and its steps).

Pick a viewpoint marked View per element under + New view and the list gets one card, a group (Components of a container · 5 views), opened on its first view; a click on the card shows or hides its views. It holds a view of each element of the viewpoint's types (external systems left out), named after the element and showing it and what lies inside it (its filter starts with … and what is inside it). Add a container and its view appears in the group at once; delete it and its view goes. Rename the element and its view follows, unless you renamed the view. A group's views take its folder and viewpoint: their properties say which group they are in, and they are not deleted, detached or given another view type alone, nor are elements picked or hidden in them by hand; deleting the group deletes them all. In the metamodel editor, a viewpoint's View per element sets the types it makes a view of each of. Agents get a group from create_view with such a viewpoint, and set the types with subjectTypes on upsert_viewpoint.

+ New view offers them by group, in two columns over the canvas, and so does the Viewpoint list in a view's properties, marked from the metamodel, with what the picked viewpoint shows under it; None keeps the view's type and filter for it alone. A view of a viewpoint has its view type and filter and follows it: change the viewpoint in the metamodel editor and every view of it changes too. Its card and its properties name the viewpoint. Its filter is the viewpoint's, read-only (Set by the viewpoint); Detach beside it keeps the view type and the filter for the view alone, to edit there, and so does picking another View type. Any view's filter can be saved with Save as viewpoint… under a name: a new name adds a viewpoint, the name of one replaces its view type and filter, and its views follow. Agents use create_view and update_view with viewpoint, and upsert_viewpoint (with its group) and delete_viewpoint.

Filter

In a view's properties (in Designer, the button on its card; it shows on hover and on the active view), its Filter says what the view does with the model's elements, as a chain of levels — for example needs, under each the requirements refined from it, under each of those the scenarios that verify it:

  • The chain works among the view's elements — every element for a view that lists none — and says how many that is. Show every element beside it makes the view list none again, so that it shows the whole model.
  • + Start with — the first level: Every element, or the elements of one type, the roots of the tree.
  • + Level under — the next level, along a relation from the level above, in either direction (Refined into → Requirement, Verified by → Scenario), along Any relation of any type either way (offered where more than one relation leads on), or the children it contains (Contains → Container), to one type or to any element (Contains → Any element), each with how many elements it reaches. × on a level removes it and those under it.
  • + or on a level — another way to its elements: roots of another type (Need or Requirement), or elements reached along another relation (Refined into → Requirement or Verified by → Scenario). The level takes what any of its ways reaches; × beside a way removes it.
  • + Filter on a level — keep its elements by property value (EARS type is event-driven, Status is not set), relation (Has no Verified by), place (Inside Billing) or text. Each filter shows how many elements come in and go through, and its dot switches it off to try without it. Filters are joined with and; a click on and turns it into or, and a run of filters joined with or lets through what any of them does (a bracket marks the run, its count stands by its last filter). The menu offers filters that narrow the level (and) and alternatives to its last run (or).
  • Before the elements exist — every menu offers first what the model's elements give, then, with 0, what the metamodel allows: types with no element yet, the relations and containment the metamodel allows from the level above's types (Need → Refined into → Requirement with no requirement written), and the values of their fields. Build the chain first, then fill it from the table.
  • + Sort — by name, type or a property, within each level; the arrow turns it descending.
  • Click a way or a filter to change it in place: a way's relation (Along) and the types it takes, none ticked for any; a type filter's types; a property filter's property, is / is not / is set / is not set and its values (ticked from those found, with how many have each); a relation filter's relation and Has / Has no; a place filter's container; a text filter's words. Each change applies at once and is one undo step; Done closes the editor.

The view's table shows the tree — a guide line per level, the type beside each name, the top level as headings, each row folding what hangs under it, and each element's summary — and so does its wiki. An element under several parents (a requirement refined from two needs) shows under each with a +1. Every kind of view shows exactly what the filter gives — its count and the view agree. A canvas (structure view), a matrix and a hierarchy draw those elements and only the relations the chain follows — tick Draw every relation between them for all of them; on a canvas an element under several parents is drawn once, with a line to each, and a container the filter does not give is not drawn (its elements keep their places). A flow view plays its sequence instead. A change to the filter or to the model updates every view at once. Smart Layout arranges what is drawn. The filter is kept with the view, each change one undo step; Reset removes it. A view of a viewpoint shows the viewpoint's filter, read-only, with Detach; Save as viewpoint… keeps a view's type and filter in the metamodel under a name.

Structure views

The classic diagram. Relations between elements hidden inside a collapsed container are drawn to the container instead, so a system-level view stays readable while the detail is one click away. Set the view's Auto-layout to Hierarchical nested tree for deep containment hierarchies. The button on the canvas then reads Tree Layout and lays the view out top-down, children too.

Flow views & sequences

A sequence is an ordered list of existing relations. Open Sequences in the left panel, click + New sequence, then click relations on the canvas to append them as steps. Reorder with the arrows, add a note per step (shown on the arrow instead of the relation label), remove steps or Clear all steps, or Create Flow view from sequence in one click (a sequence that already has one names it instead). A Flow view is linked to exactly one sequence; participants are the elements involved, in order of first appearance. Scroll or press ⌘/Ctrl++/− to zoom; ⌘/Ctrl+0 fits.

Sequences are stored with milestones, so a Flow view can show how a scenario changed over time.

Hierarchy views

  • Size — Leaves (area ∝ number of descendants), Uniform (siblings equal) or Relations (area ∝ connectivity).
  • Levels — how many levels below the focus are drawn: 1 to 4 or all (2 by default).
  • Drill — a click selects an element; a double-click focuses its subtree. ↑ Up, Esc or Backspace go up one level, and a double-click on the background goes to the top. Hover a rectangle for its type, children, leaves and relations. Focus, size and levels are remembered per view.

Table views

A table lists what the view's filter gives, as a tree: the chain's levels — needs, the requirements under each, the scenarios under those — or, without a chain, the elements' containment. Each row has the element's name, a guide line per level, its type beside the name and a chevron that folds what hangs under it, and its summary: one line its type's template (Summary in tables in the metamodel editor) makes of the data it has — a requirement's obligation first (MCP server shall reject the write — if a tool call would add an invalid type), a scenario's outcome before its when, an ADR's status and decision, a state where it leads — rendered as Markdown (bold, italic, code, links), the whole of it in the tooltip (a requirement's whole EARS sentence). A click on a row shows the element's attributes in the properties card, where its type's wizard is too; a double-click on its name renames it in place. Relations are edited on the canvas or in the matrix. The table has no palette: elements are added where they will show, by a + row after the rows under each element (+ Requirement · refined into) and one at the end for the top level (+ Need). A + row with one type adds it at once; one with several opens the list of them. An element of the chain's last level, or of a type that holds nothing, has no + row under it. With a chain, an element added under a row goes on the next level, linked to the row's element the way that level hangs under it (a requirement added under a need is refined from it), and is placed beside it; it is made to pass that level's filters where it can (a requirement added under a filter EARS type is event-driven is event-driven, and its + row says so), and a type the filters leave out is not offered. Without a chain, it goes inside the row's element. A new element's name opens in its row, or its type's wizard when it has one. A long table (200 lines or more) draws only the rows around what is scrolled into sight, so a register of hundreds of requirements opens at once; an element just added is scrolled to.

Matrix views

A design structure matrix of the view's elements. A filled cell means at least one relation from the row element to the column element. Click it to select the relation, or pick one from the list when there are several. In Designer, click an empty cell to add a relation (where the metamodel allows it) and click a selected cell again to remove it. With a filter chain the matrix draws only the relations the chain follows, so a new relation is of a type the chain follows between the two (a requirement added to a need is refined from it), or none is added; an empty cell over a relation the matrix does not draw adds no second one. Rows and columns follow containment, and relations of hidden children count for their container. Because the matrix is just another view, it stays in sync with every diagram — add a relation on a Structure view and the cell lights up.

Wiki views

A wiki page reads as an encyclopedia article written from the model. Under the title stand the element's type and where it sits; the short facts (status, technology, date…) are in a box beside the lead, the description is the lead, long fields (an ADR's Context, Decision, Consequences) are sections, and a Contents box lists the headings of a longer page. Relations are sentences read from the page's element: “Uses Event Bus (publishes payment.completed, Kafka) and Transactions DB. Used by API Gateway. Constrained by ADR-001.” — a sentence that would name more than six elements says how many there are and shows them on request. Requirements show their EARS sentence with editable slots.

The pages follow the view's filter when they hold a chain of levels: the overview lists the first level's elements, and each element's page has the elements under it in the chain as its children — a need's page its requirements, each with the scenarios that verify it — named, or as chapters in Multi page. The pages tree follows the same chain, and the article shows only what the chain gives. Without a chain the pages follow containment.

The elements under a page are grouped by type under a heading with their count (Requirements (46)), at every level; a group is shown by its own name and description. The switch at the top of the page picks Single page, which names the children and links to their pages, or Multi page, which writes them as chapters of the same article, as deep as the view's Depth says (1 to 5 levels, in its properties; deeper children are preview cards). A need's page lists the requirements derived from it the same way.

The list of Pages on the left is laid out as the articles are — groups first, then a row for each type — and stays closed until you open a branch or read a page inside it. Its search looks through the names of the pages and what they say, and shows the words around a match; Enter opens the first page found. Overview, at the top, is the page about the whole view; Glossary, at the bottom, says what each kind of element and relation in the view is, as the metamodel defines it — so the wiki explains the words it is written in. The same descriptions appear under the heading that first names a type on a page, and on hover over a type or the verb of a relation sentence.

In the Designer every text on a page is edited in place. What can be done with an element is in one menu — [edit] beside its title or chapter heading, or a right click on the element in a page or in the list of pages: Add child, Add relationship, Edit facts (the parent and the short facts, in the box beside the lead) and Delete. A relationship is added in two steps that read as the sentence the page will write: how it reads from this element (Uses…, Used by…, Constrained by…), then the element it names. A right click on an element in a relation sentence edits or removes that relation. The page you are on is saved with the view, so a deep link lands on it.

A page is also where the model is written. Each group of elements on a page ends with an empty line: type in it and press Enter, and the next element of that group is there, with the line ready for the one after — no wizard and no change of page. A requirement is written as its sentence (“When a payment fails, the system shall tell the customer why”): the clauses go to its EARS fields and the sentence gives it a name; any other element is named. A line that is no EARS sentence (“Users can export their statements”) is kept as written, with its sentence left to be filled in. Paste a list and the page shows what its lines will become before it adds them, as one step to undo; the markers of the list (-, 1., [ ]) are dropped. What you write stays in the order you wrote it until the page is left. Where the new element goes follows from the page: inside the system or group you are reading, derived from the need or requirement, or at the top of the model from Overview. Add: at the end of a page or chapter lists the types it has none of yet — first the ones its neighbours hold, the rest by category — and opens a heading with such a line; only what the metamodel allows in that place is offered.

The sentence of a requirement can be changed part by part, by clicking a part, or whole: [rewrite] above it opens it as text, and Enter reads it into its parts again, which is also how a When becomes a While. No word is dropped on the way: a subject other than the system (“the mobile app shall…”), a condition that opens with none of the EARS words (“After three failed logins, …”) and commas inside a condition stay in the sentence. must, should and will are read as shall, and as soon as, as long as or in case as the EARS word they stand for.

Warnier views

A Warnier view draws what the view shows as a Warnier–Orr diagram: each element on the left of a brace that holds what is under it, read left to right like an outline. It draws the view's filter as a tree — the chain's levels, or, with one level or none, the elements by containment — so any view can be switched to it under View type: a system with its containers and components, needs with their requirements, a process with its steps. Steps stand in their Order (the rest after them, as the view orders them), a step that repeats or is optional has (1,n), (0,n) or (0,1) and its condition under its name, ⊕ stands between alternatives (Children run: choice), each with (0,1) under it unless its Repeat says otherwise, and + between parts that run at once — the standard Warnier–Orr notation. A state machine reads the same way: a compound state's states are alternatives, a parallel state's regions run at once; pseudostates are left out. A click on an element opens its properties card; there is nothing to arrange. The viewpoint Process (Warnier) is a Warnier view of the processes and their steps.

In the Designer a Warnier view is written where it is drawn, as rows are added in a table:

  • + Step, faint under each brace, adds a step at its end; + beside a process or step with nothing in it adds its first; + Process under the processes adds a process (in an empty view it is all there is). The new element's name is open to type; a + pressed while a name is typed keeps it first.
  • The selected card, or the one under the pointer, has its actions in its type line: set the repetition, move up, move down, outdent, indent and delete. The card keeps its size when they show.
  • The repetition (or a click on a step's (1,n)) opens its choices — 1, (0,1), (1,n), (0,n) — and its condition (for each order line).
  • A click on a brace, or on its ⊕ or +, changes how the steps in it run: in sequence, a choice ⊕, or at once +.

A view whose filter is a chain of relations (needs, then the requirements refined from each) is renamed only; add along a chain in its table.

Layout & navigation

Smart Layout

One button, twelve algorithms: eight variants of a layered layout (top-down, left-to-right, packed groups…), stress, force-directed, tree and Radical's own C4 layout; the two best are refined by simulated annealing. All are scored on edge crossings (and how shallow they are), relations leaving an element in nearly the same direction, uneven edge lengths, relations drawn through elements, too many relations on one side of an element, corridors (many relations squeezed through one narrow place, which a layout with the users of a library around it avoids), compactness, proportions, elements bunched in one part of their container, and room for labels. Each criterion is compared among the candidates, so none outweighs the others by its units, and the best one overall is applied (a layout with overlapping elements never wins); the layout you have stays unless another is clearly better — with edge routing cleaned up afterwards. On diagrams under 150 elements it also tries what the live physics (below) would make of that best one, and keeps it only when it scores better. It respects containment, so children are arranged inside their parents, and a group of many barely linked elements (the requirements of a domain, say) can be packed as a compact block, with linked elements side by side. The layout you get is the one that stays: nothing moves it afterwards until you do. A view set to Hierarchical nested tree gets a top-down tree layout instead.

While it runs the button shows its progress. Then a message names the layout that won, with crossings and overdraws before and after, or says the current layout already scores best. The (i) beside the button opens Why this layout?: every algorithm tried, with its score.

Dragging and pins

A drag moves only what you drag: the element (with the other selected elements, if you drag a selection), and the elements it is kept in a row or column with, which follow it across the line. Nothing else moves while you drag. When you drop it, elements it now covers are pushed just clear, each in one piece and in one direction, and a container that grew pushes its neighbours the same way; the rest of the diagram stays where it was.

A drag is one undo step: Undo puts back everything it moved or pushed and takes off the pins it set.

A dropped element is pinned: the live physics (below) leaves it where you put it from then on. Select it to see the pin at its corner; click the pin to unpin it. A view's pinned elements are listed in its properties, with a button that unpins them all. Running Smart Layout rearranges the whole canvas and unpins everything on it (Undo brings the pins back with the old positions); if it keeps the current layout, the pins stay.

Live physics

A light force simulation keeps containers hugging their children and makes room when an element is added: the new element and its surroundings move, the rest of the diagram stays where it is. A container that is expanded opens with its children where they were (children saved on top of each other are set apart), and its neighbours in the same parent (and the parents' neighbours above) step aside just enough, as does whatever they would then lie on; nothing else moves. A container that is collapsed shrinks where it stands, and nothing around it moves. A diagram you open, a view you switch to and a layout Smart Layout just made are left exactly as they are. An element whose only relations go to expanded containers is drawn back next to them when the physics runs, if there is free room on the way. Hold ⌘/Ctrl as you start a drag to let the physics nudge neighbours out of the way while you drag; the node you hold stays where you put it, and pinned elements do not move. From 150 elements up such a drag is a plain one: what you hold moves, and whatever it is dropped on makes room. Dragging a box selection (Shift+drag on the background) moves, saves and undoes like dragging one element.

Alignments

Select two or more elements and choose Align… → Keep in a row (centres on one horizontal line) or Keep in a column (one vertical line). The rule belongs to the view you made it on, and every layout keeps it: drag one member — or an element inside a member container, which grows or shrinks it — and the others follow, the live physics holds the line, Smart Layout picks its best arrangement with the alignment applied. Members may sit in different containers, and expanded containers can be aligned by their boxes.

With Keep their order ticked in the same menu (the default; Studio remembers your choice) the elements also keep the order you selected them in, left to right or top to bottom — select them right to left and the row swaps them round. Drag one past its neighbour and the neighbour is pushed ahead, and Smart Layout never swaps them. Dashed guides show each alignment, with arrowheads when the order is kept; select a member to get buttons that switch order-keeping and remove the alignment, or use Align… → Stop keeping aligned. A view's alignments are also listed in its properties, each with an in order switch (the order they are listed in, which is the order they were selected in).

Align… → Keep in a grid (three or more elements) puts them in a grid filled row by row in the order you selected them, and lays it out in even cells. Pick the number of columns with − / + in the menu (about square by default); later, select a member and use − / + on the guide, or the columns field in the view's properties. Every row stays a row and every column a column, in order, whatever moves.

To arrange what is inside a container, select just the container: the button reads Align children… and offers the same row, column and grid for its children, in the order they stand now — left to right, top to bottom, or row by row for a grid. This works on a collapsed container too: the rule is saved straight away and the children line up when you expand it. With the container selected, its children's guides show their buttons too.

Fit & Smart Fit

Fit All frames the visible elements. Smart Fit (Radical menu) keeps the camera fitted as the diagram changes — useful while importing or laying out, less so while hand-arranging. Scroll to zoom, drag the background to pan.

Quick Search

The search bar sits at the top of a canvas (a structure view). Results are ranked across labels, types, descriptions and technology. ↑/↓ to move, Enter to select the element on the view you are in, or on another view that shows it, Shift+Enter to pick it in All elements, the table of the whole model, Esc to close. With an AI provider configured the same box becomes the assistant (see AI assistant).

Milestones

A milestone is a named, dated snapshot of the whole model — elements, relations and sequences. Click + New milestone in the left panel, name it (v1, v2… by default) and press Enter to capture the current state. Click any milestone to step back in time: the canvas shows the model as it was, the chip at the top names it, and every view still works.

  • One layout per view — a view shows its elements where it has them, for the live model and every milestone, so an element stands in the same place in each and only what changed differs. A milestone keeps its own layout of the whole model, where its views start from. What you move on a view while a milestone is shown is not saved into the view.
  • Diff — the toggle on the chip colours what changed since the previous milestone: added, changed, and removed elements drawn as ghosts. Flow views show removed steps the same way.
  • Editing in the past — if you change something while a milestone is active you are asked what you meant: propagate the change to that milestone and every later one, save as a new milestone right after it, or discard — the chip says unsaved and has the three buttons. With diff on, it counts what was added, changed and removed.
  • Slides can be pinned to a milestone, so a presentation can tell the story in order.
  • Restore to live — in a milestone's properties (the gear on its card): the milestone becomes the live model, and no milestone is shown. It is one undo step; the milestones themselves stay as they are.

Viewer & Presenter

Viewer is a sandbox. Every view opens with the layout it has in Designer; drag, collapse, re-layout, switch views and milestones — all of it is thrown away when you return to Designer (which shows the milestone, or the live model, it showed before, on the view you were looking at, laid out as Designer has it), so you can explore freely in front of others. The metamodel editor, opened from Viewer or Presenter, edits Designer's model: what was explored is thrown away first. Adding to the model, with Import from Hub or Radical Forge, switches to Designer. It is also the perspective the Hub uses to show concepts.

Presenter adds the slide dock. Pick or create a presentation, then Add slide to capture what is on screen: the view, the camera, the layout and collapse state, and the model at that moment. Click a slide to see it on the canvas. Slides can be renamed (double-click the name), re-captured, and linked to a view or a milestone; to change their order, ask an agent (update_presentation). A Hierarchy slide keeps the level it was drilled into, and a slide an agent made with focus zooms onto those elements. Present (or F5 from anywhere) fills the window with the slide; a bar at the bottom has previous, a dot per slide, its name and number, next and exit. → ↓ Space advance, ← ↑ go back, Esc exits. The URL updates as you present, so a listener can open the same slide.

Inspector

Inspector shows what radical check says about the model, in three tabs. Each element a tab names is a link: it opens a panel with the element's findings and tests, and from there Show on canvas goes to Designer on a view that shows it, or Open wiki page to its page. The verdict at the top counts the errors and warnings of the whole check, and each tab's badge says how many of its goals are met, or how many errors it has.

  • Model quality — how good the model is on its own, before any test runs. A tile per dimension: Consistency (it follows its metamodel), Completeness (each requirement a whole EARS sentence, each accepted ADR its context, decision and consequences), Traceability (needs → requirements → what satisfies them → scenarios → tests) and Decisions (accepted ADRs with a fitness function). A dimension is as strong as its weakest metric. Below them the traceability chain (a link that falls short opens the findings that break it), the gaps by group, the goals and baselines of check.json, and every finding by dimension.
  • Implementation — how faithfully the code follows the model, by what the tests say: requirements verified (all their scenarios name tests, and all passed), accepted ADRs verified by their fitness functions, the named tests passing, and the tests the model names among those it should (rule test-unbound). Each axis shows what falls out at each step, the requirements each architecture element satisfies by what the tests say, and the scenarios and fitness functions that do not pass, with what they leave unverified. A note says how old the test results are: they hold for the code as it was then, while the model is checked as it is now.
  • Settings — the model folder's check.json as a form: a goal in percent for any metric, and per rule its severity, baseline (max) and, for test-unbound, the test files it looks at. Changes stay a draft until Save to check.json; the bar above them says how many there are and which loosen the CI gate (a lower severity, a higher baseline, a lower goal, fewer test files looked at), and check.json after saving shows the diff review will see. Ratchet lowers each baseline to what the check finds now, as radical check --ratchet does.
  • The rules about the model run on the model as you edit it, with the same code the command line runs.
  • What the tests say comes from the last radical check <model folder> --report <test reports>: it keeps the test cases it read in the folder's .radical/test-results.json, and Studio picks them up by itself. A scenario or a fitness function names its tests in its Tests property, one file › title per line. Until a report is there, the Inspector button is greyed out.
  • Settings are only for a model kept in a folder, since check.json lies beside it; the command line reads the same file, so Studio and CI agree. Saving them is the only thing the Inspector writes; it never changes the model.

Metamodels

A model in Radical is a graph of typed elements and typed relations. The metamodel is the rulebook for that graph: which element types exist, what each one may sit inside, which relations may join which types, and which fields each type and relation has. It travels with the model — in a .radical file it is the metamodel key, in a model folder metamodel.json — so whoever opens the model gets the same rules.

Everything that edits the model consults it:

  • The palette lists its types, grouped into C4, Domain, Governance, Requirements, States, UX and Other, and your own types under Custom.
  • Placement — dropping an element where its type may not sit (a Component straight on the canvas, a Person inside a System) is refused with a message, and so is reparenting.
  • Connections — the relation type is inferred from the pair of element types, and a pair no relation type allows is refused.
  • The properties card and the wizards are built from the type's fields, including enum options and fields that show only when another one has a given value. The table sums up each element in one line, from the type's Summary in tables.
  • The AI assistant, Radical Forge and the MCP server receive the rules with every request, and their edits are checked against them like yours.

Studio ships two metamodels, chosen when you create a model (New model; --metamodel radical or c4 for the MCP server):

How the layers of Radical connect

Read one requirement through the model, from the words someone wrote to the code that keeps it:

  1. A Need keeps the stakeholder's text as written — a brief, a user story, a regulation.
  2. Each Requirement derives from that need: one EARS sentence the system must make true.
  3. A Scenario verifies the requirement: Given / When / Then, ready for a test.
  4. A State machine — the lifecycle of a domain Entity — shows the states the scenario walks through, and the scenario verifies the machine too.
  5. A Mockup illustrates the requirement, the scenario or a state, and is presented by the web app that renders it.
  6. A Container (or system, component…) satisfies the requirement — it becomes the subject of the EARS sentence — implements the state machine and realises the entity whose data it owns.
  7. An ADR records the decision the requirement led to (traces to) and constrains the containers it governs; a Fitness function implements the ADR as an automated check.

Every arrow in that story is a relation type with a fixed direction; the sections below describe each type and each relation, and which pairs they join.

The C4 metamodel

The C4 model describes software at four levels of zoom: the people and systems around yours (context), the deployable parts of a system (containers), the parts of a container (components), and code, which Radical leaves to your editor. Radical's C4 adds three specialised containers — database, web app, queue — so the diagram says what each part is without a note. Every C4 type has a Description and an External flag (except Group); containers and components have a Technology as well. Both metamodels contain all of this.

Element types

Person
Someone who uses or runs the system: a customer, an operator, another team. A person stands at the root of the canvas or inside a group, never inside a system — they are outside of it by definition. Mark a person External when they belong to another organisation. Retail Customer, Bank Operator.
Software System
Something that delivers value to its users and is owned by one team: yours, or one you depend on (mark it External). On a context diagram it is a box; expanded, it holds its containers. Systems may nest inside other systems and groups, and in Radical inside a domain, where the system is the bounded context that realises that (sub)domain. Core Banking Platform; SWIFT Network (external).
Container
Something that runs or stores data and is deployed on its own: a service, a worker, a mobile app, a serverless function. It lives inside a system (or a group within one). Technology says what it is built with. Payments Service — Kotlin, Spring Boot.
Database, Web App, Queue
Containers with a known role, drawn with their own shapes: a Database stores data and never starts an interaction; a Web App is a browser front end and may hold components; a Queue carries messages between containers. All three live in a system or a group and have a Technology. Accounts DB — PostgreSQL; Web Banking — React; Event Bus — Kafka.
Component
A part of a container behind a clear interface: a controller, a domain service, an adapter. Components live inside a container, a web app or a group — never straight in a system or on the canvas. Payment Validator inside Payments Service.
Group
A labelled boundary with no meaning of its own: a team, a layer, a deployment zone. Groups nest in groups, sit at the root, or inside a system to gather some of its parts (as Structurizr groups do). A group gives no place an element could not have without it: containers, components, databases, web apps and queues go into a group only when it is inside a system, and moving a group is refused where what it holds would have no place. No relation starts or ends at a group: connect what is inside it.

The Interacts relation

Interacts is the only relation in C4 and covers any meaningful interaction: the source calls, uses, sends to or delivers to the target. Its label says what happens (“Makes payments using”), its Technology how (“JSON/HTTPS”). The direction is the direction of the request, not of the data: draw it from the initiator.

  • Person → system, container, web app, component.
  • Software System → person, system, container, database, web app, queue, component.
  • Container and Web App → person, system, container, database, web app, queue.
  • Component → component, container, web app, database, queue, system.
  • Queue → container, web app, component (a consumer it delivers to).

What the rules leave out is deliberate: a Database never initiates, so nothing starts at one; a container does not call a component of another container directly — draw the call to the container, or from component to component; and no relation touches a Group.

The Radical metamodel

Radical is the default. It contains the whole C4 metamodel unchanged, except that a Software System may also sit inside a Domain, and adds fifteen element types in six layers. The types of the new layers can sit at the root, in a system, in a domain or in a group, unless noted. Needs, requirements, scenarios, mockups, ADRs and fitness functions open a wizard when you create them, and the Table view sums each of them up in one line.

Domain layer

Domain
A part of the problem space, in the language of the business rather than of the software: Payments, Customer onboarding. Domains sit at the root, in groups, or in other domains to any depth (subdomains). Kind says how much it matters — core (where you compete), supporting or generic (buy it) — and Vision what it is for. A Software System placed inside a domain is the bounded context that realises it. Between domains, Depends on and Partnership draw the context map (see relations).
Entity
A thing the domain keeps track of and that has an identity over time: a reservation, an order, a payment. Entities live at the root, in a domain or in a group. Kind is aggregate root (the default, drawn with a solid border) — a consistency boundary other aggregates refer to by id — or entity (dashed), a part that belongs to exactly one aggregate through Part of. The C4 element that owns the entity's data realises it, a state machine is its lifecycle, and it can satisfy requirements. In the Wiki the parts of an aggregate list under its root; a table does so when its view's chain follows Part of. Order (root) with Order Line (part of Order).

Requirements layer

Need
Raw input in the stakeholder's own words, kept verbatim: a product brief, a user story, a stakeholder note, meeting notes, a regulation or anything else (Kind), with its Source — who said it, or where it came from. A need is not a requirement: nothing satisfies or verifies it, and it has no status — being in the model means it was heard. Requirements derive from it, and a need can sit under a broader need. Radical Forge stores the brief it starts from as a need. “Customers must confirm high-value transfers on their phone.” — PSD2, regulation.
Requirement
One thing the system shall do, written as an EARS sentence. EARS type picks the pattern and shows only the clauses it needs: ubiquitous (“The system shall…”), event-driven (“When trigger, …”), state-driven (“While precondition, …” — or While in state, pointing at a State: “While the Order is Ready, …”), unwanted behaviour (“If condition, then …”), optional (“Where feature, …”) and complex (any combination). Action is what the system shall do, Rationale why. Type the whole sentence in the wizard and it is split into the fields for you.
The card on the canvas shows the composed sentence; its subject is the first element that satisfies the requirement, so linking a container makes the sentence name it. A requirement derives from a need or a broader requirement (decomposition), traces to the ADRs and fitness functions it led to, and can constrain C4 elements directly. “When a transfer exceeds €1,000, the Payments Service shall require strong customer authentication.”
Scenario
An acceptance example in Gherkin: Given the starting situation, When something happens, Then the outcome, with Extra steps for And / But lines. A scenario verifies a requirement, and a state machine when it walks through its states; Given is then the source state and Then the target. Tests names the automated tests that run it, one file › title per line, which radical check reads. Scenarios become tests — which is how a coding agent turns the model into checks. Given a confirmed reservation, When staff mark it ready, Then the customer is notified.

States layer

Event-driven, hierarchical statecharts with the semantics of SCXML and XState; the State machines chapter shows how to build one on the canvas.

State Machine
The lifecycle of one entity, drawn as a frame that holds its states. It is the Lifecycle of exactly one entity and is named after it on the canvas; the C4 elements that run it implement it; scenarios verify it; it can satisfy requirements and emit events when it is not yet known which state does.
State
A situation the entity can be in. States live only inside a machine or another state: a state with child states is compound. Kind normal is the usual; parallel makes its child states regions that are active at the same time; final ends its parent (drawn as a bullseye). A normal or parallel state can run Entry and Exit actions, and a normal one an ongoing Do activity; it can emit events from them.
Pseudostate
A point the machine passes through but never rests in. Initial (a filled dot) is where the machine, and every compound state that is not parallel, starts — with exactly one outgoing transition. Choice (a diamond) branches on guards; shallow and deep history (H, H*) return to the state that was last active. Pseudostates live inside a machine or a state.
Event
Something that happens and can trigger a transition: Source is external (from outside the system), internal or a timer, with an optional Payload. Events live at the root, in a machine, a system, a domain or a group, so one event can be shared. A transition points at the event that triggers it and the events it raises; people, C4 elements other than databases, machines and states emit events.

Process layer

Process logic, drawn as Warnier–Orr diagrams; the Processes chapter shows how to write one.

Process
A procedure made of steps. Children run says whether its steps run in sequence, are a choice (one of them) or are concurrent. It satisfies requirements and scenarios verify it.
Step
One part of a process, inside the process or another step. Its Order places it among its siblings, Repeat (1, 0..1, 1..n, 0..n) and Condition say how often and for what it runs, and Children run how the steps inside it run. It is performed by a person, system, container, component or web app.

UX layer

Mockup
One screen of the product: its Screen / route, a Design link to Figma or Penpot, and optionally a low-fi wireframe drawn by AI on the card. A mockup illustrates the requirements, scenarios and states it shows, is presented by the web app, container, component or system that renders it, and navigates to other mockups, with the trigger — together, the screen flow. See Mockups & screen flows.

Governance layer

ADR
An Architecture Decision Record in the Nygard / MADR shape: Status (proposed, accepted, deprecated, superseded), Date, Context, Decision, Consequences and Alternatives considered. An ADR constrains the elements the decision governs, supersedes the ADR it replaces, is what requirements trace to, and what fitness functions implement. A new ADR starts proposed with today's date. ADR-001 Event-driven core — constrains Payments Service and Event Bus.
Fitness Function
An objective, preferably automated check that the architecture still has a property it was designed for (from Building Evolutionary Architectures): what it measures (Description), its Category — structural (dependencies, layering), operational (latency, availability), process (review, deployment) or holistic — the Threshold / success criteria and Tests, the automated checks that run it. It implements the ADR it verifies and constrains the elements it guards; requirements can trace to it. “Payment p99 < 250 ms” — operational, implements ADR-001.
Blueprint
A curated reference architecture imported from the Concept Hub — not drawn by hand, so it is not in the palette. It has a Status (draft, reviewed, approved, deprecated), the Domain / context it fits and a Rationale, and arrives with its systems, requirements, mockups and views. It sits at the root or in a domain or group and has no relations of its own.

Relations in Radical

Radical keeps Interacts between C4 elements and adds eighteen relation types. Each has a direction — read it as a sentence from source to target — and joins only the pairs listed. When you connect two elements Studio picks the relation type the pair allows; two pairs allow two types (entity → entity, domain → domain), so there you choose it in the properties card.

Domain

Realises
The software behind the domain. System or container → domain: the bounded context that implements the domain. System, container, component or web app → entity: the element that owns the entity's data. Orders Service realises Order.
Part of
Entity → entity: a part of an aggregate points to its root. Aggregates never contain each other; they refer to each other with References.
References
Entity → entity: one aggregate refers to another by id, with a Cardinality (one or many) and a description. Order references Customer (one).
Depends on
Domain → domain: the source domain needs the target to do its work — the plain arrow of a context map.
Partnership
Domain → domain with a context-mapping Pattern: partnership, shared kernel, customer–supplier, conformist, anti-corruption layer, open host service, published language or separate ways — how the two teams' models meet.

Traceability

Derives from
Requirement → need: the requirement turns that stakeholder input into a shall-statement. Requirement → requirement: decomposition into finer requirements. Need → need: a need inside a broader one. The Wiki shows these as a tree and its Add child creates the link; a table whose chain follows them shows the tree too, and its + row adds an element already linked. Nothing else may point at a need.
Satisfies
Any C4 element, a domain, an entity or a state machine → requirement: this element is what makes the requirement true. The first one becomes the subject of the requirement's EARS sentence. An optional Note says how.
Verifies
Scenario → requirement or state machine: the scenario is the acceptance test for it.
Traces to
Requirement → ADR or fitness function: the decision the requirement led to, or the check that keeps it.

Behaviour

Lifecycle of
State machine → entity: the machine is the lifecycle of that entity — one machine per entity (two lifecycles of one thing are regions of a parallel state).
Implements (C4 → machine)
System, container, component or web app → state machine: this element runs the machine.
Transition
State or pseudostate → state or pseudostate, within one machine. It points at its trigger Event (none means a completion transition, taken when the source finishes), has a Guard and Actions, lists the events it Raises, and is external or internal (stays in the state without exiting it). The canvas labels it event [guard] / actions ^raised.
Performed by
Step → person, system, container, component or web app: who does the step of a process.
Emits
Person, system, container, component, web app, queue, state machine or state → event: this element raises the event; for a state, On says whether from its entry, exit or do activity. A transition raises events through its Raises field instead.

UX

Illustrates
Mockup → requirement, scenario or state: the screen shows this requirement being met, this scenario's step, or what the user sees while the entity is in this state.
Presented by
Mockup → web app, container, component or system: the part of the architecture that renders the screen.
Navigates to
Mockup → mockup, with the Trigger (“Tap Confirm”): one step of a screen flow.

Governance

Constrains
ADR, fitness function or requirement → person, system, domain, container, component, database, web app or queue: the decision, check or requirement applies to that element; an optional Note says how. This is what an agent reads before it changes the element.
Supersedes
ADR → ADR: the newer decision replaces the older one (set the older one's status to superseded).
Implements (fitness function → ADR)
Fitness function → ADR: the check verifies that the decision still holds. (The same relation type as Implements under Behaviour, with other pairs.)

Rules and checks

The metamodel is enforced in two ways.

Refused at once

  • Placing or moving an element where its type may not sit, or at the root when its type needs a parent (a container, database, web app, queue or component, a state, a pseudostate).
  • Adding one more element of a type that has reached its maximum count.
  • Giving a relation a type that does not join its two ends, or changing an element's type when one of its relations would then not be allowed.
  • Moving a group where something it holds would have no place.
  • Connecting a pair of types that no relation type allows: “Relation not allowed: Database → Person”.
  • Moving an element into itself or one of its descendants.

The same refusals reach the AI assistant, Radical Forge and the MCP server as messages they can act on.

Listed as issues

Some rules are about the model as a whole, and a model is often incomplete while you build it, so they are warnings rather than refusals. The Validation list in the metamodel editor shows them (and the MCP server's get_issues), each taking you to the element:

  • Any metamodel: a type the metamodel does not know, a misplaced element or one that needs a parent, a relation to an element that is gone or of a type the metamodel does not know (errors, e.g. from a hand-edited file); an element in a group where its type has no place; a relation between types no relation type joins, or whose type does not join its two ends; a reference field that points at nothing or at the wrong type; an empty required field on an element or a relation; too few or too many elements of a type; and, in custom metamodels, two properties of a type with one key, or a key every element already has.
  • Domain model (Radical): an aggregate root that is part of something (it should reference it); a part of something that is not an aggregate root; an entity that belongs to no aggregate or to two.
  • State machines (Radical): a machine with no entity, or an entity with two machines; a machine or compound state with no initial pseudostate, or more than one; an initial pseudostate without exactly one outgoing transition, or with one coming in; a parallel state with fewer than two regions or with an initial pseudostate; a final state with children or outgoing transitions; a transition that leaves its machine; two unguarded transitions from one state on the same event; a state the initial state cannot reach.

Checked by radical check

A model can follow its metamodel and still be unfinished. These rules say what is missing. The Inspector and radical check show them, the Validation list does not. They are warnings unless the model folder's check.json says otherwise, and its goals can ask for a share of the model that meets them; radical check --list-rules lists them.

  • Requirements: a requirement without the action or a clause its EARS type needs; one no scenario verifies; one nothing satisfies; one that derives from no need and no other requirement; a need no requirement derives from; a scenario that verifies nothing.
  • Decisions: an accepted ADR no fitness function implements; an accepted ADR without date, context, decision or consequences; an ADR whose superseded status and Supersedes links disagree; a fitness function that implements no ADR and constrains nothing; a fitness function without a threshold.
  • Tests: a scenario or fitness function that names no test. With test reports: a named test that failed or is missing from the report of its file (errors), that was skipped, or whose file did not run; with an include in check.json, tests no scenario or fitness function names.
  • The folder: a missing radical.md, a JSON file that does not parse, Git conflict markers, a node file without id or type, two files with one id (errors), and views, sequences or slides that point at something gone.

Metamodel editor

Radical menu → Metamodel editor… edits the model's metamodel — Radical or C4, as chosen when the model was made — and you can rename it. List shows a card per node type and relation type; Diagram draws them (see Metamodels): click a type or a relation to see where it may sit and what it joins, tick relations in the legend to show or hide them, and Edit type opens its card in the list. Reset to C4 preset goes back to plain C4, but only when the model holds nothing C4 has no type for.

  • Node types — on the canvas a type of your own is a card in its colours with its name and the element's, or a frame while it holds elements. Each has a label, fill and text colour, Description, default width and height, min and max instances, allowed parents (and At the root), and properties: a key, a label and a kind — text, long text, number, boolean, enum with its options, or a reference to one or many elements of a type — and whether it is required. Icons, collapsed sizes, enum defaults and fields that show only when another one has a value come with the built-in types; for your own types set them in metamodel.json. Then the Summary in tables: how the table sums up an element of the type in one line, from the data it has. It is a template of tokens — {key} a property (or {label}, {description}, {technology}), {type} the type's name, {ears} a requirement's EARS sentence, {obligation} who shall do what (the action's first phrase) and {condition} the when / while / if / where it holds under, {transitions} where a state machine goes from a state or on an event, {out:type} / {in:type} the elements linked by relations of a type, {key.sentence} its first sentence, {key.phrase} its first phrase, {key.cap} capitalised, {key.bold} bold, {a|b} the first of them that has a value — where a part in [ ] is left out when a token in it is empty, and the template's own text may use Markdown (**{status.cap}**, or {status.cap.bold}). The built-in templates start with what matters, so that a cut-off line loses detail, not meaning: [{obligation.bold}][ — {condition}] for a requirement, [{then.phrase.cap.bold}][ — when {when}] for a scenario, [{status.cap.bold}: ]{decision.sentence} for an ADR. The field lists the type's tokens and shows how the template reads on one of its elements; left empty, the built-in template for the type applies, else the description's first sentence.
  • Relation types — label, Description, the allowed pairs of source and target types (none means any pair), and their own properties (references included: that is how a transition points at its event). Reads as and Reads back as say how the relation reads in a sentence from its source and from its target (Constrains / Constrained by); the wiki writes its relation sentences with them, the canvas does not show them.
  • Viewpoints — a card per viewpoint with its view type, its filter in words and how many views are of it: its name, Group (none puts it under Custom), View type and Description, which + New view shows. A change applies to every view of the viewpoint. The filter itself is set in a view: detach a view of the viewpoint, change its filter and save it as a viewpoint under the same name. Deleting a viewpoint leaves its views their view type and filter.
  • Both kinds of type have a Description: what an element of the type is, or what the relation says about its two ends. The wiki shows it in its glossary and on its pages.
  • Built-in types can be extended but not deleted; add as many of your own as you need. A type of your own can be deleted once no element, relation or reference uses it, in the model or in a milestone, and no viewpoint or view filter names it.

Validation is live: the palette, the parent drop-down, drag-and-drop and connection previews all consult the metamodel, and the AI assistant's patches are checked against it too. The Validation list beside the types shows everything the model breaks now — errors, and warnings such as a missing required field, a reference to nothing or a state machine rule — and Open in Designer takes you to the element it is about.

Concept Hub

The Hub is a curated library of requirements, ADRs, fitness functions, patterns (C4 fragments) and blueprints (whole solution skeletons). It is rendered by the same engine as Studio, so you can open any concept as a diagram, wiki page or table before importing it. Filter the catalogue by category, tag and status, and sort it by name, category or number of connections. Copy JSON and Download give one concept as a .radical file. Select several and Add to Studio.

  • Templates — concepts with parameters (a latency budget, an endpoint, a data class) ask for values on import; the Hub template section in the element's properties lets you change them later.
  • Blueprints — pick which elements and which referenced concepts to bring in. Every blueprint ships one screen flow per actor (mockups with wireframes) and named views: on the canvas System context, Containers, Governance map, Mockups (every screen flow with its wireframes), its technical flow and one Flow view per screen flow; in the wiki Governance and Requirements. In the Hub, the view selector next to Canvas / Wiki / Table lists the views of the current mode; on import they arrive as views of your model, limited to the elements you picked.
  • Drop target — with a compatible container selected, imported elements become its children. Otherwise they land in free room nearest the middle of the screen.
  • Into Designer — Add to Model in Viewer, where the Hub's link opens a model, switches to Designer first, and the concept is saved with the model.
  • One step — whatever one Add to Model brings in (the concept, its related concepts, a blueprint's parts) is taken back by one Undo.

AI assistant

Bring your own model: Ollama (local, no key), OpenAI, Anthropic Claude or Google Gemini. Enable AI, pick the active provider, paste a key, Test connection. Nothing is proxied through radical.tools.

Then open Quick Search (⌘/Ctrl+P) and switch to ✨ AI mode — Tab on an empty box, the ✨ button, or ⌘/Ctrl+Enter to send the current text. The assistant sees the model and its metamodel and can:

  • Answer questions — “what depends on the Event Bus?”, “which containers have no owner?”. It queries the model with a small query language (LIST NODES WHERE …, GET NEIGHBORS, STATS MODEL) rather than guessing.
  • Change the model — “add a Redis cache between the API gateway and the accounts service”. The assistant works with the same tools as the MCP server: it adds, updates, moves and deletes elements and relations, builds views, sequences, slides and milestones, aligns and lays out, and edits the metamodel. Every change is checked against the metamodel and can be undone like any other edit. It can also switch to a view or bring an element into focus on the canvas.
  • Draft governance — turn a paragraph or a need into EARS requirements (linked back to the need) or an ADR with the right fields filled.

Outside Studio the MCP server gives the same tools, except the ones that drive the canvas, to Claude Code, Claude Desktop, Codex or any other MCP client.

Radical Forge

Radical Forge (New model → Create with Radical Forge on the welcome screen, or Radical menu → Radical Forge…) turns a plain-language description of a system into a model, one reviewable stage at a time: Requirements (EARS) → Domain model → Fitness functions → Gherkin scenarios → State machines → Processes → Mockups → C4 model → Review. Each stage may first ask a few clarifying questions, suggests matching Hub concepts, fills the gaps it finds in the stages before it, and can be regenerated before you continue.

  • The description is kept as a Need. When you press Start, the text is saved in the model as a need (named after its first line), and the Requirements stage links every requirement it writes to it with Derives from. If the model already has needs, Start from on the Description step loads one instead, and your edits are saved back to it. Going back and starting again updates the same need instead of adding a second one.
  • Hub concepts that fit. For the Requirements, Fitness functions and C4 stages, Forge ranks the Hub catalogue against your description (rarer words count more, and so do the concepts linked from a blueprint that fits), and the model picks at most five that fit, whatever language the description is in. They appear under Picked from the Hub, checked; untick the ones you do not want, or Import one as it is. When a blueprint fits the whole system, the C4 stage offers it first, to import as a skeleton. Without AI you see the best keyword matches instead.
  • The view structure, first. Under Views on the Description step you choose the views the run files its output into, before anything is modelled:
    • Radical structure (the default) — the structure of radical.tools' own model: a view of each viewpoint of the metamodel, in the folders Conceptual (Domain map, Entities of a domain, Traceability, Specification, Entity lifecycles, State machine, Event catalogue, Process, Screen flow, Screens), Logical (System context, Containers of a system, Components of a container, Container dependencies, Domain realisation, Responsibilities) and Governance (Decisions, Decision log, Fitness functions, Requirement coverage, Requirement gaps). Customise… lists them by folder; untick the ones you do not want, or tick the whole-model Domain model, Process (Warnier), Containers and Components, left out by default. A viewpoint that draws one element gets its group, which holds a view of each domain, state machine, process, system or container and takes in the ones later stages add. A stage's views are made when the stage begins, so what it adds shows up in them as it goes, and the ones it leaves showing nothing go again when it ends; Traceability is made as soon as the need is saved. The model's own view of a viewpoint is used wherever it is. The wikis it makes, Specification and Decision log, open in Multi page with a Depth of 5, so each reads as one article. These views list no elements, so whatever is added later, by a run, an agent or by hand, shows up in them.
    • Layer canvases — seven canvases that list what each stage adds: Conceptual (the need, requirements, scenarios and mockups, and for now the domain model too), Screen flow (the mockups alone, so it shows how one screen leads to the next with Navigates to), Domain (the domains and their entities), States (the state machines, their events and the entities they are the lifecycle of), Processes (a Warnier view of every process and step), Logical & physical (the C4 elements) and Governance (fitness functions and ADRs). A stage's canvas is created, empty, when the stage begins (and removed again if the stage leaves it empty), and reused by a later run with the same name.
    Forge preselects the structure the model already has. After each stage it shows the view of the stage's work (Traceability, Domain model, Fitness functions, Entity lifecycles, Processes, Screen flow, Containers, or the stage's layer canvas). On a canvas, new elements are placed beside what it already shows, in a block that grows sideways rather than down. The structure is fixed once the run starts.
  • Each stage refines the whole model. A stage looks at the model from a new side, so it finds what the stages before it missed: a process step no requirement asks for, a timeout no scenario covers, a screen showing a field no entity holds. Where your description or answers already imply the missing piece, the stage proposes it, with the links its own stage would have given it (a new requirement derives from the need and gets a scenario), or a correction of what is wrong; what would go beyond the description it names as an open question in its summary. Each time, the stage pauses on Add this to earlier stages?: what it found, and exactly what it would write — each element with its type, name and fields, each link with its two ends, each change with the old value and the new one. Add it writes all of it; Don't add writes nothing. Either way you can type a reply first (another name, what to leave out), and the stage follows it. A stage cannot write to earlier stages without asking, and it never deletes. The stage's step on the bar above is marked ✎, amber while a proposal waits for you, then with how many elements you let it refine; its tooltip names them, and so does Refined … elements of earlier stages under the stage's result. Regenerate takes them back with the rest of the stage; what you or another program change in the model while the stage runs is not counted and stays. In a folder with no base from git, the run saves the model as it was before it, so Changes on branch shows everything the run changes. Under the stage's result, open gaps lists what the completeness rules of radical check still find for the stages done (a requirement without a scenario once the scenarios are written, a step nobody performs once the C4 model is there); the next stage gets the list.
  • Arrange after each stage. When a stage is done, Forge asks whether to keep its new elements in a Row, a Column or a Grid on each canvas that shows them (an alignment every later layout keeps), and offers Smart Layout on that view. Nothing is rearranged unless you choose it.
  • The domain model comes right after the requirements, which are its source: the stage adds the domains and entities the requirements talk about, groups entities into aggregates, links the references between them and maps how the domains relate, and links each entity to its requirements. The later stages speak its language: scenarios name its entities, state machines model the lifecycle of its entities, and C4 links the systems and containers to the domains and entities they realise.
  • State machines follow the scenarios: the stage finds the entities of the domain model with a real lifecycle (often none, and rarely more than three), models each with a state machine, and derives its transitions from the scenarios — Given the source state, When the event, Then the target state and its effect — including declines, timeouts and cancellations. The scenarios verify the machine, and the C4 stage later links the elements that run it (Implements) and own the entity's data (Realises).
  • Processes follow the state machines: the stage writes each procedure the requirements and scenarios describe (often none) as a process of ordered steps, with what repeats ((1,n) for each order line), what is a choice ⊕ (scenarios with one When and different Thens) and what runs at once +. The scenarios verify the process, it satisfies its requirements, and the C4 stage later links each step to who performs it (Performed by). The Processes view lays itself out, so there is nothing to arrange after this stage.
  • Mockups come before C4: the stage creates the user-facing screens with Illustrates and Navigates to links, then Generate wireframes draws a wireframe for every mockup that has none. The C4 stage then designs the front-ends the screens need and links each mockup to its container with Presented by.
  • Review comes last, once every part of the model is there: it reads the whole model against your description, closes the open gaps the description implies and makes the parts agree (one name for one thing, scenarios that match the transitions and the order of the processes, no step, screen or element no requirement asks for). Every change it would make is a proposal you answer, and what stays open is in its summary.
  • Finish here ends the run at any stage and keeps what has been generated. The final step summarises every stage (what was added, what was skipped) and exports the scenarios as .feature files; ← Back resumes where you stopped.
  • From your own agent. The same run, with the same stages, prompts, clarifying questions and Hub suggestions, works in Claude Code, Claude Desktop or any other MCP client, with the agent's model instead of a key in Studio. While an agent runs Forge on the folder Studio has open, the Forge button in the search bar pulses — blue while the agent generates a stage, amber while it waits for you (its questions, a refinement of an earlier stage it proposes, how to arrange a stage, whether to go on) — with the stage it is at; click it to see the run's steps, read only, each stage that refined earlier ones marked ✎ with how many. Answer the agent in its own chat. Follow on the canvas in that view has Studio keep up with the agent: each time it adds or changes elements, Studio opens a view that shows them (the one you are on, when it shows any; a canvas before a table; never All elements) and frames what the agent has done in this turn. What no view shows yet is followed once a view does, as when a stage is filed into its views at its end; the Forge button is underlined while it follows. Move the camera or open another view yourself and it leaves you alone until the agent's next turn, after a pause of 15 seconds; it stops with the run. The button stops pulsing when the run finishes, when the agent's client closes, or after 30 minutes without a change.

MCP server

The MCP server lets a coding agent work on your model directly: Claude Code, Claude Desktop, Codex or any other client that speaks the Model Context Protocol. It runs locally over stdio, is bound to one Markdown folder, and offers the same tools as the AI assistant in Studio, so the agent can read the architecture, ADRs and requirements before it writes code and update the model when the design changes. Nothing leaves your machine except what your agent sends to its own provider.

Set it up

With Node.js 20.11 or newer, run the published package; nothing to clone:

npx -y @radicaltools/mcp --folder /absolute/path/to/my-model   # waits for MCP messages on stdin

Pin a version (@radicaltools/mcp@0.2.0) for a setup that does not change under you, and keep it at the version of your Studio (Radical menu → About Radical Studio); on Windows use npx.cmd. radical-mcp --version prints the version, and the agent reads it in get_model_summary. Or build it from a clone of the repository (see local install):

npm install
npm run build -w @radicaltools/mcp
node apps/mcp/dist/index.js --folder /absolute/path/to/my-model   # waits for MCP messages on stdin

Then register that command with your client, using absolute paths:

# Claude Code
claude mcp add radical-folder -- npx -y @radicaltools/mcp --folder /path/to/my-model
# … or from a clone
claude mcp add radical-folder -- node /path/to/radical.tools/apps/mcp/dist/index.js --folder /path/to/my-model

# Codex
codex mcp add radical-folder -- node /path/to/radical.tools/apps/mcp/dist/index.js --folder /path/to/my-model

For Claude Desktop, add it under mcpServers in ~/Library/Application Support/Claude/claude_desktop_config.json (on Windows %APPDATA%\Claude\claude_desktop_config.json) and restart the app. Give the full path to node, because the app does not see your shell's PATH:

{
  "mcpServers": {
    "radical-folder": {
      "command": "/usr/local/bin/node",
      "args": ["/path/to/radical.tools/apps/mcp/dist/index.js", "--folder", "/path/to/my-model"]
    }
  }
}

The folder may also be relative to the directory the client starts the server in. A missing or empty folder becomes a new, empty model; --metamodel radical or c4 picks its metamodel (default radical, the Radical metamodel). A folder with other files and no radical.md is refused, so the server never writes into a folder that isn't a model.

Working alongside Studio

Open the same folder in Studio: in the desktop app, or in a Chromium browser through Open → Folder… (the browser asks for folder access; a model kept only in browser storage cannot be reached by the server). Studio reloads the folder when the agent changes it, so new elements appear on the open canvas. For about five seconds after the last change, new and changed elements are marked and removed ones show as ghosts, so you can follow the agent; a change to the layout alone is not marked. Then ask the agent to call get_model_summary first; the server's instructions tell it to as well.

Studio writes what you select on the canvas, and the view it is on, to .radical/selection.json in the folder. The agent reads it with get_selection, so you can say “fix the selected mockup” instead of naming it.

With each change the server also records its version in .radical/agent-activity.json. When it is not Studio's version (Claude Desktop running the server from an old clone, an npx setup pinned to an earlier release), Studio says so once for the model, naming both versions and which is older: builds of different versions may read and write the model differently, so update the older one. Builds of one version from different commits count as the same version.

When the model folder is in a git repository, a change can start in the model: add or change a requirement, a scenario or a component in Studio, then ask the agent to implement it. get_changes lists the elements and relations added, removed and changed since the branch left main (or since the commit you name), with each field's old and new value and the elements each one relates to, such as the component that satisfies a requirement and the tests its scenarios name. Moving elements and editing views are not changes to implement, so they are left out. radical diff on the command line prints the same list.

Changes on branch

Studio shows the same changes while you edit, without git: get_changes and radical diff --save-base save the model where the branch left main to .radical/base.json in the folder, and radical hooks install <folder> adds git hooks that save it again after a checkout, a commit or a pull. With a base beside the model, the Changes on branch button in the toolbar counts the changed elements. Its tooltip and the Inspector say what the changes are counted since: main and the commit, or the ref radical diff --since was given (HEAD, a tag, a branch). A field emptied again, a box ticked and unticked or a text typed and deleted, is no change. Turned on, it marks new and changed elements on the canvas and shows removed ones as ghosts, inside their container on every view and clear of what it holds, every view in the list counts the changes it shows (a removed element where its ghost is drawn), and the properties card lists each changed field with the words removed and added. The Inspector, which a base opens even without a test report, starts its Implementation tab with This change: each requirement and ADR changed since the base, with what the last test report says of it (verified, failing, test not written) and two warnings the check cannot give, a requirement that changed while its scenarios did not, and a removed one whose test still runs. Its first tab, Changes, on which it opens, lists every element added, changed (with the fields that changed) and removed, and the relations; a click on an element opens its properties card, read-only, with the words that changed, Show on canvas and Open wiki page, each offering the views that show the element. A base older than a day is marked there with the commands that save it again, since Studio cannot tell which branch is checked out now.

When the base is saved

The base is the model at the commit where the current branch left main (git merge-base HEAD origin/main; main, then HEAD, when there is no origin/main). Only the command line and the MCP server work it out and save it; Studio reads .radical/base.json every few seconds and compares the model with it as you edit, so the list of changes is never stored, and it empties once the base catches up with the model.

Outside git. A folder git does not track has no such base. When a Radical Forge run starts on a folder with no base from git, in Studio or from an agent, it saves the model as it is at that moment (often an empty folder) as the base, so Changes on branch and the Inspector show everything the run adds and changes, counted since the start of the Forge run. Such a base never counts as old, and the next run replaces it; a base from git is never replaced.

radical hooks install <folder> adds the four hooks (in this repository, npm run hooks). A git fetch, a reset or a stash runs no hook: the base stays as it was until the next checkout, commit or pull, or until you save it by hand.

  • Committing on the branch keeps the base: it is where the branch left main, so the list holds the whole branch's work, also what an agent has already committed.
  • After the pull request is merged, switch to main and pull: the base becomes the new main and the list empties. On the old branch it stays, since a squash merge puts a new commit on main and the branch still left it where it did.
  • To see only what is not committed yet, save the last commit as the base: radical diff <folder> --save-base --since HEAD. Without the file (.radical/base.json deleted) there is no base, and Changes on branch offers the commands that save one.

Editing while the agent writes. You can keep working in Studio while an agent changes the same folder; neither overwrites the other.

  • Turns. After each write the server marks the folder as being written by an agent, for 15 seconds. Meanwhile Studio holds its saves and says so once (An agent is editing this model…). It takes in each change of the agent as before, keeping your edits on top, and saves them when the agent pauses. A reload or a closed tab meanwhile does not lose them: Studio writes them at once, merged with the agent's, and keeps them in the browser until the folder has them, to merge them in when the model is opened next.
  • Merges. When one side writes after the other changed the folder, the two changes are merged element by element and field by field: a new element on each side, different fields of one element, a view renamed here and a relation added there all stay, and so do the elements each side put on one view and a new order of the views (a folder moved up) on one side. Where both changed the same value, or both reordered the views, what is in the folder is kept, and a notice in Studio (or the agent's tool result) names it. Moves and sizes merge without a word. A file that does not read as a model, such as one git left with conflict markers, is never merged over: nothing is written until it is fixed.
  • Undo. Undo and Redo go on working as the agent's changes come in: they take back and give back your own steps, on the model with the agent's changes in it, and never take one of those back. Where a step changed a value the agent has changed since, the agent's value stays, and a notice names it.

The server keeps where the run stands in .radical/forge-run.json, which is how Studio's Forge button knows.

Single .radical files, actions that drive Studio's canvas (switching the view, focusing an element), loading a milestone over the current model, clearing the whole model, and remote HTTP connections are not supported.

Command line

radical check checks a Markdown folder with the rules the Inspector runs, so CI can fail when the model is broken or a test it names fails. It reads the files and never changes the model. Build it from a clone with Node.js 20.11 or newer: 

npm install
npm run build -w @radicaltools/cli
node apps/cli/dist/index.js check path/to/my-model --report reports

It checks the folder (files that read, ids, references), the metamodel (the Validation list of the metamodel editor) and completeness (see Rules and checks).

OptionWhat it does
[folder]The model folder. Default: the working directory.
--config <file>Rule settings. Default: check.json in the model folder, when there is one.
--format text|json|githubPlain text (default), JSON, or GitHub Actions annotations.
--report <path>A test report (Vitest or Jest JSON, Playwright JSON, JUnit XML), or a directory of them; repeat for more. The tests that scenarios and fitness functions name in their Tests property are looked up in it. The test cases it reads are kept in .radical/test-results.json, where the Inspector finds them.
--evidence <file>With --report: writes what the reports say about each scenario, fitness function, requirement and ADR as JSON.
--ratchetLowers each max in the config to the count found now and writes the config back. It never raises one.
--verboseLists every warning, not the first five of each rule.
--list-rulesLists the rules and their default severity, and the metrics goals can set.
radical --versionPrints the version, with the commit it was built from when the build is not a release (0.3.0+1a2b3c4).

Exit status: 0 no errors (warnings allowed), 1 errors, 2 the check could not run.

check.json sets a rule by its id, or one kind of metamodel issue by metamodel/<code>, to error, warning or off. With max, up to that many findings pass as warnings and one more fails the check, so an existing model can adopt a rule before every gap is closed:

{
  "rules": {
    "adr-incomplete": "off",
    "requirement-without-scenario": { "severity": "error", "max": 104 }
  }
}

goals sets the least share of a metric, in percent: requirements with a scenario, accepted ADRs with a fitness function, and with --report requirements and ADRs verified, scenarios passing, tests the model names, … (--list-rules lists them). A metric below its goal is a finding of goal-unmet, an error unless the config sets that rule otherwise. Where max says how many gaps a rule may have, a goal says how much must be covered, so it keeps its meaning as the model grows. The Inspector's Settings edit both.

{
  "goals": {
    "requirements-with-scenario": { "min": 85 },
    "requirements-verified": { "min": 80 }
  }
}

This repository checks its own architecture model this way on every push.

File formats

.radical (JSON)

One file: nodes, relations, sequences, views (with per-view positions, camera and layoutConstraints — the alignments and grids), defaultLayoutConstraints (alignments on the model's layout, made on the All elements canvas of earlier versions), defaultEdgeStyle (curved or orthogonal lines), snapshots (milestones), presentations, the metamodel and Hub template records. Older .c4.json files open unchanged.

Markdown folder

my-model/
├─ radical.md                 # manifest
├─ nodes/
│  ├─ retail-customer.md      # one element = one file
│  └─ core-banking-platform/  # an element with children becomes a directory
│     ├─ _index.md            # the element itself
│     └─ payments-service/
│        ├─ _index.md
│        └─ fx-engine.md
├─ relations.json
├─ views.json · sequences.json · snapshots.json · presentations.json
├─ metamodel.json · hubTemplates.json
├─ _layout.json               # positions, camera, line style & All-elements alignments — the only noisy file
├─ check.json                 # optional: rule settings for radical check and the Inspector
└─ .radical/                  # editor state, kept out of Git by its own .gitignore
   ├─ selection.json          # what is selected in Studio, for the MCP server
   ├─ forge-run.json          # where an agent's Forge run stands
   ├─ agent-activity.json     # an agent is writing: Studio holds its saves until it pauses
   └─ test-results.json       # test cases from the last radical check --report

Each .md has YAML front-matter (id, type, label, then the element's properties, sorted) and the description as body. Hierarchy is the directory tree. Output is deterministic — sorted keys, stable file names — so Git diffs show what changed and nothing else. Edit the files by hand, or let an agent edit them through the MCP server; the app picks them up, and merges what you have not saved yet into them.

A JSON file that cannot be read (a trailing comma, Git conflict markers) is not taken for an empty one: Studio says which file it is, keeps the model that was on screen, and saves nothing to the folder until the file reads again. The MCP server refuses such a folder with the same message.

Back and forward. Every change of place (another view, perspective, Inspector tab or selected element) adds the route to the window's history. ‹ and › at the left of the toolbar go back and forward and name the place they lead to; the clock next to them lists the places of this window, newest first, the current one marked, and goes to the one you pick. Alt+← / Alt+→ (⌘+[ / ⌘+] on a Mac), the browser's own Back and Forward, and in the desktop app a mouse's side buttons do the same.

A model kept in a file or a Markdown folder loads a moment after Studio opens; the link is applied once it has. A browser folder that needs Reconnect… keeps the link until you reconnect it. File and folder paths only open in the desktop app; in the browser a folder is identified by its id, so its links work in the browser that opened it.
