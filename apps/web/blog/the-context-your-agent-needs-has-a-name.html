The context your agent needs has a name. It’s the architecture model.

Tomasz Zajac · 28 October 2026 · 7 min read

For twenty years I’ve watched the architecture model be a nice-to-have. We drew it when an audit was coming or compliance asked, usually in draw.io or Confluence, and by the second release it was out of date. Nobody paid a price for that, since the code shipped anyway, so it never became a must-have.

Coding agents are changing that, which I didn’t see coming.

“Context” is the architecture model

People who never worked on architecture are rediscovering it, though they don’t call it that. They call it context: a folder of Markdown files the agent reads before it writes code, with the conventions, the components and the house rules. It’s a good instinct and I’m not mocking it. But it’s a reinvention, and a partial one. Describing a system so that someone who wasn’t in the room can act on it is a forty-year-old discipline. Zachman’s framework is from 1987, Kruchten’s 4+1 views from 1995, ISO 42010 made viewpoints a standard, and TOGAF has taught the business-to-technology chain since the nineties. Before writing your own in a folder of notes, check what’s already been worked out. The gaps in your notes are where the agent will guess.

So yes: the context is the architecture model. Once you call it that, most of what follows is fairly obvious.

Why the harness isn’t optional

I’m not a sceptic about AI in delivery. An agent integrates a third-party API faster than I can read its docs, and I want that. But the speed comes with two properties an architect has to take seriously. The agent guesses: where the input leaves a gap, it fills it with whatever is most probable, which often isn’t what you meant. And it isn’t deterministic, so the same brief gets you a different design on Tuesday than on Monday. I don’t expect the next model release to fix either, because that’s how language models work.

Without a harness, those two properties turn into risk that shows up later: a system with three ways of doing the same thing and nobody who can tell you which one was intended. With one, they give you drafts to review, and reviewing a draft beats starting from a blank page.

The “AI-based SDLC” is the SDLC

There’s a lot of writing now about an AI-native software lifecycle. Read the details and it’s the ordinary lifecycle done properly: testable requirements, a model of the system, design before code, automated verification, and a short loop between making a change and knowing whether it was right. We knew all this. We skipped it because people were slow enough that skipping it was survivable, and agents removed that slack. When the volume of change isn’t limited by typing speed any more, modelling and fast feedback stop being optional.

What the model is, and what it is not

It isn’t a draw.io diagram. It isn’t C4 either, although C4 is part of it. C4 shows the structure of the software, and structure is one viewpoint. Why the structure looks the way it does, what it has to guarantee, which business process it serves: you won’t find any of that in a container diagram.

To get the full picture you go back to basics, which for me means Zachman’s rows: conceptual, logical, physical. TOGAF cuts it differently, into business, data, application and technology architecture, but both agree on the point that matters here. The business layer is part of the architecture, not an input to it. Conceptual covers that business side (what the system is for, its requirements, the processes it supports), logical is how the parts connect regardless of technology, and physical is where it runs. Requirements and processes were always architecture; we just filed them somewhere else.

Your model, not a standard one

Every company should define its own model and adjust it as it learns. Borrow from the standards, don’t adopt them whole. ArchiMate is serious work, but for most organisations it’s over-engineered: some sixty element types, most of which nobody will use, and a learning curve that kills adoption early. TOGAF’s ADM is a method for an enterprise architecture function with a budget, and a product team of forty people isn’t that. UML and SysML can notate almost anything, which in practice means nothing in particular. I’d take a small metamodel your team actually fills in over a complete one that stays empty.

My minimal set follows the three layers above. None of the building blocks is new, and each comes from somewhere older than the current wave of tooling.

Needs

It starts with the needs: the brief, the workshop notes, the ticket as the customer wrote it. I keep them as they came, because the raw words are evidence; ISO 29148 separates stakeholder needs from requirements for the same reason. Months later, when someone disputes a requirement, the need tells you whether anyone actually asked for it.

Requirements

Derived from the needs and written in EARS, so each one has a testable form. EARS came out of Rolls-Royce engine control software in 2009 and fits on a page: when, while or if something happens, the system shall do something. It sounds bureaucratic until you hand an agent a requirement that just says “fast”.

Scenarios

Gherkin, each scenario verifying a requirement. Given/when/then comes from behaviour-driven development, but the part I care about is the link: a scenario names the tests that check it, so a build can tell you whether a requirement is verified.

Mockups

Only where a scenario involves a screen, and a rough one is enough. Otherwise the agent designs the screen and you find out what it chose when the pull request arrives.

Processes

BPMN has drawn these since 2004: work across people and systems, in order, including the point where the system takes over. Requirements give you the system’s obligations one by one. The process shows whether, put together, they actually get a customer from the first step to the last.

The domain model

Entities, their attributes and the relations between them, in the domain-driven design sense. It’s the vocabulary everything else uses, so when a requirement says order and a component stores an order, it’s the same entity with the same attributes. Leave it out and you’ll see a slightly different vocabulary in every file an agent touches.

State machines

One per entity whose lifecycle matters, as Harel statecharts (1987). A status column tells you which states exist, not which transitions are allowed or what triggers them, and that’s usually what breaks when a new feature touches the status.

The C4 elements

The structure. Yes, C4: Simon Brown’s answer to how much UML a team really needs for structure. People, systems, containers and components cover the logical and physical layers, and most teams draw them already.

Decision records

In the form Michael Nygard described in 2011: status, context, decision, consequences. Code records what was chosen, never why. An agent that can’t see the decision will happily propose the rejected option again, with good arguments.

Fitness functions

From Building Evolutionary Architectures: automated checks that an architectural property still holds, like a dependency that mustn’t exist or a response time the system has to keep. Without them a decision tends to become a wish the first time someone, person or agent, is under pressure.

That set covers most systems I’ve worked on, and it’s enough for an agent to do real work with.

What makes it a model rather than a pile of documents is how the blocks relate. A requirement derives from a need, a scenario verifies it, a component satisfies it. A decision constrains the component and a fitness function checks the decision still holds. A state machine is the lifecycle of one entity, and a process moves entities through those states. That graph is the model, and diagrams, tables and documents are views of it. Which is why you edit the graph, not the picture; edit only the diagram and you’re back in draw.io.

How people and agents use it

People and agents use it the same way. They read it first, to learn the constraints and the current state before changing anything. They write it when modelling a new system from a brief, or an old one from code nobody documented. And they read it again afterwards, to check that what got built matches what was decided.

Humans have always been bad at the reading part, because reading the model is slower than asking a colleague. An agent has no colleague to ask, so it reads what’s there, all of it. That makes the model worth more than it used to be, and its gaps cost more.

What you get

A process in which AI can be used at scale, which is different from vibe coding. Vibe coding produces a pull request that engineering then reviews for two days, or approves by default because nobody has two days, and neither holds up as the volume grows. What you can defend in front of your CTO and your auditor is a model the agent reads before it writes, plus a check afterwards that compares the result with the model.
