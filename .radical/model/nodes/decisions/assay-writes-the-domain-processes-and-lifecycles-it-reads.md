Entities drawn by the agent with no table facts: nothing to check a foreign key against. 3. A domain per container or per database: rejected for one per system. 4. Behaviour without tests left out, as before: the model then hides what the code does. 5. Tests written whole by the agent: their assertions would be unchecked claims; a pending test says only what is to be checked."
consequences: "A model found in the code has its data, its processes and the lifecycles of what it keeps, each with its evidence in .radical/assay/run.json, and every behaviour the agent found has a scenario, verified or not. Processes and state machines are the agent's reading of the code, marked inferred, which a person reviews in the model rather than one question at a time. A pending test is a skeleton the team fills in: radical check counts it skipped, so the scenario shows unverified until someone writes its body. The ORM readers match the common forms of each framework, not every one; an entity of a table no reader sees can still rest on code the agent quotes, as an inferred element. Access files are read with mdb-reader, a runtime dependency of the MCP server only (loaded when a run meets one): the CLI keeps no runtime dependency and notes the Access files it does not read."
context: "Radical Assay found the C4 model in the code (ADR Radical Assay), the screens of a running application (ADR Assay explores the running application) and the needs and decisions documents state, and turned tests into requirements with scenarios. A domain model, processes, state machines and the behaviour no test checks were left to the agent, with no facts to rest on, and runs on legacy code (three VB6 repositories with no test at all) came back with C4 only. The maintainer, 2026-11-07 (translated from Polish): \"I have C4 ... and what about the rest? scenarios, processes and so on?\" Asked one by one, they chose all four stages in one pull request; scenarios from code with a test skeleton where the repository has a test framework; one domain per system, its entities from the tables; processes and state machines written directly as inferred rather than proposed."
date: "2026-11-07"
decision: "The readers record more facts: each table's columns and the tables its foreign keys reference (SQL CREATE TABLE and ALTER TABLE, and ORM classes: JPA, Entity Framework Core, Django, SQLAlchemy, TypeORM, Prisma); the values a status or state takes (an enum named for one, a CHECK … IN list, a MySQL ENUM, a TypeScript union) with the lines that set each value; entry points (HTTP routes declared in code, VB6 forms and menus, scheduled jobs, message handlers); and the test framework a unit's manifest names. A plan gains entities, processes and state machines. Entities are observed, each on its table facts, in a domain per system that the plan names; part-of and references join two entities only where a foreign key of one's tables references the other's; the server relates every element of the run built from a unit whose code names a table to that table's entity (realises). Processes and state machines are written directly as inferred, not proposed: each step cites the entry point, explored path or code it rests on, with the person or element that performs it and the mockups that illustrate it; a state machine is the lifecycle of its entity, its states the values of a state fact (or code quoted), each transition citing the code that makes it, and the elements whose units set the values implement it. A requirement's scenario may rest on code the agent quotes when no test or explored path shows it; accepted, the scenario is written, and where the unit building the element that satisfies it has a test framework (Vitest, Jest, Mocha, JUnit, pytest, xUnit, NUnit, MSTest) the server writes a pending test for it into that repository (tests/assay/, src/test/java/assay/ or the test project's Assay/ folder) and binds it to the scenario in the repository's .radical/radical.json. A VB6 unit, or one with no test framework, gets the scenario only."
