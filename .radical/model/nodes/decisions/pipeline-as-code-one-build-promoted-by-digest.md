type: "adr"
label: "Pipeline as code, one build promoted by digest"
alternatives: |
  1. A build per environment, made reproducible: needed where environments cannot share an artifact, at the price of keeping every build reproducible.
  2. A build per environment without that: what staging tested is not what production runs (Humble, Farley: Continuous Delivery).
  3. Promotion by a mutable tag (latest, staging): the tag can move between the test and the deploy.
concern: "ci-cd-pipeline"
consequences: |
  • What production runs is, byte for byte, what staging tested.
  • Configuration has to live outside the image (environment variables, mounted files), so that one image fits every environment; a setting baked in at build time per environment is no longer possible.
  • Images stay in the registry as long as they may be promoted or rolled back to.
  • Workflows are tied together by job outputs and a reusable deploy workflow; a deploy started by hand names a digest.
  • The pipeline's own time, success rate and reruns are measured and judged like any other quality of the element, so a slow or flaky pipeline becomes a finding rather than a complaint.
context: "This element is built, checked and deployed by machine many times a day, and the pipeline that does it is code with failures of its own. The forces: a pipeline clicked together in a web UI cannot be reviewed, versioned or rebuilt; a check that runs only on a developer's machine is skipped the day it matters, while one that runs only in CI is slow to learn from; a rebuild for each environment ships something other than what was tested, as dependencies, base images and tools move between builds; long-lived cloud keys in CI secrets are among the credentials most often stolen from pipelines, readable by every workflow that may use them and valid from anywhere once leaked; a slow pipeline is worked around (changes batched, merges made without waiting), and one that fails at random teaches everyone to press Re-run; caches and parallel jobs buy time but go stale or race; and two deploys to one environment at once leave it in neither version. Neighbouring packs own the rest: the main branch's ruleset (no direct pushes, no force pushes, the approvals) in the Code review and branching pack; the test run and its own time limit in the Test strategy pack, the static checks and theirs in the Code quality gate pack; rollout, rollback and how often the element is released in the Deployment and rollback pack; which environments exist, and the gate that production gets the digest staging tested, in the Infrastructure pack; version numbers and who approves a release in the Release and versioning pack; pinning actions by commit SHA, provenance and SBOMs in the Software supply chain pack; the running element's own credentials in the Secrets pack; and the DORA delivery metrics in the Delivery metrics pack."
date: "2026-11-24"
decision: "A change merged to main is built once: the job build of deliver.yml builds the image with docker/build-push-action, pushes it to ghcr.io/our-org/shop/order-api tagged with the commit SHA, and passes its sha256 digest on as a job output. Every deploy job, for staging and for production, calls the reusable workflow deploy.yml with that digest and deploys image@digest; no deploy job builds anything, and what differs between environments is configuration read at start, never the image. That production gets the digest staging tested is checked by the Infrastructure pack's promotion gate; signing, provenance and SBOMs of the image are the Software supply chain pack's. The pipeline is code: every workflow lives under .github/workflows in the element's repository and changes through pull requests like any other code, nothing is configured by hand in the web UI, and steps that more than one workflow or repository needs live in reusable workflows (on: workflow_call) instead of being copied; actionlint checks every workflow on every pull request. The pull-request workflow ci.yml ends in a gate job named ci that needs every other job of the workflow and fails unless all of them succeeded, because GitHub reports a skipped job as a success. The main branch's ruleset, which the Code review and branching pack keeps, requires ci beside the checks the Code quality gate and Test strategy packs name, so the gate always runs on the CI platform's runners, whatever ran before on a developer's machine. Where the pipeline first runs: one command, run locally and mirrored in CI. A pull request's runs are cancelled when a newer commit is pushed to it (concurrency with cancel-in-progress), while deploys to one environment queue in a concurrency group of that environment and are never cancelled halfway. Dependencies are cached by their lockfile (setup-node's npm cache, BuildKit's GitHub Actions cache for image layers), and jobs that do not depend on each other run in parallel. The pipeline is held to targets over the last 30 days: all the checks of a pull-request commit finish within 15 minutes at the 90th percentile, the runs of at least 90 % of the commits on main succeed, and at most 5 % of runs need a second attempt. CI platform: GitHub Actions. On GitHub Actions radical sense github-actions measures those figures every night; on another platform a job of the team's own writes the same figures for radical sense json, until an adapter for the platform is contributed to radical sense by pull request. Cloud credentials: OIDC federation, no stored keys."
