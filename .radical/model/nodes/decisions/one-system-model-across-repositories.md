label: "One system model across repositories"
alternatives: "A model in every repository, edited together by one agent: several pull requests of the model to agree on, and the wanted state stays scattered. Federation between the systems: the trial above. One repository for everything: solves this, and is not what many organisations have. A --scope flag or a partition in the model: each caller would have to name its part, while the repository already says what it builds."
consequences: "One change of the system is one pull request of the model, with one state to reach. A repository's gate stays deterministic and its own. The model's rules run in the model's repository, on the whole model. A check of the whole system reads the reports of every repository. A team no longer has a model and versions of its own, and reviews its part of the shared model. radical check --from-ci and git hooks in a checkout read the model's repository, not the code's, so a code repository passes --report. Implementation across repositories needs an order, which the model gives by its relations and the pipeline carries out."
context: "A system built in several repositories had a model in each, joined by federation, and an agent changed only its own. A trial on the SDLC demo showed the price: one feature that crossed two repositories took nine tickets, five pull requests of the model and two of code, because what one agent knew reached the other as a ticket, and gaps surfaced one repository at a time. A repository is where code is deployed and who owns it. It is no boundary for what an agent sees or proposes. A model in a repository of its own was held back by radical check and radical sense run, which judge the whole model they are given: in a code repository they measured other repositories' elements and counted their requirements towards the goals."
date: "2026-11-05"
decision: "The repositories of one system share one model, in a repository of its own. A code repository names it in .radical/radical.json (\"model\": { \"repo\": \"<address>\", \"ref\": \"<branch>\" }) and has it checked out at .radical/model, with the checkout's own git. That model belongs to the repository around .radical/: .radical/radical.json is found past the checkout's .git. There, radical check and radical sense run judge the repository's part: the elements it builds, by the nearest mapped ancestor, the requirements they satisfy and what those derive from, the state machines they implement or that are the lifecycle of the entities they realise, with everything in them, those entities, the scenarios of those requirements and machines, the ADRs that constrain the elements and the fitness functions of those. radical diff --part lists what changed in that part since a commit, as the part is now and as it was then: what the repository has left to build. Everything else is read, as another model's elements are, and nothing is found about it, measured for it or counted towards a goal. A repository that names no model is judged whole, as before. Federation stays for boundaries between organisations, such as a company's standards or a vendor."
status: "accepted"
