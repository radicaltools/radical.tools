decision: |
  Build Radical Assay as a member of the Radical family: it finds the model in an existing system, as an assay finds what an ore is made of. The family reads as one workshop: Assay finds the model in existing code, Forge builds a model from a brief, Crucible searches for where the code breaks it, Hallmark stamps in CI how much of it is proven.
  It runs Forge's stages in reverse order, from what the code states to what it can only suggest: (1) C4 from workspaces, package manifests and their dependencies, imports, Dockerfiles, compose, Kubernetes and Terraform files, OpenAPI and AsyncAPI descriptions; (2) the domain model from database schemas, migrations, ORM mappings and types; (3) state machines from status enums and the transitions the code makes; (4) processes from handlers, jobs, queues and sagas; (5) scenarios from the tests, each bound to its tests in .radical/radical.json verifies; (6) EARS requirements from the scenarios and the code; (7) needs and ADRs from READMEs, the git history and configuration.
  Facts are read by deterministic extractors, in a workspace of their own that the radical CLI and the MCP server both call, in the manner of sensors: they write the facts with their evidence (repository, file and line) into .radical/ and change nothing in the model. An agent interprets them: it names, groups and infers, and writes the model with the shared tool catalogue. Every element Assay writes cites its evidence and has a confidence: observed (read from a fact), inferred (concluded from several) or a hypothesis (intent no file states). The evidence and the confidence are kept in the repository's .radical/, not in the model, which holds nothing of the repository (ADR The model folder holds nothing of the repository). The agent does not write the model element by element: it hands the server a plan (assay_apply), the elements, relations, scenarios and requirements it proposes, each citing the facts it rests on by id and saying which repository it belongs to. The server checks the plan (every cited fact exists, the types and relations follow the metamodel, an observed element cites a fact that states it), writes what is observed or inferred, and returns the hypotheses (needs, ADRs, requirements) as proposals the user accepts, changes or rejects one by one, with the proposal flow of ADR Forge asks before each refinement; only accepted ones are written. A run also writes .radical/radical.json: implements for the C4 elements it found, verifies for the scenarios, so Hallmark, sensors, Crucible and Studio know at once where each element lives.
  The first stage splits the work: later stages run per repository and per container, in parallel, so a large system does not have to fit in one context.
  Several repositories. A run takes one directory or several local directories, each a repository already cloned (a parent directory stands for every repository directly inside it, or up to three levels down when it holds nothing but folders; a directory that is no repository and holds none is a folder of code in its own right, read and left as it was, its facts kept in the central repository's .radical/assay/facts/), or a .zip file of code, which the server unpacks into the central repository's .radical/assay/unpacked/ without the .git folders it may hold, so that no git configuration of an archive ever runs; Assay fetches and clones no repository. The extractors run on each repository on its own. A linking step then matches facts across repositories into relations between their elements: an API one repository describes or serves and another calls (an OpenAPI path, a generated client, a base URL in configuration), a topic or queue one publishes to and another consumes, a package one publishes and another depends on, a database or service name in deployment files; each such relation cites the evidence on both sides, and a match by name alone is a hypothesis. The user picks the shape of the result when the run starts: federated, where every repository gets its own model in its .radical/model, a relation across repositories goes into the consumer's model, the consumer's deps.json names the provider's model, and an optional landscape directory gets a model with no elements of its own, only views over the others (as radical federation fetch composes them); or central, where one model holds the whole landscape and each repository's .radical/radical.json implements declares the elements it holds, the nearest declared element owning everything below it, and names the central model it maps to. The facts and the linking are the same for both; only the writing differs. The first version writes the central shape only, the shape of a repository that holds the landscape's model beside repositories of code: the MCP server is bound to the central model's folder, the code repositories are given as local directories, and each gets a .radical/radical.json whose implements name the central model's elements it builds, whose verifies bind its tests to the central model's scenarios, and whose model entry names the central model's repository by its address, as ADR One system model across repositories has a repository name the model of its system. The federated shape comes later.
  Readers of every stack (2026-11-03). Units are found wherever they are in a repository, not only at its root: npm, Maven, Gradle, Go (with modules or before them), .NET projects and solutions, Python, VB6 projects and groups (their project references and the COM binaries they reference), and a folder with a Dockerfile no manifest claims; each is an app, a library or tests. How the system runs is read from docker-compose files, Kubernetes manifests and .NET Aspire AppHosts (services, what each references, the database, queue, cache or observability image it runs); its calls from OpenAPI paths, gRPC services in .proto files with the units that register and call them, and addresses (a URL or host:port naming another unit or service, a load-balanced route, a host given as a default, a variable named for a service, a local port only one unit listens on); its data from connection strings (ADO and OLE DB, ODBC, JDBC, .NET, PDO, Go's MySQL driver, database URLs) and the tables its SQL names. A database runs on the deployed service its server names. Quality is measured by a bench (packages/assay/bench): pinned public repositories of several stacks and ages, with the units and calls a person wrote down from each project's documentation, tuned on six (microservices-demo, spring-petclinic-microservices, eShopOnWeb, VBCorLib, VBCCR, a VB6 attendance system) and checked on three written down before the extractor first ran on them (robot-shop, dotnet/eShop, and Sock Shop's nine repositories).
  Code in any language. Where no extractor reads a repository (VB6, COBOL, Delphi, PowerBuilder, or a stack it does not know yet), the agent reads the code itself and cites it: the repository, the file, the lines and the text it quotes from them. The server checks that the quoted text is in those lines of that file, ignoring how it is spaced; a citation it finds is evidence for an inferred element, relation or requirement, never for an observed one, which only a fact can back. An element built from no unit names the folders it is built in, which the server checks exist, for the repository's .radical/radical.json. The citations are kept with the rest of the evidence in .radical/assay/run.json. Extractors for such stacks (a VB6 project's .vbp and .vbg files, its COM references and its connection strings first) come after, and turn what is cited today into facts.
  On a repository or set of repositories that already has a model, Assay does not write elements: it lists where the facts and the model differ (a container or dependency in the code that the model lacks, a relation in the model that no import or call backs, an entity the schema dropped, a relation across repositories with no fact on either side), which a fitness function can run in CI as drift.
  All of Assay is available over MCP, the way Forge is (ADR Forge on the agent's model): assay_* tools of the MCP server start a run on the directories and the shape the user gives, run the extractors and the linking step, return the facts per repository and container, hand the agent each stage's prompt, keep the run, and carry the proposals the agent shows the user (as forge_propose_refinement and forge_answer_refinement do). In the central shape it writes the folder it is bound to and every code repository's .radical/radical.json; in the federated shape, later, it will write the models of the run's repositories, not only the folder it is bound to. The CLI offers the deterministic part (radical assay extract, and the drift report later) for scripts and CI. Studio in a browser cannot read a repository, so it has no Assay wizard; showing an agent's Assay run and its proposals in Studio, as it shows an agent's Forge run, comes later.
  Its quality is measured against this repository's own model, kept by hand: Assay runs on a copy without .radical/model and the result is compared element by element (precision and recall of containers, relations, scenarios and test bindings); for several repositories, against a fixture of three small repositories with code kept in the tests (a library, a service describing its API in OpenAPI, and a consumer of both), whose expected model is written by hand.
  The first version covers stage 1 (C4 from the units, deployments, calls and data of every stack above), stage 5 (scenarios from the tests the test reports name, grouped by the agent) with, for each scenario, the requirement it verifies, inferred from the tests and proposed as a hypothesis for the user to accept, so that every scenario verifies something and each requirement is satisfied by the element whose code the tests exercise; the linking step (packages and project references, OpenAPI paths, gRPC, addresses, deployments, data); documents as sources of hypotheses; the central shape over one or several code repositories; the assay_* MCP tools with the plan; and the mapping in .radical/radical.json, implements and verifies. The federated shape and drift come next, then the domain model, state machines and processes, and more ecosystems (message topics, GraphQL, AsyncAPI, Terraform, PHP, Ruby, Rust). The need, the requirements and the components of Assay itself come into this model with that first version (Hallmark asks each need for a requirement and each requirement for what satisfies it).
  Sources besides the code (2026-11-06). What a system's people wrote about it is evidence too, of intent rather than of what runs: documentation pages, a wiki, an exported Confluence space, README files and docs folders. A run takes sources besides its code, at its start or later (assay_add_sources): a folder, a .zip file or a public http(s) link. The server keeps a text copy of each document in the central repository's .radical/assay/sources/ (Markdown, text, HTML turned into Markdown, a PDF's text, and text formats such as YAML, JSON, XML and SQL), so that a citation of it can be checked when it is made and read again later, and lists each as a document fact with its title and headings; the README files, docs folders and ADR records of the code repositories are document facts too, cited where they are. A link is fetched once, a page at a time, with no credentials and from no loopback, link-local or private network address (unless the server runs with RADICAL_ASSAY_PRIVATE_LINKS=1), redirects checked one by one, within limits of size and time: a link that asks for a login is refused, and its pages are exported by the user (PDF, HTML or Markdown) into a folder or a .zip given instead. The agent cites a document as it cites code (assay_read gives it the lines of any file of the run's repositories and sources), and a document's citation backs only a hypothesis or an inferred claim, never an observed one: a document says what someone meant, not what the code does. Nothing a source or an archive names is trusted with where its files go: each copy is written inside its own folder, a name made only of dots is renamed, and a source given again replaces its earlier copy only when the new one is taken. From documents the plan may propose, besides requirements, needs and decisions (ADRs): each comes back as a proposal the user accepts, changes or rejects, and an accepted requirement derives from the need it names instead of the run's need Found in the code.
  A run reads the documents before the tests (2026-11-06, after an agent first ran Assay end to end): the needs a document states are answered first, so a requirement found in the tests derives from the need it serves rather than from Found in the code; a requirement a document states that no code builds is written satisfied by nothing, a gap the model shows rather than hides; a library several containers use is a component of a group of shared libraries, bundled into each, not a container, which C4 keeps for what runs.
