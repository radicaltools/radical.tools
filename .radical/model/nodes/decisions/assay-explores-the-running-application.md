label: "Assay explores the running application"
alternatives: "1. The agent's own browser (Claude in Chrome, a browser in the client): less code, but the server sees nothing, so no screen or step is evidence and no test can be written from it. 2. A crawler that follows links by itself: deterministic, but it stops at forms and sign-in. 3. Computer use on screenshots: works for any application, desktop too, but every claim is the agent's reading of a picture. 4. Desktop in the first version (the maintainer kept it for later). 5. Tests written by the agent rather than generated from the recorded steps (the steps are what the server saw; generation keeps the test to them)."
consequences: "A model found in the code gets the user's side: screens tied to the requirements they illustrate and the web application that presents them, and scenarios checked by tests that did not exist before, the most useful gain for an application with no tests of its interface. The tests are generated from what one run saw: they are a start the team keeps or rewrites, and they assume the data of the test database they were recorded on. Exploring needs the application running and a browser on the machine; the MCP server gains playwright-core as a runtime dependency, and the CI job that runs the unit tests installs Chromium. The refusal of destructive controls goes by their names, so a destructive action named otherwise is not caught: the test database is what keeps the user's data safe. Desktop applications wait for their drivers."
context: "Radical Assay finds the model in the code, the deployments, the tests and the documents (ADR Radical Assay). What a user sees and does, the screens and the paths through them, is in none of them as such: the routes and templates of a front end say little of which screen leads where, and a legacy application often has no test of its user interface at all. The application itself shows it when it runs. The maintainer, 2026-11-03 (translated from Polish): \"Can you add a stage in which you click through the application ... run locally?\" Asked one by one, they chose the Assay server to drive the browser, with the agent saying what to click; screens as mockups, the paths as requirements with scenarios for the user to accept and as Playwright tests in the application's repository; clicking freely on a test database except for what is plainly destructive; local addresses only; a pull request of its own; web applications first, though \"the application may be standalone\". On 2026-11-06 they asked for desktop applications too, then kept the first version to the web."
date: "2026-11-06"
decision: "Assay gains an Explore stage, over MCP only: the server opens an application running on this machine (localhost, a loopback address or a .localhost name) in a browser it drives with Playwright, the user's Chrome when there is one, else Playwright's Chromium, and an agent explores it step by step (assay_explore, assay_explore_act). The server, not the agent, sees the page: each screen comes back as its address, title, headings and the controls it can act on, each with a reference, its role and its accessible name, and the server keeps its screenshot in the central repository's .radical/assay/explore/. Every action the agent takes is a step of a named path: the control by its role and name, the action, the value typed, the screen it led to. The server refuses an address of another host, going back from a page that leads there, and a control whose name says it pays, buys, transfers money or deletes or closes an account; the user runs the application on a test database, so everything else may be clicked. Screens and paths are facts of the run, as the code's are: a plan names mockups built from screens, written as observed with their routes, presented by the web application, and joined by navigates-to in the order of a path, labelled with the action between them; a requirement's scenario may rest on a path instead of tests, and when the user accepts it the server writes the path as a Playwright test into the application's repository, in e2e/assay/, one file per path, each control found by its role and name and each screen checked by its heading or address, and binds the scenario to that test in the repository's .radical/radical.json. People and roles the sign-in screens show are inferred elements citing those screens. Desktop applications (Windows UI Automation, macOS accessibility, Electron, Java Swing) come later, with a driver per platform behind the same tools."
