Paths as properties of the elements in the model: puts the real system into the model, and one central model would hold every repository's folders. .radical/implementation.json or .radical/elements.json: radical.json is the name chosen for a central model's repositories, and the file may hold more of the repository later (its owner, its CI artifacts)."
consequences: "A sensor can be generic: it gets the folders to look in, so one OpenAPI or dependency sensor serves every repository. The mapping is data, checked against the model, and drifts no further than a warning. The model still holds no paths. A repository of a central model declares the elements it builds the same way. This repository's elements.mjs goes; its sensors read element.paths."
context: "A sensor measures an element of the model in the repository's code, so it must know where that element is built: which folders hold the CLI, the Payments API or a component. The model says nothing of it, on purpose (ADR Fitness functions measure each element their decision constrains): mapping the model onto the real system is the repository's. Each repository wrote it in a script of its own sensors (this one in .radical/sensors/elements.mjs), so no sensor could be generic, and no other tool (Crucible, check, the MCP server, Studio) could ask where an element is."
date: "2026-11-02"
decision: "A repository says which elements of the model it builds, and where, in .radical/radical.json: { \"implements\": [{ \"element\": \"<id>\", \"name\": \"<the element's name, for people>\", \"paths\": [\"apps/cli\"] }] }, paths from the repository's root. An element may be the model's own or another model's of its federation. An element without an entry is built where its nearest ancestor with one is, so a component inherits its container's paths and overrides them with its own. radical sense run gives a repository's sensor the element's paths in --context (element.paths). radical check warns about an entry whose element the model lacks, whose name differs from the element's, or whose path the repository lacks, and setup --status shows how many elements it maps. radical implement <element> --path <folder> writes an entry, finding the element by its id or name, and Studio's card shows where an element is built, or the command that maps it. The file is the repository's, not a tool's: the MCP server, Crucible and the tests a change touches read it next."
