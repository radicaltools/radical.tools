label: "Calm drags pin what they drop"
alternatives: "Keep the physics during drags but damp it or cap how many elements it may move (still moves what the user did not touch, and does not stop the pull-back after the drop); pin without calm drags (the drag itself still shakes the diagram); honour pins in Smart Layout (fixed positions inside ELK and the annealer: a core-IP change that needs its own benchmark; left open); keep pins through Smart Layout at the places it chose (pins that no longer mean \"where I put it\", and never cleared); Alt for the push drag (Alt is the default connection modifier)."
consequences: "Arranging by hand no longer disturbs the rest of a diagram, and a hand-placed element stays put when the physics later runs (a small diagram relaxing, an expand). Pins accumulate with every drop until the next Smart Layout; meanwhile the physics has fewer elements it may move. A drop never leaves an overlap with a pinned element (amended 2026-10-09: the first version left pinned elements where they were, so dropping onto an element dragged earlier left the two on top of each other for good, which users read as the physics switching off). Unpinning is per element (the pin on a selected element), per view (its properties) or by id for agents (remove_alignment). A click is not a drag: React Flow reports one as a drag, so a calm drag starts only once the element moves. Smart Layout output is unchanged; it only clears the pins. Amended 2026-10-13: a drag is one undo step of its own (the first version gave it none, so Undo did nothing after a drag, or took back the drag together with the edit before it). The store keeps the model as it was when the drag began and makes the step when the drag ends having moved something; undo puts back what was moved or pushed and takes off the pins the drop set. Not in Viewer or Presenter, where nothing that is moved is kept. Amended 2026-10-14 after exploratory runs 13 to 24: from 150 nodes up a Cmd/Ctrl drag is a calm one as well (see \"A laid-out diagram stands\"). A drag is the same whatever React Flow hands over: when the grabbed element's container is selected too, React Flow drags the container and leaves the grabbed one out, and after a box select it drags the selection's frame (onSelectionDrag*); both were neither saved nor an undo step. The canvas takes the first element React Flow actually drags as the one held. The arrow keys no longer move elements (React Flow's keyboard moves changed the screen only)."
context: "On large canvases with many layout constraints, a drag ran the live WebCoLa physics: dozens of other elements moved during the drag, kept moving for seconds after the drop (measured on this repo's architecture model, 499 nodes: 44 of 45 shown elements moved, the farthest by 27 000 px, still moving 4 s after the drop), and the dropped element was pulled back from where the user put it. Drags are how users arrange a diagram by hand."
date: "2026-10-08"
decision: "A drag on the canvas is calm by default: only the dragged element moves (with the other selected elements React Flow drags along, and the members of its rows and columns, which follow it across the line so the line holds; an ordered line pushes the next member ahead). The physics does not run during the drag. On the drop, elements the moved ones now cover (drawn boxes closer than 24 px) are pushed clear whole, along the axis of least overlap, and whatever they then cover in turn; pinned elements are pushed too and stay pinned where they land (the pin keeps the physics off an element, not the user's drop); an element that lines hold on both axes stays, and the element covering it moves off it instead; a container that grew pushes its neighbours the same way; nothing else moves. The dropped elements are pinned: a PinConstraint (LayoutConstraint type 'pin', one per canvas) that the live physics holds like a frozen node, for good. Cmd/Ctrl held at the start of a drag (a key the connection modifier does not use) runs the physics as before. Pins bind the live physics only: a layout of the whole canvas (Smart Layout, the tree layout, the MCP server's smart_layout), run on purpose, places every element anew and removes the canvas's pins in the same undo step; when it keeps the current layout, they stay. This amends \"User alignments bind layout\" (every engine honours every constraint kind) for pins."
status: "accepted"
