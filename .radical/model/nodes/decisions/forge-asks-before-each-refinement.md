label: "Forge asks before each refinement"
alternatives: "Keep the list after the stage (the owner asked to be asked as things are found). Ask with a free-text question and let the AI write afterwards (what is applied could differ from what was shown). Accept part of a proposal change by change (a link to an element left out would fail, and a half-applied finding is harder to read than a reply asking for less). MCP elicitation to ask from the server (not every client supports it; the agent asks in its own chat instead)."
consequences: "The user decides on each finding while the stage still has it in hand, sees exactly what will be written, and can steer it with a reply (a name, a narrower scope). A stage takes longer and needs the user present while it runs; a stage with many findings asks many questions, so the prompt asks for one proposal per finding with everything it needs. A proposal applies whole: the user cannot accept half of one. The guard makes the rule hold whatever the AI does, at the cost of refusing a write a stage could have made without asking (an existing element's harmless correction)."
context: "ADR Forge stages refine earlier stages let every stage from the domain model on add what an earlier stage left out right away and asked for consent after the stage, as a list to keep or reject. The owner found that too late and too coarse: by the end of a stage a refinement had already shaped the rest of the stage, the list showed only a type and a label, and taking one back could leave the stage's own elements pointing at nothing. They asked Forge to ask every time it finds something an earlier stage should get, showing exactly what it would add, and to ask for their opinion."
date: "2026-10-19"
decision: "A stage no longer writes to earlier stages itself; it proposes. In Studio the AI gets one more tool, propose_refinement, and over MCP the agent gets forge_propose_refinement and forge_answer_refinement. A proposal is a reason (what the stage found) and the exact changes as calls of add_node, add_relation, update_node, update_relation and move_node (no deletions). @radical/common/ai/forge/proposals.ts checks it, describes it field by field with old and new values and the elements' labels (describeProposal), and applies it all or nothing (applyProposal). Studio pauses the stage and shows the proposal under the progress; the user adds it or not and may write a reply, which goes back to the AI with the answer. Over MCP forge_propose_refinement keeps the proposal and returns the text to show; the agent asks the user and calls forge_answer_refinement with their answer and reply; only then is it applied. While a stage runs, refinementGuard refuses a direct write to an earlier stage (a node of a type the stage does not make, a change, move or deletion of an element that was there before the stage or came from a proposal, a link between two such elements) with a pointer to the proposal tool. The step bar shows ✎N for the refinements accepted, amber while a proposal waits; Regenerate still takes back the accepted refinements with the stage. The keep-or-reject list after the stage and forge_reject_refinements are gone. The rest of ADR Forge stages refine earlier stages stands: refinements stay within the brief, the gaps go into each stage's task, and the Review stage comes last."
