## Steps

1. The same model (container API with 1,100 components, Small with 2)
2. create_view {tempId:'g', name:'Components', viewpoint:'Components of a container'}
3. smart_layout {viewId: <API's view>}
4. update_view {id: <API's view>, kind:'table'}

## What differs

```text
Expected: The reply says only Small was laid out and API is too large for a canvas; the refusal advises something the server accepts for a view per element
Actual: Reply: 'Smart Layout arranged the 2 new views per element'; views.json: Small 4 places, API 0; smart_layout on API: 'Show it as a table (update_view with kind "table")'; update_view: refused 'its viewpoint, kind, filter and folder are the group's'
Seen: 2 of 2
Where it probably comes from: apps/mcp/src/folderModel.ts (~line 983) counts fresh views whatever this.smartLayout returned; packages/common/src/ai/tools/layoutTools.ts noCanvasLayout gives the table advice also for partOf views
A test that would catch it: apps/mcp/src/folderModel.test.ts: create_view with a per-element viewpoint where one element holds 1,001 elements names only the views laid out; smart_layout on that view does not advise update_view kind table
```

## Fixed (2026-11-15)

Create_view and other writes name only the views per element Smart Layout arranged and give the refusal for the others, and for a view per element the refusal (and update_view's) advises upsert_viewpoint with kind "table", which the server accepts.
