label: "Radical Crucible"
alternatives: "Keep the flow as documents and scripts in this repository only (works for us, offers nothing to others). Integrate an existing AI testing service (no access to the model's rules; findings do not come back as bound tests). Only a fuzzing library (misses what needs eyes: camera, wording, expectations). Only exploratory agents (finds siblings a round late, never proves a rule holds)."
consequences: "Projects that keep a Radical model get their rules checked by machine and searched by agents, and each finding ends as a bound test. The model gains weight as a specification: its requirements become oracles, so vague ones show up. Running agents costs tokens and machine time (a round of twenty used one laptop fully); the orchestrator must cap resources and survive API limits. Deriving properties from EARS needs a mapping from the requirement's words to the system's actions, which a project has to supply or an agent has to propose and a person confirm. The repository's own exploratory flow (briefs, verify scripts, fix rounds) becomes the framework's reference use and moves into it piece by piece."
context: "radical.tools has been tested in exploratory rounds since 2026-10-13: agents briefed by docs/EXPLORATORY-TESTING.md, each finding re-run by the maintainer's session, the open points decided by the maintainer, the fixes made by agents in worktrees with a test that fails first, and the tests bound to the model's scenarios for radical check. Runs 1 to 69 found about 250 bugs no test described, and about half of each recent round was a rule broken in a place no test named (ADR Rules checked as invariants, whose fuzz test is the first piece of machinery for it). The loop works but lives in briefs, shell scripts and a person's session; nothing in the Radical family offers it to other projects, and existing tools each cover one part without the model: property-based engines (fast-check, Hypothesis, QuickCheck) have no oracles, AI explorers (Mabl, Testim, Meticulous) do not know a system's rules, deterministic simulation (Antithesis) works below the product's rules."
date: "2026-10-21"
decision: "Build Radical Crucible as a member of the Radical family, around one loop: the model is the source of the oracles, three ways of searching find where the code breaks it, and every finding goes back into the model. The name pairs it with Radical Forge: Forge builds the model, Crucible puts the code to the test against it. Its parts: (1) oracles: generic invariants of a stateful application (undo exact, save round trip, reload changes nothing, nothing moves by itself, no dangling references, no console errors), rules derived from the model (EARS requirements as properties, state machines as allowed transitions, the domain model's invariants, ADR decisions), and the maintainer's decisions on exploratory questions turned into rules; (2) drivers: in-process (a store or an API), UI through Playwright and the accessibility tree, MCP and CLI, and several actors at once (a user and an agent on one folder); (3) fuzzing: action sequences from a declared or discovered action model, shrinking, seeds and replay, a survey mode, failure signatures, a known list tied to findings, fixed seeds in CI and random ones at night; (4) exploration: agents briefed from the model and from what changed, disjoint areas, isolation, reproduction scripts, every finding re-run before it is shown, a search for the same pattern elsewhere, questions kept apart from bugs; (5) hardening: a deterministic test written from a finding, a fails-first gate, a flakiness check under load, and the binding to a scenario; (6) a coverage map in the model and the Inspector: per requirement and ADR its scenarios, invariants and last exploration, with goals in check.json; (7) a decision queue whose answers become ADR amendments and rules. It starts as three commands of the radical CLI (radical fuzz, radical explore, radical harden) extracted from what this repository does today, with radical.tools as its first user; deriving oracles from EARS and state machines comes after."
status: "proposed"
