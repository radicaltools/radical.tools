decision: |
  Build Radical Crucible as a member of the Radical family, around one loop: the model is the source of the oracles, three ways of searching find where the code breaks it, and every finding goes back into the model. The name pairs it with Radical Forge: Forge builds the model, Crucible puts the code to the test against it. Its parts: (1) oracles: generic invariants of a stateful application (undo exact, save round trip, reload changes nothing, nothing moves by itself, no dangling references, no console errors), rules derived from the model (EARS requirements as properties, state machines as allowed transitions, the domain model's invariants, ADR decisions), and the maintainer's decisions on exploratory questions turned into rules; (2) drivers: in-process (a store or an API), UI through Playwright and the accessibility tree, MCP and CLI, and several actors at once (a user and an agent on one folder); (3) fuzzing: action sequences from a declared or discovered action model, shrinking, seeds and replay, a survey mode, failure signatures, a known list tied to findings, fixed seeds in CI and random ones at night; (4) exploration: agents briefed from the model and from what changed, disjoint areas, isolation, reproduction scripts, every finding re-run before it is shown, a search for the same pattern elsewhere, questions kept apart from bugs; (5) hardening: a deterministic test written from a finding, a fails-first gate, a flakiness check under load, and the binding to a scenario; (6) a coverage map in the model and the Inspector: per requirement and ADR its scenarios, invariants and last exploration, with goals in check.json; (7) a decision queue whose answers become ADR amendments and rules. It starts as three commands of the radical CLI (radical fuzz, radical explore, radical harden) extracted from what this repository does today, with radical.tools as its first user; deriving oracles from EARS and state machines comes after.
  Packaging (settled 2026-10-22): the engine is a workspace of its own, packages/crucible, published as @radicaltools/crucible on the one product version; the commands are in the radical CLI; a project's Vitest can import the engine without the CLI.
  How a project uses it: one fuzz file per system it drives declares the actions (weights, arguments that pick targets by index so every shrunk sequence runs, whether an action edits), how to settle (driven to rest before every check), what to observe, the invariants (the generic ones given adapters, plus the project's own as functions of the observation before and after a step) and the plans (fixed seeds for CI, random ones at night). radical fuzz writes JUnit with one case per world and invariant (`crucible/store.fuzz.ts › bookstore › undoRestores`), so scenarios and fitness functions bind to invariants with no change to check. A failure's signature (its rule, its last action and the shape of what differs, without ids) groups failures and filters the known ones; a known entry no run hits for a week is reported as stale.
  Findings: fuzzing and exploration hand back one record (title, source, rule, signature, steps with world, seed and path, expected and actual, how often seen, commit, status, binding), which replaces today's three copies (the fuzz test's KNOWN entry, the IMPROVEMENTS item, the test.fail). Its status goes open → hardened (a bound test that fails) → fixed; a finding that may be intended is a question for the decision queue, whose answer adds a rule either way.
  Open points, as proposed: the mapping from a requirement's words to actions lives in code, in the fuzz file's vocabulary, proposed by an agent and approved in a pull request, state machines before EARS; agents get only what needs eyes, capped in crucible.json (4 in parallel by default, tokens and wall time per round) with a round journal to resume after API limits; every driver has settle(), a manual clock in-process and an idle signal from the app in the UI, UI failures replayed and shrunk in-process; a requirement no oracle can be derived from goes to the decision queue with the reason, and check shows requirements with an oracle as a metric without a goal.
  Phases, each with a gate measured on this repository's history: (1) radical fuzz: on main at #230, before the fixes, it finds the same 22 violations, and the CI plans stay under a minute; (2) radical harden: the tests generated for #232's fixes fail before each fix and pass after it, 10 runs of 10; (3) radical explore: on the commits of runs 65 to 69 a round finds at least half of what they found, tokens recorded; (4) oracles from the model: the model's two state machines and one EARS requirement become oracles that run in CI.
