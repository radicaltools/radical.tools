consequences: "A run leaves the model in the shape radical.tools' own model has, and a later run, an agent or a hand edit appears in the views without listing anything. Views of viewpoints the run never fills are not made. Relations across layers show where a viewpoint's chain follows them (Traceability, Responsibilities, Decisions) instead of on none of the views. Table, wiki, matrix and Warnier views lay themselves out, so most stages offer fewer canvases to arrange. A view whose chain shows elements only for a while (Requirement gaps until scenarios verify the requirements) stays once made. Layer canvases keep working as before for those who prefer them."
context: "Radical Forge filed its output into six canvases of its own (ADR Forge files its output into layer views), listing each element in them. radical.tools' own model is structured differently: a view of each of the metamodel's viewpoints, in the folders Conceptual, Logical and Governance, none of which lists elements; each shows what its filter chain gives, so it stays current as the model grows. The owner asked Forge to ask for the structure before it models, with the radical model's as the default, a way to adjust it, and views made only when something lands in them."
date: "2026-10-18"
decision: "Before a run starts, Forge offers two structures (ForgeStructure in @radical/common/ai/forge/views.ts): Radical, the default whenever the metamodel has viewpoints, and Layer canvases, the six canvases as before. Radical is a list of viewpoints with a folder each (RADICAL_FOLDERS, radicalViewpoints: Conceptual for domain map, domain model, traceability, specification, entity lifecycles, event catalogue, processes, screen flow and screens; Logical for system context, containers, components, container dependencies, domain realisation and responsibilities; Governance for decisions, decision log, fitness functions, requirement coverage and requirement gaps); a viewpoint of another metamodel goes into a folder named after its group and is left out unless ticked. The user can untick any viewpoint. The structure is preselected from the model (defaultForgeStructure): Layer canvases when it has a Forge layer canvas (a static view named Conceptual that lists elements) and no view of a viewpoint, Radical otherwise; it cannot change once the run has started. With Radical, after the need is stored and after each stage, every chosen viewpoint the model has no view of yet gets one (named after the viewpoint, in its folder) as soon as its chain shows an element, the model's elements from before the run included; the model's view of a viewpoint is reused wherever it sits. A stage runs on its view when that is a canvas and on All elements otherwise; afterwards Studio shows the stage's preferred view (forgeStageView: Traceability for requirements and scenarios, Domain model, Fitness functions, Entity lifecycles, Processes, Screen flow, Containers), else the first view the stage filled. The Arrange questions cover the static views among them that show the stage's new outermost elements; over MCP new elements are placed beside what such a view shows (computed from its chain). Studio asks on the Description step; over MCP forge_start takes views: { structure, viewpoints } and the procedure tells the agent to ask the user first."
