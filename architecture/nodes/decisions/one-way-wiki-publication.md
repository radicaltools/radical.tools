label: "One-way wiki publication"
alternatives: "Raw node Markdown or Markdown attachments lose the selected view's generated hierarchy and composed model prose. A single Confluence page remains available but is insufficient as the only mode for a large wiki. Duplicate pages for every graph occurrence cause multiple copies of the same requirement/scenario and break stable identity. A local mapping cannot be recovered on a fresh CI runner. A single large content property can exceed Confluence's size limit, so mappings are bucketed. Bidirectional sync conflicts with Radical remaining the source of truth."
consequences: |
  A page tree makes large company wikis browsable without putting hundreds of elements into one page. It adds mapping, partial-failure and graph-to-tree semantics; the canonical first-parent rule is explicit and crosslinks retain other occurrences. Titles are prefixed by the wiki name and duplicate names get a stable short suffix; IDs remain stable across later renames through the remote mapping. Up to four writes run concurrently, with checkpoints between batches. Interrupted writes are reported with the landing-page ID for a rerun. Confluence body edits are replaced by publication; comments are not imported. Previously exported pages removed from the view are reported and retained. Cloud is supported first; Data Center needs another transport. Local images and interactive mockups are not uploaded and produce warnings. --structure document remains available as the simpler publication mode.
  Moving the existing Studio composition into common preserves the interactive wiki's behavior while making export content follow it. Output markup is renderer-specific; field selection and model prose are shared. Headless tests cover the shared document and CLI adapters, while existing wiki browser tests guard editing, nested chapters and navigation.
context: "Companies read architecture documentation in Confluence while Radical remains the source of truth. A wiki is a generated view of typed elements and relationships, not a collection of independent Markdown pages. Its chain may show one element under several parents. The existing CLI must export a particular wiki, including the Tes confluence requirement-to-scenario view."
date: "2026-10-17"
decision: |
  Add radical export confluence [folder] --view <id-or-name>. Local exports produce a complete document as Markdown, Confluence storage XHTML or a standalone HTML preview. Explicit --publish defaults to --structure tree: a managed landing page and one page per distinct element. --structure document publishes one page instead. Reuse the model view pipeline and metamodel prose helpers. Preserve chain hierarchy, requirement sentences, Markdown fields, references and in-scope relationships. An element reached under several parents has one canonical page beneath its first occurrence, with links from every other parent. Native Confluence page links use planned titles so forward references resolve when all pages exist. Keep stable element-to-page IDs in bounded, versioned content-property buckets on the landing page; do not write publication state into Radical. Checkpoint successful writes and recover interrupted creates by title plus a stable view/element ownership marker. Never adopt unrelated pages. Updates verify ownership and use the current page version. --parent-id creates or moves the managed landing page beneath the chosen parent; changing an element's canonical parent moves its managed page. Never delete stale or unrelated pages automatically. Publishing reads credentials from environment variables, supports --token-env for a named variable, includes a source-of-truth notice and never imports changes from Confluence.
  Wiki content composition lives in a pure @radical/common/wikiDocument builder used by both WikiView and the CLI. It owns visible scope, navigation and page children, complete document occurrences, field classification and visibility, requirement sentences and their full-model subject/state context, relationship grouping/details and glossary counts. It exposes structured page blocks with source property/relation identities; Studio renders editable React controls from them, while CLI renderers translate them to Markdown or Confluence markup. Publication banners, native Confluence page identity/mapping and transport stay in the CLI. Do not maintain a second set of wiki content rules in an exporter.
status: "accepted"
