alternatives: "More exploratory rounds only (each finds about half siblings again, and finds them a round late). One hand-written test per place a rule applies (the list goes stale as actions are added). A command layer every store edit goes through, deciding undo, milestones, saving and merging in one place (the structural fix; a large refactor of diagramStore.ts, still worth doing, and the invariants are what would show it changed nothing)."
consequences: "A rule broken in a place no test named, or by a fix next to it, fails CI before an exploratory run finds it. Exploratory runs keep what no invariant can say (camera, wording, what a user expects to see). The test needs the store to run headless with deterministic layout; actions that depend on timing (the live physics, a drag's frames) are driven to rest before the check, and some rules hold only up to a tolerance (half a pixel). A random sequence that finds an old open point listed in IMPROVEMENTS is filtered out by name until it is fixed, so a known gap does not keep CI red. The engine around the store's actions and rules (plans, seeds and replay, shrinking, survey, the known list, signatures) is Radical Crucible's (@radical/crucible, which brings fast-check), and the test is its first fuzz file."
context: "Exploratory runs 1 to 69 found about 250 bugs no test described. Every fix came with a test of the scenario reported, and those tests hold: a fixed bug does not come back where it was fixed. Yet each round about half of what it found was the same broken rule elsewhere: in runs 45 to 64 about 40%, in runs 65 to 69 about half (the wiki's relation editor after the card's and the canvas's, Quick Search on a relation after D12 for elements, a merge's relation ends after Undo's item 127, the viewpoint select in a milestone after the Lines select), plus fixes that broke a neighbour (the fix of item 3 made every agent write drop Smart Layout's result, item 236). The store's actions each apply the rules of undo, milestones, saving and agent merges themselves, so one rule lives in many places, and a test of one scenario cannot see the others nor the combinations of two features where most findings lay."
date: "2026-10-21"
decision: "The product's rules that docs/EXPLORATORY-TESTING.md uses to tell a bug (\"How to tell that something is wrong\") are also checked by machine, as invariants over random sequences of store actions. A property-based test (fast-check, in @radical/ui's tests) builds sequences of user and agent actions (add, delete, move, drag, collapse, align, Smart Layout, view and milestone switches and edits, an agent's write merged with mergeModels, undo, redo, a reload) on several models and checks after every step: undo then redo gives the state back exactly; a save read back is the same model; a reload moves and writes nothing; every child lies inside its parent and no siblings overlap on the canvas shown; no relation, step or view entry points at nothing; an edit while a milestone is shown leaves the live model as it was. CI runs it with fixed seeds; more seeds run on demand. A failure shrinks to the shortest sequence that breaks the rule, which becomes a plain regression test with its fix. Where a rule is a list (every action that edits a view, every place that makes a relation), a test walks the whole list rather than one member."
