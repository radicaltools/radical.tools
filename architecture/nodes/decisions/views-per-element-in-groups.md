label: "Views per element in groups"
alternatives: "A view per element made once, by New view or Forge, and left to the user (the owner wanted a new container to appear by itself, under one entry). A group computed at display time without stored views (each view needs its own positions, routes and slides). A parameter in the chain resolved at run time (every reader of view.pipeline would need the subject; storing the scoped chain needs none). One view of a single element picked in New view beside the groups (the owner chose groups only)."
consequences: "A run with three state machines and four processes gets two entries in the list, each opening onto small views that read and lay out on their own. A container added by hand, by an agent or by a later stage gets its view in its group without anyone making it; one deleted takes its view along. The whole-model viewpoints stay available in New view. Context outside the element (people, other systems, entities of other domains) comes from a second level of the chain, so it shows only what is linked to the element's inside. The group's views are stored like any view (views.json), so other tools see them; their positions are their own."
context: "A viewpoint was a view type and a filter chain, so a view of it showed every element the chain gives: one Processes view with every process, one Containers view with every system's containers, and no structure view of state machines at all. C4 draws a container diagram for one software system and a component diagram for one container; a state machine and a process read on their own. The owner asked for a view per state machine, per process and per container, wherever that makes sense, and for Forge to make them."
date: "2026-10-19"
decision: "A viewpoint may name the types it makes a view of each of (ViewpointDef.subject: { types }); Studio calls such a viewpoint, and its views, View per element. A view of such a viewpoint is a group: it holds a view of each element of those types that is not external (DiagramView.partOf and subject), whose chain is the viewpoint's with the first level kept to the element and what lies inside it (a within filter with self, scopedChain in @radical/common/viewpoints.ts), so the canvas, table, Warnier and every count read it as any chain. model.syncViewGroups (planned by planViewGroups) makes a view when such an element appears and removes it when the element goes, is retyped or made external; Studio's store runs it in _sync, the headless facade after each change, so a new element joins its group at once in Studio, over MCP and in Forge. The views are named after their element and follow its name until renamed, sit in the group's folder (moving one moves the group), follow its viewpoint, cannot be deleted, detached or retyped alone, and go with the group. New view marks these viewpoints View per element and opens a new group on its first view; the list of views shows the group as one card, marked too, that shows or hides its views. create_view and update_view with such a viewpoint make a group, upsert_viewpoint takes subjectTypes, and the metamodel editor sets the types (View per element). The Radical metamodel brings State machine, Process, Containers of a system, Components of a container and Entities of a domain; C4 brings the two C4 ones. With the Radical structure Forge makes the group of each in Conceptual or Logical, and leaves the whole-model viewpoints Containers, Components, Process (Warnier) and Domain model unticked."
status: "accepted"
