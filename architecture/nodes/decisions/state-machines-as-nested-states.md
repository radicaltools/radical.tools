label: "State machines as nested states"
alternatives: "The full UML notation (regions, entry and exit points, junctions and forks as their own types): more types without more meaning for what people, agents and Forge write. A region type: a parallel state's children are regions already. Pseudostates as kinds of state: a pseudostate is never active, holds nothing and has a fixed small size, which the metamodel ties to the type. A machine tied straight to a C4 element (the first draft, `lifecycle-of` machine → component): it mixed what the lifecycle is of with what runs it. The entity as text on the machine (`subject`, the first draft): nothing to link requirements, owners or other machines to. Transitions as nodes linked to their events: see ADR Properties can reference nodes. A separate behaviour preset: models on the governance preset would not get it, and presets extend each other."
consequences: "Every model on the unedited governance preset gets the types on its next load (ADR Edited presets fork). The palette and the metamodel diagram have a States group; unit and e2e counts were raised to match. Radical Forge got a State machines stage between the scenarios and the mockups, with a States view of its own (ADR Forge files its output into layer views), and the MCP server returns the statechart warnings a write brings in. Statecharts are laid out by the general Smart Layout, which knows nothing of their cycles and long labels yet; a layered layout for them is the next step."
context: "The product owner asked for event-driven hierarchical state machines in the metamodel, and for a Radical Forge stage that derives them from the scenarios before the mockups. The lifecycle of an entity (an order, a payment) had no notation: Gherkin scenarios describe its state changes, but nothing in the model held the states. The metamodel already has nesting (canvas containment), typed relations with properties and soft validation."
date: "2026-10-09"
decision: "The C4 + DDD + Governance preset gets four node types, state-machine, state, pseudostate and event, with SCXML / XState semantics, and the DDD preset an `entity` type (a domain object; kind aggregate-root or entity). States nest by containment inside a machine or another state; a state with child states is compound; kind parallel makes its child states regions active at once; kind final ends its parent. A machine and every compound state that is not parallel enter through one initial pseudostate with a single transition to the default child. The model keeps three concerns apart: a machine is the lifecycle of one entity (`lifecycle-of`, machine → entity, one machine per entity); the C4 elements that run it implement it (`implements`, system/container/component/web app → machine, extending the relation fitness functions use for ADRs); the element that owns the entity's data realises it (`realises`, C4 → entity, extending the DDD relation). A transition carries guard, actions and kind, and points at its trigger (`event`) and at the events it raises (`raises`) with reference properties (ADR Properties can reference nodes); a state-driven requirement points at the state it holds in with `precondition_state`, and its EARS sentence reads \"While the <entity> is <state>\". A state publishes an event with emits (on entry, exit or do). @radical/common's statechart.ts checks the statechart rules as warnings in validateModel, including a machine with no entity and an entity with two machines. The canvas draws statechart notation, names a machine after its entity, labels a transition `event [guard] / actions ^raised`, and the live layout nests machines and states like systems, domains and groups."
status: "accepted"
