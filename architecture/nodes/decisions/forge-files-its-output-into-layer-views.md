label: "Forge files its output into layer views"
alternatives: "Layer groups as in this repo's model (moving elements into containers changes the model, not how it is viewed); one view per stage (requirements and the scenarios that verify them apart); all three views created at the start (an empty view shows the whole model); arranging every stage automatically (the owner asked to be asked, and Smart Layout on a large view takes seconds and redraws what they arranged by hand)."
consequences: "Each layer is readable on its own and a stage no longer lands on the previous one. Relations across layers (satisfies, traces-to, constrains, verifies from a scenario to a state machine) show on none of the views; All elements and the table views still show everything. The name is the key: a renamed view makes the next run create a new one, and a regenerated stage leaves its view in place (empty, it shows the whole model again). Chat runs in Studio place sideways too. A grid or row the user picks is a layout constraint like any other (ADR User alignments bind layout). State machines get one shared States view rather than one view per machine: a run rarely makes more than three, and their frames keep them apart."
context: "Radical Forge put every stage's elements on whatever canvas was open, placed by the AI runner in rows of four that restarted at the same spot each run. A full run (dozens of requirements, scenarios, fitness functions and C4 elements) became one tall canvas whose stages lay on top of each other until the live physics pushed them apart. This repo's own model reads in layers (ADR Model in two layers), and its owner asked for the same split and to be asked how to arrange each stage."
date: "2026-10-08"
decision: "A Forge run adds each element to one of four static views by type: Conceptual (need, requirement, scenario, mockup), States (state-machine, state, pseudostate, event; added 2026-10-09 with the State machines stage), Logical & physical (C4 elements) and Governance (fitness-fn, adr); any other type follows its stage. A view is found by name and created when its first element arrives, because an empty view shows the whole model. Studio runs a stage on its view (on All elements while the view does not exist yet) and shows the view afterwards; the MCP server files the elements at forge_start and forge_complete_stage and writes their positions on the view. New elements go beside what the canvas shows, in a block that grows wider than tall (landscapeSlot, createBatchPlacer). After each stage Forge asks whether to keep the stage's outermost new elements in a row or a column (in creation order) or a landscape grid on their view, and whether to run Smart Layout on it: Studio's Arrange panel, and over MCP the forge_complete_stage answer plus forge_arrange. Nothing is arranged without the user's choice. The rules live in @radical/common (src/ai/forge/views.ts) and the placer in @radical/layout, for both."
status: "accepted"
