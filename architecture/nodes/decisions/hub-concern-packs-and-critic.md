label: "Hub concern packs and critic"
alternatives: |
  1. Keep the concepts and improve their content: they would stay single elements that break the check on import, and still compete with what the model writes.
  2. A critic made only of a language-model review (Forge's Review stage): it guesses what is missing, differs from run to run and cannot gate CI.
  3. Recognise a concern by the words of an ADR instead of a marker: fragile across languages and wordings, and a dismissal could not be recorded.
  4. Concern packs without a critic: the user would still have to know which concerns apply, which is the knowledge the Hub should bring.
  5. Drop the Hub: loses the place where know-how about decisions and their checks can be shared, by us now and by organisations later.
consequences: |
  • A pack is worth more than a concept and costs more to write: a few deep packs instead of many shallow concepts; every pack must pass radical check once imported and bound (fitness function Concern packs pass check).
  • The critic is deterministic and runs in CI; a language model may later phrase its questions in Forge, but does not decide what applies.
  • A trigger that finds too much makes the critic nag; triggers are tuned for precision, and a team can always settle a concern with an ADR that says it does not apply.
  • The Radical metamodel gains an optional `concern` property on ADRs; a model on the C4 metamodel or a fork without it has no concerns to report.
  • A trigger depends on the types of the metamodel it was written for; a pack declares that metamodel (requiredMetamodel) and the rule skips packs whose metamodel the model does not use.
  • Next steps, not in this step: the critic's questions in Forge's clarify and Review stages, binding in Studio's import dialog, more packs, and a Hub of an organisation's own standards that team models take in through federation.
context: "The Hub holds 128 concepts: ADRs, patterns, fitness functions, requirements and blueprints. Almost every one is a single element with no relations (relations: []), and hubRefs link concepts only inside the Hub. An imported requirement has no need it derives from, nothing that satisfies it and no scenario; an imported fitness function implements no ADR and names no test; an imported ADR constrains nothing. The model's own rules (requirement-without-origin, requirement-unsatisfied, fitness-fn-unlinked, ...) then flag what the import brought in. The texts are generic (\"OAuth 2.0 / OIDC with a 15-minute token\"), which Radical Forge's model writes as well, and fitted to the system at hand. The blueprints are large generic C4 pictures. Nothing in this repository's own model came from the Hub. The matching benchmark (ADR Hub matching ranks, the model picks) measures whether the right concepts are suggested, not whether a model is better for them."
date: "2026-10-22"
decision: "The Hub holds only concern packs: each covers one concern (authentication, authorization, personal data, backup and recovery, integration resilience, messaging, observability, secrets, API evolution, rate limiting) in the catalogue as category `concern` (catalogue/concern/<id>.radical), whose hub block holds (1) the concern's id and a trigger: a LIST NODES or LIST RELATIONS query in the model query language, and for relations the end the concern applies to (the query language gains source.external and target.external for it); (2) the questions that force the decision, as the pack's template parameters with options; (3) a connected slice: a need, the EARS requirements derived from it, an ADR marked with the concern (the ADR's new `concern` property in the Radical metamodel), the fitness functions that implement the ADR, and the scenarios that verify the requirements. The answers fill the texts and pick the variant: an element of the slice may name the answers it is imported for (hubWhen), so an answer such as \"nobody signs in\" brings an ADR saying the concern does not apply. Importing a pack binds it to any number of elements: the ADR and the fitness functions constrain each and each satisfies the requirements, so the slice passes radical check apart from the tests the team still has to write; bound to none it comes in unbound. Two check rules make up the critic, both in the decisions dimension and warnings by default: concern-unaddressed reports, for every pack whose trigger finds elements that no accepted ADR marked with the concern constrains (directly or through an element containing them), the concern once, with those elements and the pack's questions, and says when a proposed ADR is still being decided; concern-unbound reports an accepted ADR marked with a concern that constrains nothing, with where to bind it. An accepted ADR addresses the concern whatever it decides, so a dismissal is kept in the model and asked about no more; a superseded or deprecated one does not. Findings are coded with the pack or concern id, so a project can set one concern apart. The rules get the packs from their caller (the CLI and the MCP server from the catalogue they bundle, Studio from the Hub catalogue it loads), so @radical/common does not depend on the catalogue. The MCP server's get_issues lists the unaddressed concerns with where to bind them, and forge_import_hub_concept takes the answers and the elements. In Studio the Inspector offers each unaddressed concern's questions, which open a wizard like the node wizard on the pack: where it applies (the fewest elements that cover all checked), one question a step, the details, and a review. The single concepts and blueprints are removed with the import paths only they used (the blueprint and related pickers, the template form); the blueprints and patterns stay in the repository as Smart Layout's bench models. Forge's use of the packs: ADR Forge settles concerns, C4 binds them."
