label: "Federation composed by the CLI"
alternatives: "A central architecture repository: model and code in two pull requests that drift apart, one bottleneck for review, check needing every repository's test reports. (Drawn again on 2026-11-01 as one C4 model with a radical.json in each code repository naming the elements it implements: it answers the review and the evidence with paired branches, two gates and a nightly discovery, at the cost of those two pull requests; kept as a variant, not chosen.) A hundred independent models: no landscape, copies of shared elements, references between systems never checked. Published model packages in a registry: infrastructure to build before any value; the source in deps.json can become one later. Git submodules: whole repositories with code, a pinned commit not known to be checked, edits inside them possible. Native multi-model workspaces in Studio and the MCP server: the right end state, but a large change to both; the composed folder gives the same picture now."
consequences: "A repository's model holds references to other models' elements (relations by UUID) and never copies of them. Studio and the MCP server need no notion of several models: they see one folder. Since the amendment there is one copy: Studio, in the browser too, and the MCP server edit the model folder, and only the other models' elements come from a file the CLI fetched; Studio reads the file again when a fetch changes it. Fetching stays the CLI's (git), so a folder never fetched shows only its own model, and Studio says which command fetches the rest. The branch's changes and the base compare only the model's own elements. Checking needs the dependencies fetched: CI needs read access to their repositories. A landscape repository is one more model whose dependencies are all the systems."
context: "An organisation with a hundred code repositories needs one picture of its architecture while each team changes its own part together with its code, in one pull request (Model first, then the code). Studio and the MCP server open one Markdown folder; radical check checks one; element ids are UUIDs, so they are unique across models. A relation to an element a model does not have is the error rel-end-missing."
date: "2026-10-17"
decision: "Each repository keeps the model of what it implements and names the models it depends on in deps.json (name, git repository, model folder, pinned ref). The CLI composes the federation: it fetches each dependency's model at its ref from git into a cache, and writes one model folder under the repository's .radical/federation/ with the repository's own elements and relations as they are and every dependency's marked with origin <name>@<commit>. Studio and agents open that folder. radical federation sync (and watch, continuously) carries back to the repository's model folder only what has no origin, and refuses any change to what has one. radical check composes the federation itself when the folder has deps.json. The product itself only refuses edits to elements and relations with an origin, in the shared model operations (so Studio and the MCP server alike), and marks them. Amended 2026-11-01 (the product owner's choice): Studio and the MCP server open the model folder itself, not a composed copy. radical federation fetch fetches the dependencies, theirs too (a model pinned twice comes at the nearest pin), and writes their elements and relations, each with its origin, into the model folder's .radical/federation.json, out of git; the git hooks of radical hooks install run it in the background after a checkout, a commit, a pull and a rebase. Studio and the MCP server add those elements when they read the folder and never write an element or relation with an origin into it, so there is no second copy to keep in step: the composed folder, sync and watch are gone."
status: "accepted"
