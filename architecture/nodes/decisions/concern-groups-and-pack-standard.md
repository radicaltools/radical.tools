label: "Concern groups and pack standard"
alternatives: |
  1. Group by quality attribute only (ISO 25010): authentication and secrets both land in Security, data retention and backups split between Security and Reliability, and Technology has no place.
  2. Free tags instead of groups: no single place to look, the inconsistency the review found.
  3. The proposed list (communication, data, API, authentication, tech stack, resiliency, maintainability, security, quality): mixes areas, attributes and a subgroup.
consequences: |
  • One question decides where a pack goes: where is the decision made.
  • A pack costs more to write; fewer, better packs.
  • Fitness functions come with something to run, so a team can name its test the same day.
  • The catalogue grows by group; empty groups show what is still missing.
  • Structural decisions (style, monolith or services, sync or async) get their own group, first in the list, instead of hiding in Maintainability and Integration.
  • Every requirement of a pack has a check or a written reason; a variant with a requirement and no fitness function no longer builds, so packs grow fitness functions (about 60 were missing) and a few honest unchecked reasons.
  • The same fact never fills two packs with two numbers; a pack that needs another's decision names the pack instead of asking again.
  • A pack cannot ship a snippet that was never run: writing one costs a sample run or a documentation check.
context: "The first ten concern packs sat in one flat list, and a classification proposed for them mixed three axes: areas of the system (communication, data, API, tech stack), quality attributes (resiliency, maintainability, quality) and a part of another group (authentication within security). Their contents were uneven: two or three questions, requirements without numbers, decisions that named no technology, fitness functions described in prose that nobody can run, and no sources to check them against."
date: "2026-10-22"
decision: "Every concern pack belongs to exactly one group, by the area of the architecture where its decision is made: Architecture (how the system is structured and divided and how its parts talk to each other: architectural style, decomposition, communication style, module boundaries), Identity & access (who calls and what they may do), Security (protection against abuse and leaks), Data (what is kept, for how long, how consistently), Integration (how the system talks to others), Reliability (how it behaves under failure and load), Operations (how it is run and watched), Maintainability (how its code is tested and changed) and Technology (what it is built on: backend stack, frontend stack, infrastructure, data store). Each group names the ISO/IEC 25010 characteristics it serves. A pack's hub block holds its group (concern.group) and its sources (title and link: OWASP ASVS, GDPR articles, Google SRE, ISO 25010, 12-factor, the tools' own documentation), which the pack is reviewed against but which the Hub and Studio do not list. The Hub, Studio's import dialog and the concern wizard show and filter packs by group. Every pack meets a standard that the catalogue's validation enforces where it can: at least three questions with options, each option saying what it means and when to pick it; at least two sources; every fitness function naming its tool (a Tool: line) and carrying a snippet to copy (a fenced block). What it cannot check is reviewed: requirements carry a number from the answers or a standard where one applies, and decisions name technologies and the criteria to choose between them. Amended 2026-10-28 after a review of all 33 packs (0 excellent, 27 needing work; 29 fitness functions that could not run or could not fail): the build also refuses a {{KEY}} that names no question or detail, a detail no text uses, a token in an option's label or description (a label fills the texts and is not filled; the wizard shows descriptions as written), a snippet that hard-codes a detail's value beside a # KEY comment, an EARS clause starting with the keyword the sentence adds (\"While while\"), an option no element is imported for and no decision names, a fitness function imported with none of the decisions it implements, and (spec level) a requirement named in the checks of no fitness function imported whenever it is, unless it says in unchecked why the team keeps it by hand. Two rules the build cannot check are reviewed: one decision has one owner pack (dependency updates in Dependency hygiene, vulnerability deadlines in Software supply chain, feature flags in Deployment, code ownership in Code review and branching, the latency budget in Capacity, the SLO in Availability, log lines in Error handling and logging, the outbox in Data consistency, consumer idempotency in Messaging, contract tests in API evolution and Communication style, data ownership in Decomposition, migration rollout in Deployment, keys at rest in Encryption) and the others refer to it in words; and every snippet is run against a sample or verified against the tool's documentation before it ships, pinned to version tags, with cloud-, runtime- and framework-bound checks gated on the answer that picks them."
