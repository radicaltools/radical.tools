label: "Studio's speed is measured nightly"
alternatives: "Time budgets in the pull-request gate: they fail on a slow runner and pass a slowdown that stays under the budget. Measuring per pull request on a label: still varies, and is forgotten. A dashboard outside the model: the thresholds would live in a tool, not beside the requirements they keep."
consequences: "A slowdown is seen the morning after, in a finding naming the commit, not in the pull request that made it. The measurements stay out of git (CI artifacts, .radical/measurements.json): without a night in the last three days the fitness function reads stale. Each metric has two conditions: an absolute limit, set at about twice what a developer's machine measures and to be tightened once the nights show what CI measures, which catches a slow drift; and a limit against the median of the last seven nights (radical check --baseline), which catches a jump without one slow night giving a false finding. The night keeps those seven nights' measurements as a CI artifact it hands on to the next night (nightly-history), outside git; the first nights have no baseline, and the relative conditions read not evaluated until they do. Amended 2026-10-30 (the user's decision: the median of seven nights)."
context: "Studio has to stay usable on a model of 20,000 elements (need Smooth with large models), and what a user waits for there (opening, switching views, typing) is time. Time measured on CI's shared machines varies from run to run: a large-model test with a 100 ms budget failed on CI at 115 ms (#289). The agreed SDLC keeps the pull-request gate deterministic (tests, sensors whose result does not vary, radical check), runs the sensors that vary at night, and records what the night finds in crucible/findings through a bot pull request, not in the model or Studio (ADR Sensors measure, the model decides)."
date: "2026-10-30"
decision: "How fast Studio is on a large model is measured at night, not gated per pull request. The nightly workflow (.github/workflows/nightly.yml) builds Studio and drives it with apps/e2e/tests/studio/scale.spec.ts on radical.tools' own model repeated 14 times (21,000 elements): opening the folder, opening it again from its cache, switching views, a letter typed in Quick Search and in the card. The spec writes what it measured; radical sense json reads it as measurements labelled model=radical-x14; the fitness function Large model stays responsive states the conditions, and radical check decides. A condition that does not hold, or a night that measured nothing, becomes a finding in crucible/findings/ (source sense), which the night proposes in a bot pull request. In the pull-request gate the large-model tests count work (files read, model copies, full scans, texts folded) instead of time, so they pass or fail the same on any machine."
status: "accepted"
