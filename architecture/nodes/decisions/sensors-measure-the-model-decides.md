label: "Sensors measure, the model decides"
alternatives: "One tool per fitness function: none covers load, browser, structure and production at once. Thresholds inside each adapter, which reports only pass or fail (JUnit): works today, but the threshold is invisible to the model and to review. Structured condition fields (metric, operator, value, unit): easier to validate, heavier to read and edit in Markdown files and the wiki. Keeping `threshold` as text beside `metrics`: two places for one criterion. Keeping `tests` beside `metrics`: two ways of naming a check. A fitness function between each scenario and its tests: about sixty wrappers that add nothing, and the decision metrics would count tests instead of decisions. Adapters outside the repository, with only the format published: no tool works out of the box. Measurements committed to git or kept in an external store: bot commits and a growing history, or a new service and its access."
consequences: "One condition language and one evaluator for scenarios and fitness functions, in CI and in Studio's Inspector. A threshold is part of the model and shows in its diff; a tool can be swapped without touching the model as long as its adapter emits the same metric. Every supported tool is code the project maintains, so the adapter interface and its contract test have to stay small. A measurement from another job or from production counts only while it is fresh. The model folder format changes (tests and threshold go), so concern packs, Forge's prompts, the wiki and the rules in check.json about tests and thresholds move to metrics. A quality requirement links to its fitness function with traces-to; a quality scenario can state its response measure itself."
context: "A fitness function often depends on several tools: a load test, a browser audit, a dependency rule, a production metric. radical check read only test reports, so a check that is no test runner could not be named (Workspace boundaries, Installable MCP package, Model in step with code), and a numeric threshold lived as prose in `threshold` (Smart Layout quality) or as an assertion inside whatever script wrapped the tool. The model said what was wanted, but nothing compared it with what was measured. Scenarios and fitness functions named their tests in a separate `tests` property, a second way of saying what checks them."
date: "2026-10-29"
decision: "Sensors are adapters built into the CLI (`radical sense <adapter>`): each turns one tool's output into a measurement file in the radical-metrics/1 format (source, time, context, and measurements of metric, value, unit and labels) and judges nothing. The engine is radical check in @radical/common. Scenarios and fitness functions state their checks in a `metrics` property, one condition per line (`api.latency.p95{env=staging} <= 300 ms`, `test(<file> › <title>) passed`), with `combine` (all, any or at least N; all by default) and `max_age`. The engine evaluates each condition against the latest measurement with its metric and labels, and test() lines against the test reports: passed, failed, stale (older than max_age), not run, or invalid. `metrics` replaces `tests` on both types and `threshold` on fitness functions; a model in the older format is migrated on read (tests into test() lines, threshold into the description). Measurements stay out of git: radical sense keeps the latest of each metric and labels in .radical/measurements.json, and radical check also reads the files and directories --metrics gives (artifacts of other CI jobs). Adapters live in the radicaltools monorepo, one module each behind one interface, contributed by pull request with a fixture of the tool's output. A fitness function is not put between a scenario and its tests: both state their conditions directly."
status: "accepted"
