Source, issues and pull requests (radicaltools/radical.tools). GitHub Actions: ci.yml runs on every pull request into main the workspace boundary check, type-check and tests (keeping a Vitest JSON report per workspace and of tools/, artifact test-reports, via tools/test-reports.mjs), the E2E suite (unless labelled skip-e2e; report in e2e-report, with reports/e2e.json) and the MCP package check on Linux and Windows with Node 20 and 24. deploy.yml runs on every push to main: E2E first, then the checks and tests, then it builds Studio and the Hub and uploads them and the website to AWS through an OIDC role (no long-lived keys). A release is tagged v<version> on main by npm run release:tag after the pull request npm run release made (tools/release.mjs: one version in the four released packages and the lockfile, the changelog's Unreleased entries under it). Pushing the tag starts three workflows, each first running node tools/release.mjs check on it: release.yml drafts a GitHub Release with unsigned macOS, Windows and Linux installers and the version's changelog section (pull requests touching the packaging only build them); vscode-publish.yml publishes the VS Code extension (not for a pre-release); npm-publish.yml verifies the npm tarballs of the CLI and the MCP server and publishes them with npm Trusted Publishing and provenance, on the dist-tag next for a pre-release, refusing a tag whose commit is not on main and skipping a version npm already has. npm-publish.yml also runs by hand for one package, a dry run by default, publishing only from main. The E2E suite (e2e.yml) runs in four shards; on a pull request the screenshots that changed are committed to the branch by the job Commit new screenshot baselines, which then starts ci.yml by hand on that commit (a GITHUB_TOKEN push starts no workflow). Once the tests and the E2E suite are done, the job Architecture model runs radical check on architecture/ with that run's reports and fails on an error.
