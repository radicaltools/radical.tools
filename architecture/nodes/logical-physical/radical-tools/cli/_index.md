The `radical` command line (apps/cli, package @radicaltools/cli, private until a distribution decision). `radical check [folder]` checks a Markdown model folder before a commit or in CI: the files read as a model, the model follows its metamodel, it is complete (requirements have scenarios, accepted ADRs fitness functions, scenarios and fitness functions name their tests, …), and with --report the tests they name passed in the Vitest, Jest, Playwright or JUnit reports given. --evidence writes the status of each scenario, fitness function, requirement and ADR as JSON, and --report also keeps the test cases in the folder's .radical/test-results.json for Studio's Inspector. It never writes the model's own files. Rules and goals are set per project in check.json in the model folder (or --config): per rule a severity and a baseline that --ratchet lowers and writes back, per metric a goal in percent that goal-unmet reports when missed; --list-rules lists both. Output as text (with a Goals block), JSON (with every metric) or GitHub annotations; exit 0 (no errors), 1 (errors) or 2 (could not run). The rules and metrics live in @radical/common (src/check), so Studio's Inspector runs the same check. `radical diff [folder]` lists what changed in the model since its version in git (--since, default the merge base with the default branch; text or JSON), the list get_changes gives over MCP, and with --save-base keeps that base in .radical/base.json for Studio; `radical hooks install [folder]` adds git hooks that save it after a checkout, a commit or a pull. Neither writes a model file. The build bundles the private workspaces, as the MCP server's does. CI runs radical check on the repository's own model (job Architecture model, with the run's test reports); npm run check:architecture runs it locally.
