The `radical` command line (apps/cli, the public npm package @radicaltools/cli). `radical --version` (or -v) prints the product version of its build, with the commit it was built from unless the build is the release tagged v<version>. `radical check [folder]` checks a Markdown model folder before a commit or in CI: the files read as a model, the model follows its metamodel, it is complete (requirements have scenarios, accepted ADRs fitness functions, scenarios and fitness functions name their tests, …), and with --report the tests they name passed in the Vitest, Jest, Playwright or JUnit reports given. --evidence writes the status of each scenario, fitness function, requirement and ADR as JSON, and --report also keeps the test cases in the folder's .radical/test-results.json for Studio's Inspector. It never writes the model's own files. Rules and goals are set per project in check.json in the model folder (or --config): per rule a severity and a baseline that --ratchet lowers and writes back, per metric a goal in percent that goal-unmet reports when missed; --list-rules lists both. Output as text (with a Goals block), JSON (with every metric) or GitHub annotations; exit 0 (no errors), 1 (errors) or 2 (could not run). The rules and metrics live in @radical/common (src/check), so Studio's Inspector runs the same check. `radical diff [folder]` lists what changed in the model since its version in git (--since, default the merge base with the default branch; text or JSON), the list get_changes gives over MCP, and with --save-base keeps that base in .radical/base.json for Studio; `radical hooks install [folder]` adds git hooks that save it after a checkout, a commit or a pull. Neither writes a model file. The build bundles the private workspaces, as the MCP server's does, and is given its version, commit and day by @radical/node-files/buildInfo (tsup define). CI runs radical check on the repository's own model (job Architecture model, with the run's test reports); npm run check:architecture runs it locally.

`radical export confluence [folder] --view <id-or-name>` exports a selected wiki as Markdown, storage XHTML or an HTML preview, and with --publish publishes it to Confluence Cloud. Publication defaults to a page tree (--structure document selects one page): one managed landing page and one page per element, following the view's chain with canonical first-parent placement and crosslinks for shared elements. A bucketed content-property mapping on the landing page keeps stable page IDs across renames and enables resuming partial publication. --parent-id places or moves the managed export. It verifies ownership markers, skips unchanged element pages by source hash and remote version, reports version conflicts, keeps stale pages, uses environment credentials (--token-env supports a named token variable), identifies Radical as source of truth, and never changes the source model.
