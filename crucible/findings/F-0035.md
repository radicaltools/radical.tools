## Steps

1. New model, All elements (structure): Software System + Requirement; Alt-drag system → requirement: satisfies
2. Alt-drag the requirement onto the system, 'inside': warning 'Removed the relation System satisfies Requirement'
3. Alt-drag system → requirement again: refused 'System holds Requirement'
4. Responsibilities view: empty; over MCP (f3b-mcp-satisfies.mjs) radical check: requirement-unsatisfied, get_issues: no issues

## What differs

```text
Expected: A governance link (satisfies, constrains) to the holder is kept or counted, or the check counts containment; validation and check agree
Actual: Relation removed, refused again; Responsibilities 2 rows → 0; radical check requirement-unsatisfied 0 → 1; get_issues silent. Existing models already have such relations (injury: ADR Laptop variant constrains Pain Assessment App; architecture/: domain Modelling satisfies 4 of its requirements) and nothing flags them
Seen: 2 of 2 (Studio), 2 of 2 (MCP)
Where it probably comes from: guess: packages/common/src/model.ts relationRefusal / relationsToNewHolders (every type but transition); packages/common/src/check/rules.ts requirement-unsatisfied ignores containment
A test that would catch it: packages/common/tests: after reparentNodes of a requirement into its satisfying system, requirement-unsatisfied reports nothing (or the relation stays)
```

## Decision (2026-10-23)

The user chose: governance relations (satisfies, constrains, verifies and the like) are outside the holder rule. Only structural relations (uses, delivers to, …) between an element and what holds it are refused and removed on a move; a requirement inside the system that satisfies it keeps `satisfies`, and it can be drawn. The model's requirement for the holder rule is updated on the fix branch, with the code.
